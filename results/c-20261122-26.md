## ## Quantitative Speedup Analysis: N-Gram vs. Draft Models

Speculative decoding accelerates text generation by proposing multiple candidate tokens using either a fast heuristic (such as N-gram matching) or a lightweight draft model, and verifying them in parallel against a heavier target model [2, 3]. Because executing $n$ tokens in a batch during verification is more efficient than autoregressive sequential generation, overall throughput increases [1, 4].

*   **N-Gram Prompt Lookup (`--spec-type ngram-simple` with `--spec-draft-n-max 16`)**: N-gram techniques scan the current prompt or history context to match repeating patterns (frequently encountered in code refactoring loops or repetitive tool-call loops). When patterns repeat, N-gram lookup can propose up to 16 tokens instantly without loading a secondary model into VRAM. However, its effectiveness drops sharply on novel code structures or non-repetitive logic.
*   **Small Draft Model Pairing**: In contrast, a neural draft model generalizes better across structural code generation. For instance, pairing a small draft model with a larger target model consistently yields higher acceptance rates on syntax generation than static N-gram tables, though it imposes a static VRAM penalty.

## ## Draft-Model Pairing Feasibility on a Single 24 GB GPU

Running a large language model like Qwen3.8-27B (or Qwen3.6-27B equivalents) alongside a 0.5B draft model (e.g., Qwen2.5-0.5B-GGUF) on a single 24 GB VRAM card is entirely feasible when utilizing quantized weights and a quantized KV cache [9].

*   **Memory Overhead**: A 4-bit quantization of a 27B model (e.g., Q4_K_M or UD-Q4_K_XL GGUF) consumes roughly 16.3 GB to 17 GB of VRAM [9]. Adding a 0.5B draft model consumes an additional ~0.4–0.8 GB depending on its quantization. This leaves a safe margin of 5 to 6 GB on a 24 GB card for active KV caches.
*   **KV Cache Optimization**: To prevent memory exhaustion during long agent trajectories, the KV cache must be quantized (e.g., using `--cache-type-k q4_0` or setting `OLLAMA_KV_CACHE_TYPE = q4_0` if running via Ollama/llama-server wrappers) [9]. For example, running Qwen 27B with a quantized 4-bit KV cache allows scaling context significantly on a 24 GB card, whereas uncompressed F16 KV caches can consume massive amounts of VRAM and trigger memory spilling [9].
*   **Acceptance Rate and Net Speed**: While a 0.5B draft model has a lower semantic alignment with a 27B model than a same-family larger draft, its ultra-low inference latency ensures that even modest acceptance rates ($\approx 0.50 - 0.65$) result in positive net token/sec gains (typically 1.5× to 2x speedups over baseline autoregressive generation).

## ## Multi-Turn KV Cache Persistence and Slot Caching

During long coding agent trajectories, repeated prompt evaluations (system prompts, tool definitions, file structures) create severe prefill bottlenecks. `llama.cpp` addresses this via host-memory prompt caching (`--cram`) and multi-slot execution (`--np`) [20].

*   **Configuration Parameters**: 
    *   `--np <slots>`: Controls the number of concurrent contexts (slots) the server handles [20].
    *   `--cram 256`: Allocates host system RAM (in megabytes) to store pre-computed prompt representations and prefix caches, offloading them from GPU VRAM [20]. 
    *   Prefix caching and slot caching allow `llama-server` to hot-swap cached system prompts directly into the GPU context when a match is detected, bypassing re-prefilling entirely and drastically reducing Time to First Token (TTFT) by 50% to 90% [20].
*   **VRAM Fragmentation Mitigation**: Maintaining multiple agent turns across slots can lead to memory fragmentation if KV blocks are dynamically resized. Utilizing static slot allocation (`--np`) combined with bounded host-memory caching (`--cram 256` or higher based on system RAM availability) ensures that inactive agent trajectories do not bloat GPU VRAM, preventing out-of-memory errors during prolonged tool-call loops.

---

## ## Safety and Regression Guidelines: When to Dynamically Disable Speculative Decoding

Speculative decoding and aggressive N-gram lookups are not universally beneficial and can introduce latency or correctness regressions under specific conditions. Speculative decoding should be dynamically disabled when:

1.  **Vision Modality (`mmproj`) is Loaded**: When processing multi-modal agent inputs containing images or UI screenshots requiring the multimodal projector (`mmproj`), draft models and N-gram heuristics fail to anticipate vision-token cross-attention dependencies, leading to high draft rejection rates and wasted compute overhead.
2.  **High-Temperature / Creative Generation**: When the coding agent is instructed to operate at a high temperature ($T > 0.8$) or during high-entropy creative exploration/brainstorming tasks, token predictability plummets. Low draft acceptance rates under high temperatures cause speculative decoding to run *slower* than standard baseline generation due to verification overhead.
3.  **Strict Determinism or Exact Tool-Call Syntax Constraints**: If a multi-turn agent loop encounters a phase requiring rigid adherence to strict JSON schemas or tool-call syntax where draft hallucinations risk malformed parameters, speculative execution should be bypassed to ensure token-by-token compliance.

---

## ## Conclusion

For KesherAI's local coding agent operated by Roee on a 24 GB GPU, speculative decoding provides a practical 1.6× to 2.3× speedup [9]. Pairing a 4-bit quantized 27B target model with either an N-gram lookup (`--spec-type ngram-simple`) or a lightweight 0.5B draft model fits comfortably within the 24 GB VRAM limit, provided that a quantized KV cache (`q4_0`) is enforced [9]. Multi-turn agent efficiency is maximized by leveraging host-memory prompt caching (`--cram 256`) to eliminate redundant prefill overhead [20]. Finally, implementing dynamic safety checks to disable speculative decoding during high-temperature execution or multi-modal vision tasks ensures optimal performance and response fidelity.
