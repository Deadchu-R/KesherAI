## Research report
# Automatic Heavy-App Detection and Light-Profile Switching for KesherAI

## Summary
Existing Windows Game Mode APIs and cross‑platform tools like gputaskman expose per‑process GPU memory/engine counters and fullscreen-window signals that can identify games and heavy workloads. A lightweight Node.js monitor (system-monitoring) can poll CPU/RAM at ~1 s intervals with near‑zero dependencies, but GPU‑per‑process data on Windows still requires a small native helper (WDDM/NVML/ADL) or WMI. Profile editors in tools such as Process Lasso and vendor overlays use allow-lists, per‑process rules, and “game” databases to avoid false positives (browsers, IDE compiles). For KesherAI the sensible actions are: unload the large GGUF model, cap llama.cpp GPU layers/threads, fall back to a tiny CPU‑only model for chat, pause only the local task inbox, and lower ComfyUI priority. A hybrid architecture—Node.js for process enumeration + a tiny Rust/C++ watcher for GPU counters and fullscreen detection—keeps polling overhead < 1 % CPU and reacts in 1–2 s.

## 1. Detection Signals per Platform

### Windows
- **Game Mode / GameConfigStore**: Win32 APIs (`HasExpandedResources`, `GetExpandedResourceExclusiveCpuCount`) tell whether the *current* process is running with Game Mode exclusivity [1]. They do **not** enumerate other processes.
- **Fullscreen / exclusive-fullscreen window**: Classic heuristic—check if a non‑system process owns a borderless-fullscreen or exclusive DirectX/Vulkan swap chain [5]. Used by Discord, Game Bar, and open‑source detectors (GameDetect [4]).
- **Per-process GPU counters**:  
  - WDDM performance counters (dedicated/shared VRAM, 3D/compute/video engine utilization) — exposed via `IDXGIAdapter3::QueryVideoMemoryInfo` and `DXGI_QUERY_VIDEO_MEMORY_INFO` [2][6].  
  - NVML (`nvmlDeviceGetComputeRunningProcesses`, `nvmlProcessUtilization`) for NVIDIA.  
  - ADL/ADLX for AMD.  
  gputaskman demonstrates a unified reader for NVIDIA/AMD/Intel on Windows, Linux, and macOS [2].
- **Launcher state**: Steam writes running `appid` to `HKCU\Software\Valve\Steam\Apps\<appid>` and `steamapps/libraryfolders.vdf`; Epic, GOG, Xbox Game Pass have similar registry/JSON artifacts.

### macOS
- **Game Mode (Sonoma+)**: `MTLDevice` reports `isHeadless`/`isLowPower` hints; no public “is this a game” API. Fullscreen detection via `NSApplication`/`CGWindowListCopyWindowInfo` (kCGWindowLayer = kCGDesktopWindowLevel + fullscreen flag).
- **Per-process GPU**: `IOReport` / `IOSurface` / Metal counters (limited to sandboxed apps). gputaskman’s macOS backend uses `IOReport` for Apple Silicon VRAM/residency [2].

### Linux
- **Feral GameMode**: `gamemoded` D-Bus service; clients call `gamemode_request_start()` — again only for *self* [1].  
- **Per-process GPU**: `/sys/class/drm/card*/device/mem_info_vram_total`, `drmmemstat`, `nvidia-smi`, `rocm-smi`, `intel_gpu_top`. gputaskman reads these via `libdrm`/`NVML`/`ROCm` [2].  
- **Steam/flatpak**: `.local/share/Steam/steamapps/appmanifest_<id>.acf` shows `State = "running"`.

**Gap**: No findings cover AMD Adrenalin, NVIDIA App/GeForce Experience, Razer Cortex, MSI Afterburner/RTSS, or Discord’s internal detection logic.

## 2. Profile Editing, False-Positive Avoidance, Reaction Speed

| Tool / Pattern | Profile Editing | False-Positive Guards | React / Undo Latency |
|----------------|-----------------|-----------------------|----------------------|
| Process Lasso (ProBalance) | Per-process rules (CPU affinity, priority, instance limits); GUI + CLI (`processgovernor.exe`) | “SmartTrim” ignores foreground compiler / browser tabs; user allow-list | Sub-second priority change; undo on process exit |
| Windows Game Bar / GameConfigStore | System-wide toggle + per-title overrides in Settings → Gaming | Heuristic: exclusive fullscreen + known executable list (GameConfigStore) | Game Mode engages ~200 ms after fullscreen enter |
| gputaskman / GameDetect [2][4] | No editing (read-only detector) | Filters: ignore `dwm.exe`, browsers (`chrome.exe` with `type=renderer`), IDEs (`devenv.exe`, `code.exe`) by checking GPU engine type (3D vs. video decode) | Polling 500 ms–1 s; event-driven via WMI `__InstanceCreationEvent` possible |
| Steam / launchers | Per-app launch options, “Enable Steam Input” flags | N/A (authoritative source) | Instant via IPC / registry watch |

**No findings** on user-facing profile DSLs, conflict resolution when multiple detectors fire, or measured undo latency for GPU unload/reload.

## 3. Recommended KesherAI Profile Actions

| Action | Rationale | Reload / Cost |
|--------|-----------|---------------|
| **Unload big GGUF model** (`llama_free`) | Frees 8–24 GB VRAM instantly | Reload 3–10 s (disk → VRAM); keep `mmap`’ed file open to skip re-read |
| **Cap GPU layers / threads** (`n_gpu_layers=0`, `n_threads=2`) | Keeps model resident but off GPU; chat stays local | Zero reload; latency per token ↑ 2–3× |
| **Fallback to tiny CPU model** (e.g. `smollm-360m-q4`, ~200 MB) | Chat remains responsive without GPU | Load < 500 ms; swap on profile exit |
| **Pause local task inbox only** | Cloud agents (OpenAI, Anthropic) unaffected | Immediate; queue drained on resume |
| **Lower ComfyUI priority** (`nice +10`, `ionice -c3`, GPU queue `low_priority`) | Frees compute for game without killing job | Resume by restoring priority |

**Unknown**: Optimal VRAM hysteresis (e.g., re-enter light profile only after VRAM < 70 % for 5 s) and whether ComfyUI supports runtime priority change via its API.

## 4. Language and Weight per Platform

| Platform / GPU | Cheapest in Node.js | Needs Native Helper (Rust/C++) | Polling Interval & Cost | Measure First |
|----------------|---------------------|--------------------------------|-------------------------|---------------|
| **Windows NVIDIA/AMD/Intel** | Process list (`tasklist`/`ps-list`), CPU/RAM via `system-monitoring` [3] | **Yes** — WDDM/NVML/ADL per-process VRAM & engine % (gputaskman pattern) [2] | 1 s process list + 500 ms GPU counters → ~0.3 % CPU | GPU VRAM per PID > 500 MB **or** 3D engine > 30 % |
| **Windows CPU-only** | Same as above | No | 1 s → negligible | Process CPU > 40 % sustained 3 s |
| **macOS Apple Silicon** | `ps`, `sysctl`, `system-monitoring` [3] | **Yes** — `IOReport` / Metal counters for VRAM/residency [2] | 1 s CPU/RAM, 2 s GPU → ~0.5 % | `GPUTime` > 20 % or `VRAM` > 1 GB |
| **Linux NVIDIA/AMD/Intel** | `/proc`, `system-monitoring` [3] | **Optional** — `libdrm`/`NVML`/`ROCm` via gputaskman [2] | 1 s → < 0.2 % | `VRAM_used` > 500 MB or `GPU_busy` > 30 % |
| **Linux CPU-only** | Entirely Node.js | No | 1 s → negligible | CPU% > 40 % |

**Weight verdict**: Ship a **tiny Rust watcher** (~200 KB) that exposes JSON-RPC over stdio: `list_gpu_processes()`, `is_fullscreen(pid)`, `subscribe(events)`. Node spawns it once; all heavy lifting stays native. Polling driven by watcher (event-based where possible) eliminates busy loops.

## 5. Unknowns / Not Covered by Findings
- Vendor overlay APIs (NVIDIA App, AMD Adrenalin, Razer Cortex) — no public SDK docs found.
- Discord’s game-detection IPC protocol.
- Measured false-positive/negative rates for fullscreen heuristic vs. GPU-counter heuristic.
- Exact `llama.cpp` reload latency for 7B/13B/70B GGUF on RTX 3080/4090/M3 Max.
- ComfyUI runtime priority API.
- Cross-platform “heavy app” definition (thresholds for Blender, Premiere, Unity Editor Play mode, etc.).

## Conclusion
A practical, low-overhead detector for KesherAI combines: (1) Node.js `system-monitoring` for CPU/RAM/process enumeration [3], (2) a minimal Rust helper that wraps gputaskman’s per-process GPU logic [2] and fullscreen detection [5], and (3) a user-editable allow-list / rule engine mirroring Process Lasso’s patterns. React in ≤ 2 s, undo in ≤ 1 s after process exit. Profile actions should prioritize *unloading the big model* (largest VRAM win) and *falling back to a tiny CPU model* for chat continuity. The hybrid Node + native architecture keeps main-process CPU < 1 % and works on Windows/macOS/Linux with NVIDIA, AMD, Intel, and Apple GPUs.
