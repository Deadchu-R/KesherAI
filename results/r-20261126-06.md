### Opening, Following, and Converting to Chat

* **Continuing as Chat:** In systems like Cursor and Copilot, users can inspect a running or completed cloud execution and branch off or review the interaction timeline inside the task/PR context without polluting the primary chat switcher.
* **Retention and Cleanup:** Ephemeral background tasks automatically vanish from active tracking lists upon completion or session termination, persisting only when tied to a formal artifact like an issue comment, pull request, or database record [2].

---

## Recommended Design for KesherAI

To eliminate chat list flooding while retaining full visibility into model attempts, KesherAI should decouple **background execution** from **conversational chat threads**.

```
[ Task Card ]
 ├── Description & Status
 └── Runs Section (1 Run per Task)
      ├── Run #1 (Completed) -> [View Logs/Artifacts] [Continue as Chat]
      └── Run #2 (Active/Latest) -> [Live Output Stream]
           ├── Attempt 1 (Failed: Model A)
           └── Attempt 2 (In Progress: Model B)
```

### Core Architecture
1. **Runs Live Inside the Task:** A task in the inbox has a 1-to-Many relationship with *Runs*, but exactly **one active Run container** per execution request. Multiple model attempts (retries, fallbacks) nest *inside* that specific Run, rather than spawning independent top-level chats.
2. **The "Runs" Section:** Add a dedicated **Runs** tab or accordion inside the Task view. This interface displays historical execution attempts, model parameters used, execution duration, and final statuses (Success, Failed, Running).
3. **"Continue as a Chat":** If a user wants to interrogate a run's output, debug a failure, or manually steer the agent, they can click a button labeled **"Continue as a Chat"**. This explicitly converts the run log into a temporary or saved chat thread *on demand*, keeping automated runs out of the default chat list entirely.
4. **Retention and Cleanup:** 
   * Active and recent runs are retained in the task's run history.
   * Ephemeral/failed background attempts clear from active polling views automatically after completion, preserving only high-level status summaries on the task card [2].
   * Old or unpromoted run logs are archived or pruned based on age/storage policies.
5. **Phone View:** On mobile and narrow viewports, the Runs section collapses into a clean accordion or a dedicated bottom sheet. Users see a single status pill (e.g., *Running Model B (Attempt 2)*) on the task card instead of a growing list of chat threads. Tapping it opens the isolated run view.

## Concrete Tasks

1. **Decouple Task Execution from Chat Creation:** Refactor the backend worker to execute task-inbox runs without automatically instantiating a new top-level chat record in the database for every model attempt.
2. **Implement Task-Centric Run Nesting:** Update the database schema and UI to nest model attempts hierarchically under a unified `Run` entity belonging to the parent Task.
3. **Build the Task "Runs" UI Section:** Design and implement a dedicated sub-view inside the Task details card that displays execution history, active attempt status, logs, and artifacts.
4. **Add "Continue as a Chat" Action:** Implement a handler that allows users to promote a specific run history into an interactive chat thread only when explicitly requested.
5. **Optimize Mobile Viewport Handling:** Update the mobile UI layout to replace multi-chat navigation with a collapsible Runs drawer and concise status indicators on task cards.
6. **Implement Run Retention and Cleanup Logic:** Define retention rules and automated cleanup routines to purge raw ephemeral run artifacts and prevent database bloat over time.
