# Research Report: Component-Based Partial Updates for KesherAI

### Summary
KesherAI currently builds and downloads the entire Windows installer (~121 MB) for every release, even when only a single file changes. To eliminate this overhead, this report examines end-to-end patterns used by industry tools (such as VS Code, Discord, Obsidian, and Chrome), proposes a component-level split for KesherAI, details security requirements, and evaluates suitable sidecar languages. A recommended design, expected gains, and concrete next steps are provided.

## 1. End-to-End Industry Patterns

Applications handle partial or modular updates through several established patterns:
* **VS Code & Extensions:** Uses a core native shell combined with extensions packaged as self-contained units that update independently via an extension gallery. VS Code itself also leverages differential updates for its core core assets.
* **Discord & Slack:** Discord splits functionality into independent modules/packages that download dynamically inside the app runtime when needed or updated.
* **Obsidian:** Relies on a stable core application bundle (`app.asar`) combined with separate plugin directories that can be updated on the fly without reinstalling the native desktop binary [12].
* **Chrome:** Uses a **Component Updater** service that downloads small, versioned manifests and patches individual components (e.g., extensions, modules, binary sub-components) in the background without browser restarts where possible.
* **Electron-Specific Mechanisms:** 
  * **electron-updater & Blockmaps:** Generates `.blockmap` files alongside builds. Clients perform HTTP Range requests to download only changed data blocks, reconstructing packages locally [4, 6].
  * **Dual-ASAR Architecture:** Separates the stable Electron native runner (`app.asar`) from the replaceable application code (`${app.name}.asar`), allowing the app bundle to be swapped safely on restart [10].
  * **Asar Hot-Updaters:** Downloads and replaces individual files or script bundles inside an unpacked or virtualized directory structure next to a static Electron shell [24].

## 2. A Component Split for KesherAI

To decouple KesherAI's release lifecycle, the application can be split into distinct layers:

| Component | Versioning | CI Build Strategy (Turborepo/Nx) | Download Mechanism | Verification | Swap Mechanism | Rollback Strategy |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Electron Shell** | SemVer (rarely changes) | Build only on native/dependency changes | Full installer / Squirrel delta | Code signature + SHA-512 | Standard installer restart | OS/Squirrel rollback |
| **Node Server Bundle** (`packages/core`) | SemVer / Hash | Build when `packages/core` changes | Direct archive (`core.asar` or `.zip`) | Ed25519 signature / SHA-256 | Swap file into user data dir on restart | Fallback to previous cached bundle version |
| **Web UI Bundle** | SemVer / Hash | Build when renderer changes | Direct archive (`ui.asar` or `.zip`) | Ed25519 signature / SHA-256 | Swap renderer bundle directory | Fallback to previous cached UI version |
| **Plugins** | Individual SemVer | Independent package builds | Plugin registry download | Cryptographic hash | Dynamic load/unload in plugin directory | Disable failing plugin automatically |
| **Engines** (llama.cpp, ComfyUI) | Engine version | Unchanged (already separate) | External artifact fetch | Checksums | Managed in dedicated storage path | Keep older engine binaries available |
| **Phone App** | Store SemVer | App store pipelines | App stores / OTA (Expo) | Store signing | Native store update | Store rollback / OTA revert |

**How the Phone Remote and Hub Learn New Versions:**
* The Hub polls a lightweight JSON manifest endpoint hosted on GitHub Releases or S3 (similar to `releases.json`) containing the latest versions and hashes for each decoupled component.
* The Phone remote queries the Hub's local API server for component status and compatibility strings, ensuring the remote UI matches the active Hub capabilities.

## 3. Security Considerations

* **Signed Artifacts:** Every decoupled bundle (`core.asar`, `ui.asar`) must include an accompanying cryptographic signature file (.sig) generated via a private CI key (e.g., Ed25519 or RSA). The Electron main process verifies signatures before swapping files.
* **Downgrade Attack Prevention:** Component manifests must include strict minimum version constraints and monotonic version counters. The updater rejects any payload where the target version is less than or equal to the currently active version.
* **Update Server / GitHub Release Structure:** The release bucket/server holds individual component assets alongside a master `manifest.json` containing version numbers, download URLs, blockmaps, and cryptographic signatures for each component.

---

## 4. Language and Weight for Update Management

* **Node.js / TypeScript (Inside Electron Main Process):** Best suited for coordinating component checks, reading local manifests, and utilizing built-in crypto libraries for verification. It avoids adding external runtime dependencies.
* **Rust / Go Sidecar:** Alternatively, a lightweight native sidecar can manage heavy blockmap reconstructions, decompression, and file swaps outside the Node process. However, for a JavaScript/TypeScript-first stack like KesherAI, a pure Node/TS module utilizing `@electron/asar` and native crypto provides sufficient performance with zero added binary weight.

---

## Recommended Design & Expected Gains

* **Recommended Architecture:** Adopt a **Dual-ASAR / Component Bundle Hybrid**. Keep the native Electron shell static. Package the Node core server (`packages/core`) and Web UI into independent, signed `.asar` bundles fetched via a custom manifest updater service.
* **Expected Gains:**
  * **Download Size:** Reduced from ~121 MB to ~2–15 MB per component update (only downloading changed bundles or blockmap diffs).
  * **CI Minutes:** Turborepo/Nx caching ensures only modified packages trigger build and packaging tasks.
  * **Restart Time:** Faster application startup since native re-installations are bypassed; only local file swaps occur on restart.
* **Uncertainties:** Handling native Node modules (`node_modules` with native bindings) inside hot-swapped server bundles remains complex; native modules must either remain in the static shell or be compiled cross-platform and loaded dynamically.
