# KesherAI Local GPU VRAM Watchdog and Zero-Collision Engine Swapping Specification

This technical report specifies a real-time GPU VRAM watchdog and zero-collision engine memory coordinator designed for KesherAI, customized for usability under Windows 11. The system arbitrates VRAM allocations between local language models via `llama.cpp`, image diffusion engines via ComfyUI, and game engines entering Play mode.

## Summary
To prevent GPU out-of-memory (OOM) crashes and power surges during heavy multitasking, this architecture introduces a real-time polling mechanism, an automated Play-mode standby workflow, a rigid priority-based resource allocation hierarchy, and safety thresholds. By combining fast state persistence (`llama_state_save_file`) with rapid VRAM evacuation over a WebSocket bridge, game engines can enter Play mode smoothly within a strict time budget.

## ## VRAM Polling and Monitoring Mechanisms on Windows 11

For Windows 11 environments, monitoring VRAM without altering system drivers or installing binary software packages can be approached through several mechanisms:
* **NVML via Node bindings (`node-nvml`):** Direct bindings to the NVIDIA Management Library provide fast, low-overhead polling of total, free, and used VRAM. This is optimal for a Node-based backend supervisor.
* **`nvidia-smi` Daemon:** Spawning repeated child processes executing `nvidia-smi` introduces noticeable process-creation overhead and latency, making it unsuitable for sub-second real-time watchdog polling.
* **DirectX DXGI Adapter Query:** Querying DXGI adapters via Windows APIs retrieves dedicated and shared video memory statistics. However, it lacks fine-grained per-process allocation tracking compared to NVML.

*Decision for KesherAI:* NVML via Node bindings is designated as the primary polling pipeline due to its accuracy and minimal performance impact.

## ## Play-Mode Standby Protocol & State Swapping

When a game engine (such as Unity) enters Play mode, KesherAI executes a strict zero-collision memory evacuation protocol to free up maximum VRAM for the game viewport:
1. **Event Detection:** Unity or Unreal Engine instances broadcast Play-mode state change events to the KesherAI coordinator via a local WebSocket bridge (leveraging packages like `UnityWebSocket` or `WebsocketPlayer` over `System.Net.WebSockets`) [9, 12, 18].
2. **State Serialization:** The coordinator calls `llama.cpp`'s state-saving functions (`llama_state_save_file` or equivalent high-level python bindings `save_state`) to write the current context and KV cache to disk [2, 6].
3. **VRAM Unloading:** The LLM and active ComfyUI diffusion pipelines are completely unloaded from the GPU, moving data out of VRAM into system RAM.
4. **Timing Budget:** The entire sequence—from Play-mode trigger detection to complete VRAM evacuation—must execute within **500 ms**.
5. **Restoration:** Upon exiting Play mode, the WebSocket bridge signals the coordinator, which restores the `llama.cpp` model state from file back into the GPU context.

## ## Multi-Engine Priority Arbitration Rules

To resolve resource contention, KesherAI enforces a strict priority hierarchy:
1. **Game Engine Viewports (Highest Priority when Active):** When Unity/Unreal is in Play mode, game viewports receive unhindered GPU resource allocation. All other heavy background generation is preempted.
2. **Chat LLM (`llama.cpp`):** Active interactive chat responses take precedence over background diffusion tasks.
3. **Vision Router (2B Lightweight Model):** Maintained as a lightweight fast-path router, kept resident if small enough, or swapped out dynamically.
4. **ComfyUI Diffusion Jobs (Lowest Priority):** Heavy image generation tasks are queued or suspended if a higher-priority task requests resources.

## ## Power Surge, Thermal Protections, and Watchdog Policies

To protect hardware integrity against power spikes and thermal throttling:
* **Concurrent Heavy Job Limit:** Exactly **1 heavy job** (either a heavy ComfyUI diffusion batch or a large LLM context generation task) is permitted to run concurrently. Simultaneous execution of multiple heavy pipelines is strictly blocked.
* **Thermal Threshold Limits:** The watchdog continuously monitors GPU temperature via NVML. If temperatures exceed safe operating limits, active heavy tasks are throttled or suspended.
* **Crash Recovery Logging:** Uncaught exceptions, OOM triggers, or watchdog interventions are systematically written to local crash recovery logs with timestamps and memory snapshots to aid debugging.

## ## Conclusion
The KesherAI VRAM watchdog and zero-collision engine swapping architecture provides a robust framework for managing limited hardware resources on Windows 11. By enforcing a strict 1-heavy-job limit, utilizing NVML polling, and executing a sub-500 ms WebSocket-driven state save-and-unload protocol for game engine Play modes, the system prevents crashes and thermal overloads while maintaining smooth usability.
