## Goal
Research only (no code). Write the findings into docs/RESEARCH_LOG.md under a new dated heading, then end with a list of concrete future tasks.

Now: every KesherAI release builds the whole app, and the PC downloads the full Windows installer (~121 MB, KesherAI-Setup-x.y.z.exe, checked by sha512) and reinstalls, then restarts, even when only one server file or one screen changed. Releases happen several times a day.

Roee's idea: components get updates fairly independently, so only the changed part is built, downloaded and swapped.

1) How others do it end to end: VS Code (and its extensions), Discord (modules), Obsidian (app.asar vs installer), Slack, LM Studio, Jan, Cursor, Chrome (component updater), Steam; electron-updater differential/blockmap downloads, Squirrel deltas, separate hot-swappable JS bundles (server + web UI) next to a rarely-changing Electron shell, code signing and rollback of each part.
2) A split that fits KesherAI: Electron shell; Node server bundle (packages/core etc.); web UI bundle; plugins (editors, already separate); engines (llama.cpp, ComfyUI, already downloaded apart); phone app. For each: how it would be versioned, built (only when changed — Turborepo/Nx caching in CI), downloaded, verified (signature/hash), swapped without a reinstall, and rolled back if it fails to start. How the phone remote and the hub learn the new versions.
3) Security: signed parts, no downgrade attacks, what the update server/GitHub release holds.
4) Language and weight: which tool/language fits each step (e.g. a small Rust/Go updater sidecar vs the Node server doing it).

End with a recommended design, the expected gain (download size, CI minutes, restart time) and the first steps. Cite sources; mark anything uncertain.

## Acceptance
