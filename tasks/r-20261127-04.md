## Goal
Research only (no code). KEEP IT UNDER 1,200 WORDS.
KesherAI (Electron + Node, llama.cpp built in) wants a pool of small dedicated models running on the CPU only (`-ngl 0`), each for one job: a router (~2B), a watchdog for agent runs, a translator (TranslateGemma ~4B), embeddings (~0.6B), a task-organizer chat for the hub. Goal: they work side by side without making the PC slow (the user games and works on it; e.g. Ryzen 9 9950X3D 16 cores, 96 GB DDR5 dual channel; also weak laptops).
Find end to end:
1. How existing tools share a CPU among several local models: llama.cpp server router mode / multiple models in one server, Ollama's OLLAMA_MAX_LOADED_MODELS / NUM_PARALLEL / keep_alive, LM Studio's JIT loading and auto-evict, LocalAI, llama-swap. Load on demand, idle unload, max loaded at once.
2. The real limits: memory bandwidth for token generation (how many models can generate at the same time before each slows down a lot), threads per model vs. physical cores, prompt processing vs. generation, the cost of mmap'ed model files shared in the page cache, NUMA/CCD pinning on Ryzen X3D (the V-Cache CCD), priority classes (below-normal) so games and the UI stay smooth.
3. Whether one small model can serve several roles (router + organizer + watchdog) with different prompts, vs. separate models; which small models are good enough per role in Hebrew and English (Qwen3.5 2B/4B, Gemma small, Phi mini, SmolLM3), with CPU tokens/s numbers.
4. A scheduler design: a RAM budget, a thread budget, at most N generating at once with a queue, priorities per role (interactive chat first, background last), pause/shrink while a game or heavy app runs.
Include a "Language and weight" part for every platform (Windows/macOS/Linux, x86 AVX2/AVX-512, Apple Silicon, ARM, CPU-only laptops) and what to measure first. End with a "## Tasks" section of 5-8 concrete tasks (S/M/L).

## Acceptance
Tool comparison, the limits with numbers, one-vs-many models per role, scheduler design, Language and weight, Tasks.
