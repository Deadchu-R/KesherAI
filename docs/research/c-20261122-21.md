# Local GUI Screen Automation via UI-TARS and llama.cpp Multimodal Projections

## Summary

This report evaluates running local graphical user interface (GUI) screen automation and computer control within KesherAI using `UI-TARS-1.5-7B-GGUF` and `Qwen2.5-VL-7B-Instruct-GGUF` paired with multimodal projectors (`mmproj-model-f16.gguf`) under `llama-server`. By offloading visual perception to a local 24 GB NVIDIA GeForce RTX 3090, desktop control achieves complete data sovereignty, sub-1.5-second step latencies, and zero external cloud API expenses. The architecture decouples high-level task planning from coordinate visual grounding via a two-model pattern. A robust coordinate pipeline maps model predictions across mixed-DPI multi-monitor Windows virtual desktops, governed by an operating system safety layer enforcing rate limits, Bézier cursor smoothing, low-level emergency kill switches, and strict application boundary sandboxing.

## 1. Technical Requirements & Runtime Setup on RTX 3090 (24 GB)

### 1.1 `llama-server` Multimodal Architecture
`llama.cpp` supports multimodal vision-language models by separating the transformer language model weights from the vision encoder/projector weights (`mmproj`) [8]. The vision projector encodes screenshot bitmaps into vision embedding tokens that are injected into the transformer's attention context.

For local GUI automation on Windows, `llama-server` is spawned as a dedicated background service running on an independent HTTP port (e.g. `127.0.0.1:8081`), distinct from the primary conversation LLM [8].

#### Recommended CLI Invocation:
```bash
llama-server.exe \
  --model ./models/gui-vision/UI-TARS-1.5-7B-q4_k_m.gguf \
  --mmproj ./models/gui-vision/mmproj-model-f16.gguf \
  --port 8081 \
  --host 127.0.0.1 \
  --n-gpu-layers 99 \
  --ctx-size 8192 \
  --flash-attn on \
  --batch-size 2048 \
  --ubatch-size 512 \
  --threads 8 \
  --parallel 1 \
  --cont-batching
```

### 1.2 Parameter Justifications
- `--model` & `--mmproj`: Pairs the 4-bit quantized backbone (`Q4_K_M`) with the 16-bit float vision projector (`F16`). Keeping the projector at F16 preserves fine visual feature fidelity essential for locating small UI elements (icons, checkboxes, radio buttons) [3, 8].
- `--n-gpu-layers 99` (`-ngl 99`): Fully offloads all 28 or 32 transformer layers plus multimodal projections to GPU VRAM [8].
- `--ctx-size 8192` (`-c 8192`): High-resolution screenshots generate between 1,024 and 2,560 visual tokens depending on image resolution and dynamic patch division. An 8,192 token context comfortably accommodates the system prompt, screenshot visual tokens, historical action context, and grounding coordinates [4, 8].
- `--flash-attn on` (`-fa on`): Enables FlashAttention kernels in CUDA, reducing Key-Value (KV) cache memory overhead by ~50% and speeding up prefill/time-to-first-token (TTFT) by 1.8x to 2.4x [8].
- `--parallel 1`: Desktop screen automation is strictly sequential; a single execution slot prevents GPU memory thrashing and contention [8].

### 1.3 VRAM Footprint Breakdown on 24 GB RTX 3090
Operating on a 24 GB VRAM budget allows full GPU offloading while leaving ample headroom for running either the desktop environment or a second local language model concurrently:

| Component | UI-TARS-1.5-7B (Q4_K_M) | Qwen2.5-VL-7B (Q4_K_M) | Notes |
| :--- | :--- | :--- | :--- |
| **Model Weights** | ~4.78 GB | ~5.03 GB | 4-bit medium quantization [3, 4] |
| **Vision Projector (`mmproj`)** | ~0.85 GB | ~1.16 GB | F16 precision weights [3, 4] |
| **KV Cache (8k Context, FA on)** | ~1.50 GB | ~1.50 GB | FP16 KV cache with FlashAttention enabled [8] |
| **Compute Activations & Scratch** | ~1.20 GB | ~1.35 GB | Vision encoder patch processing buffer [8] |
| **Total Dedicated VRAM** | **~8.33 GB** | **~9.04 GB** | Measured under full GPU offload [3, 8] |
| **Remaining Headroom on 3090** | **~15.67 GB** | **~14.96 GB** | Available for primary LLM, OS, or CAD/game engines |

### 1.4 Lifecycle & Standby Strategy
In KesherAI, the vision slot automatically unloads after 10 minutes of inactivity (`IDLE_MS = 600_000`) via `VisionService`. When real-time game engines (such as Unreal Engine or Unity) enter Play mode, the engine signals KesherAI's `gpu-guard` to trigger temporary VRAM standby, releasing the ~8.5 GB allocated to `llama-server` and avoiding GPU out-of-memory faults during intense rendering.

## 2. Coordinate Transformation Pipeline: Model Space to Multi-Monitor High-DPI Windows Virtual Screen

A critical failure mode of GUI automation agents is misaligned clicks arising from display scaling (DPI), downsampled screenshot buffers, and multi-monitor desktop offsets. A rigorous mathematical transformation pipeline must normalize and translate coordinates.

```
+-------------------------------------------------------------------------------+
|  1. Model Output Space                                                        |
|     - rel1000: [0..1000, 0..1000]                                             |
|     - abs28: [0..w_patch, 0..h_patch] (divisible by 28 via smart_resize)      |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
|  2. Sent Screenshot Buffer Space (w_shot x h_shot, e.g. 1280 max width)        |
|     - x_shot = (x_model / 1000) * w_shot           (rel1000)                  |
|     - x_shot = (x_model * w_shot) / w_patch        (abs28)                    |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
|  3. Screenshot Downscaling Inversion                                          |
|     - scale = min(1.0, max_width / virtual_screen_width)                      |
|     - x_unscaled = x_shot / scale                                             |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
|  4. Windows Virtual Desktop Offset Addition                                   |
|     - x_virtual = x_unscaled + VirtualScreen.Left                             |
|     - y_virtual = y_unscaled + VirtualScreen.Top                              |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼
+-------------------------------------------------------------------------------+
|  5. OS Win32 API Cursor Dispatch                                              |
|     - Physical Desktop Pixels via SetCursorPos(x_virtual, y_virtual)          |
|       (requires Per-Monitor DPI Aware v2)                                    |
+-------------------------------------------------------------------------------+
```

### 2.1 Model Coordinate Representations
1. **Relative Permille (`rel1000`)**: Used by standard Qwen-VL and general vision models. Coordinates are normalized integers in $[0, 1000]$ relative to the screenshot's width and height [4]:
   $$\text{box} = [x_1, y_1, x_2, y_2] \quad \text{where } x, y \in [0, 1000]$$
2. **Absolute Patch-Aligned (`abs28`)**: Used by UI-TARS and Qwen2.5-VL native patch grids. The vision encoder resizes images so that both dimensions are multiples of 28 (patch factor $f=28$) bounded between $56 \times 56$ and $16384 \times 28 \times 28$ pixels (`smart_resize`) [1, 4]. The model outputs integer coordinates corresponding to this resized grid:
   $$w_{\text{patch}} = \max\left(28, \text{round}\left(\frac{w_{\text{shot}}}{28}\right) \times 28\right)$$
   $$x_{\text{shot}} = \frac{x_{\text{model}} \cdot w_{\text{shot}}}{w_{\text{patch}}}, \quad y_{\text{shot}} = \frac{y_{\text{model}} \cdot h_{\text{shot}}}{h_{\text{patch}}}$$

### 2.2 Windows Virtual Screen Geometry & Multi-Monitor Layouts
Under Windows, the virtual screen is the bounding rectangle encompassing all display monitors (`[System.Windows.Forms.SystemInformation]::VirtualScreen`):
- `VirtualScreen.Left`: The x-coordinate of the upper-left corner of the virtual screen. If a secondary monitor is positioned to the left of the primary monitor, this value is **negative** (e.g. $-1920$).
- `VirtualScreen.Top`: The y-coordinate of the upper-left corner. If a secondary monitor is placed above the primary monitor, this value is **negative** (e.g. $-1080$).
- `VirtualScreen.Width` & `Height`: Total spanning dimensions of the desktop canvas.

### 2.3 High-DPI Awareness Constraints
If the automation process is DPI-unaware, Windows applies bitmap virtualization (DPI scaling, e.g. 150% or 200%), causing `CopyFromScreen` to capture blurry scaled images and `SetCursorPos` to offset clicks.
- **Requirement**: The automation host must explicitly declare Per-Monitor DPI Awareness v2 before making any screen capture or cursor calls:
  ```c
  SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2);
  ```
- With Per-Monitor DPI v2 enabled, Win32 `SetCursorPos(x, y)` operates directly in true physical virtual screen coordinates across all monitors.

### 2.4 End-to-End Coordinate Mapping Equations
Given:
- Model output: $(x_{\text{model}}, y_{\text{model}})$
- Captured screenshot size: $w_{\text{shot}} \times h_{\text{shot}}$
- Capture downsampling factor: $S = \min\left(1.0, \frac{\text{maxWidth}}{W_{\text{virtual}}}\right)$
- Virtual screen origin: $(X_{\text{origin}}, Y_{\text{origin}}) = (\text{VirtualScreen.Left}, \text{VirtualScreen.Top})$

The physical desktop coordinate $(X_{\text{target}}, Y_{\text{target}})$ is:

1. **Convert to screenshot buffer pixels**:
   $$x_{\text{shot}} = \begin{cases} 
   \frac{x_{\text{model}}}{1000} \cdot w_{\text{shot}} & \text{if } \text{coords} = \text{rel1000} \\ 
   \frac{x_{\text{model}} \cdot w_{\text{shot}}}{w_{\text{patch}}} & \text{if } \text{coords} = \text{abs28} 
   \end{cases}$$
   $$y_{\text{shot}} = \begin{cases} 
   \frac{y_{\text{model}}}{1000} \cdot h_{\text{shot}} & \text{if } \text{coords} = \text{rel1000} \\ 
   \frac{y_{\text{model}} \cdot h_{\text{shot}}}{h_{\text{patch}}} & \text{if } \text{coords} = \text{abs28} 
   \end{cases}$$

2. **Invert capture downscaling and translate to virtual screen space**:
   $$X_{\text{target}} = \text{round}\left(\frac{x_{\text{shot}}}{S}\right) + X_{\text{origin}}$$
   $$Y_{\text{target}} = \text{round}\left(\frac{y_{\text{shot}}}{S}\right) + Y_{\text{origin}}$$

3. **Bounding Box Validation**:
   Clamp $(X_{\text{target}}, Y_{\text{target}})$ to enforce:
   $$X_{\text{origin}} \le X_{\text{target}} \le X_{\text{origin}} + W_{\text{virtual}} - 1$$
   $$Y_{\text{origin}} \le Y_{\text{target}} \le Y_{\text{origin}} + H_{\text{virtual}} - 1$$

## 3. OS Action Execution Safety Layer

Local agent execution requires guardrails at the operating system interaction level to prevent erratic agent loops, accidental credential submission, or system destruction.

```
       [ Incoming Model Action Request (click / type / key) ]
                                 │
                                 ▼
+-----------------------------------------------------------------+
| Gate 1: Emergency Stop Check                                    |
|   - Was Stop / PauseBreak pressed within last 10,000 ms?        |
|   - If yes -> Kill worker, reject immediately                   |
+-----------------------------------------------------------------+
                                 │ Passed
                                 ▼
+-----------------------------------------------------------------+
| Gate 2: Application Boundary Verification                       |
|   - Read foreground HWND via GetForegroundWindow                |
|   - Disallowed: isOwnApp, isSecureWindow, isSystemSettings      |
|   - Check conversation allowed list (computer_use_app)          |
|   - Enforce AppKind rules (browsers view-only; terminals click) |
+-----------------------------------------------------------------+
                                 │ Passed
                                 ▼
+-----------------------------------------------------------------+
| Gate 3: Window Title & Content Safety Filter                    |
|   - Regex check: passwords, 2FA, OTP, checkout, bank (en/he)    |
|   - If typing requested on sensitive window -> Block & reject   |
+-----------------------------------------------------------------+
                                 │ Passed
                                 ▼
+-----------------------------------------------------------------+
| Gate 4: Execution Pacing & Rate Limiting                        |
|   - 350 ms inter-action delay                                   |
|   - Bézier curve cursor smoothing (4-6 waypoints over 80 ms)    |
|   - Dispatch Win32 action (SetCursorPos / mouse_event)          |
+-----------------------------------------------------------------+
```

### 3.1 Rate Limiting & Debouncing
- **Action Throttling**: A hard minimum delay of 350 ms is enforced after each physical action (`click`, `type`, `key`, `scroll`). This ensures native UI animations, menus, and message loops process completely before the next screenshot or interaction is initiated.
- **Turn Step Budget**: An automated turn is capped at 15 consecutive tool executions. If a task is uncompleted after 15 actions, the agent pauses and requests confirmation to prevent infinite error loops.

### 3.2 Mouse Movement Smoothing
Instantaneous cursor repositioning (`SetCursorPos`) frequently breaks modern user interfaces:
- Hover menus and dynamic flyouts fail to register pointer entry events.
- Drag-and-drop operations drop payloads prematurely due to dropped pointer messages.
- Abrupt teleportation disorients users watching the session live.

**Implementation via Cubic Bézier Interpolation**:
When moving between $(X_0, Y_0)$ and $(X_1, Y_1)$:
1. Generate two randomized control points $(C_1, C_2)$ offset slightly along the normal vector of the trajectory to mimic biological human arm movement.
2. Discretize movement across $N=6$ to $N=10$ interpolation points spaced at 10 ms to 15 ms intervals (total trajectory time: ~80 ms to 120 ms).
3. Compute points using the cubic Bézier formulation:
   $$B(t) = (1-t)^3 P_0 + 3(1-t)^2 t C_1 + 3(1-t) t^2 C_2 + t^3 P_1, \quad t \in [0, 1]$$
4. Execute `SetCursorPos` iteratively at each step before issuing `mouse_event` down/up signals.

### 3.3 Emergency Stop Hotkeys (`Ctrl+Esc` / `PauseBreak` / `Ctrl+Alt+Esc`)
To guarantee immediate human intervention:
- **Low-Level Hook**: Register a global low-level keyboard hook (`WH_KEYBOARD_LL`) in the desktop application targeting `PauseBreak` and `Ctrl+Alt+Esc`.
- **Immediate State Invalidation**:
  1. Sets an internal timestamp `stoppedAt = Date.now()`.
  2. Cancels active HTTP requests to `llama-server` via `AbortController`.
  3. Kills any spawned background worker processes (`uia.kill()`, PowerShell workers).
  4. Calls `releaseHeld()` to release any held mouse buttons (`MOUSEEVENTF_LEFTUP`, `MOUSEEVENTF_RIGHTUP`) or modifier keys (Ctrl, Shift, Alt) to prevent stuck input state.
  5. Imposes a mandatory 10-second rejection lockout (`gate()` throws error), blocking any agent tools until explicitly cleared by the user.

### 3.4 Sandboxed Application Boundaries & Permissions
- **Explicit Application Whitelist**: An agent cannot interact with any application without first invoking `computer_use_app` and receiving user approval for that conversation. The active foreground process name is verified via `GetForegroundWindow` and `GetWindowThreadProcessId` prior to every single click or keystroke.
- **Prohibited Application Boundaries**:
  - `isOwnApp`: The automation agent is strictly forbidden from targeting KesherAI's own application window. This prevents prompt-injection attacks where an untrusted webpage or document tricks the model into clicking its own permission approval buttons.
  - `isSecureWindow`: Windows security contexts—including User Account Control (`consent.exe`), Windows Security Defender dialogs, Credential Manager, and LogonUI—are hard-blocked.
  - `isSystemSettings`: System configuration consoles (`SystemSettings.exe`, `regedit.exe`, `gpedit.msc`, `mmc.exe`) reject all automation.
- **Enforced Application Roles (`AppKind`)**:
  - `view-only` (Web Browsers): Browsers may only be observed via screenshots; clicks and keystrokes are blocked. Web interactions must route through sandboxed browser tools with audited origin barriers.
  - `click-only` (Terminals / Command Prompts): Shells (`powershell.exe`, `cmd.exe`, `wt.exe`) and file managers allow mouse navigation but reject keystroke typing tools; shell commands must pass through `run_command` with individual approval cards.
- **Sensitive Window Title Filter**: Window titles matching authentication or financial patterns (`/(password|sign-in|2fa|bank|payment|checkout|כרטיס אשראי|סיסמ)/i`) refuse all typing tools unconditionally.

### 4.1 Latency Analysis
The local execution pipeline exhibits a massive roundtrip latency advantage. While Claude 3.5 Sonnet requires uploading high-resolution screenshot buffers over WAN, queueing in multi-tenant API infrastructure, and waiting for heavy reasoning prefill (totaling 4 to 7.5 seconds per action) [5], `llama-server` on an RTX 3090 encodes the image projector in ~400 ms and streams the coordinate tokens in ~400 ms. This allows local interactions to feel interactive and snappy (~1 second per action) [3, 8].

### 4.2 Visual Grounding & Benchmark Variances
Sources exhibit minor benchmark score variances based on evaluation setups:
1. **ScreenSpot vs ScreenSpot-Pro**: Standard ScreenSpot tests simple mobile and web layouts where both UI-TARS-1.5-7B (94.2%) and Qwen2.5-VL-7B (84.7%) perform exceptionally [1, 4]. On ScreenSpot-Pro (which evaluates high-resolution CAD, IDE, and desktop environments), UI-TARS-1.5-7B achieves 49.6%, outpacing general vision models due to ByteDance's domain-specific GUI grounding pretraining [1, 2].
2. **OSWorld Discrepancy**: On OSWorld multi-step OS workflows, the open-weights UI-TARS-1.5-7B reaches 27.5% [1, 2], outperforming Claude 3.5 Sonnet's 15-step score of 14.9% and 50-step score of 22.0% [5, 6]. Note that ByteDance's proprietary unreleased full model achieves 42.5% [1, 2], but is not available for local deployment.

## 5. Discrepancies and Technical Trade-offs

1. **End-to-End Planning vs Dedicated Visual Grounding**:
   - *Direct Action Generation*: Models like UI-TARS can theoretically plan steps and emit mouse actions directly (`click(x, y)`). However, 7B models frequently struggle with complex, long-horizon planning and self-correction across multi-window operating system workflows [1, 4].
   - *Two-Model Architecture (Recommended)*: KesherAI decouples the pipeline: the primary text reasoning LLM plans the logical steps in natural language (e.g. "Locate and click the Save button"), while the local vision model (`UI-TARS-1.5-7B`) is invoked as a dedicated tool (`computer_find`) purely for pixel coordinate grounding. This avoids 7B reasoning drift while preserving state-of-the-art spatial precision.
2. **GGUF Projector Format Compatibility**:
   - Some community Hugging Face repositories package multimodal projectors with extension `.mmproj` rather than `.gguf`, or name them inconsistently [3, 8]. KesherAI's `savedName()` normalizes all projector files to `mmproj-<stem>.gguf` to ensure `llama-server` auto-discovery functions reliably on Windows systems.

---

## 6. Conclusion

Executing local desktop GUI screen automation using `UI-TARS-1.5-7B` or `Qwen2.5-VL-7B` with `mmproj-model-f16.gguf` under `llama-server` is entirely viable and production-ready on an RTX 3090. Requiring only ~8.3 GB of VRAM with FlashAttention enabled, the setup delivers ~1.0-second step latencies—drastically faster than cloud-based solutions like Anthropic Computer Use—with zero token costs and complete data privacy.

The implementation succeeds by pairing a two-model architecture (planning model + grounding model) with a multi-stage coordinate conversion pipeline that corrects for multi-monitor desktop offsets and high-DPI scaling. Operating under an OS safety layer with Bézier smoothing, rate limiting, and emergency hotkey stops, local computer control provides a safe, highly responsive automation experience for desktop workflows.
