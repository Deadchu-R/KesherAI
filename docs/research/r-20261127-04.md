# Efficient Multi‑Model CPU Serving with llama.cpp Router Mode and a Lightweight Scheduler  

## Summary  
Llama‑server’s router mode lets a single process host several GGUF models, each in its own child process, with dynamic load/unload and configurable thread counts. On a Ryzen 9 9950X3D the practical ceiling is a couple of models per core before memory bandwidth dominates. One small model can double as router, watchdog, translator, embeddings, and hub chat, but separate instances give finer control. A simple scheduler (queue + priorities) caps concurrent generations and protects the system during gaming.  

## 1. Existing tools for sharing a CPU among local models  

- **llama.cpp server router mode** – Run `./llama-server --models-preset models.ini --port 8080`. The server starts with no model loaded, loads the requested model on first request, and optionally unloads it after the response. Up to `--models-max` models are kept alive; LRU eviction drops the least‑recently used when the cap is reached. Each model runs in its own process, so crashes do not affect others. [1]  
- **Ollama** – Controls number of loaded models via `OLLAMA_MAX_LOADED_MODELS`, `NUM_PARALLEL`, and `keep_alive`. Improperly set `keep_alive` leaves models resident longer than needed, wasting RAM and CPU. [4]  
- **LM Studio JIT loading & auto‑evict** – Automatically evicts models when memory fills, reducing overhead. [2]  
- **LocalAI / llama‑swap** – Allow multiple models on one endpoint, often via swap scripts; provide on‑demand switching. [3]  
All approaches support *load‑on‑first‑request* and *idle unload*; the maximum simultaneous models is configurable (default varies).  

## 2. Real limits on CPU‑only generation  

- **Memory bandwidth for token generation:** Each model consumes bandwidth proportional to context length and batch size. Beyond roughly 2–3 models per core, per‑model latency spikes due to cache thrashing and page‑cache contention. [2]  
- **Threads per model vs. physical cores:** The `threads` parameter allocates CPU threads for non‑offloaded layers. With `ngl=0` (pure CPU) you can assign up to all cores (e.g., 16 on Ryzen 9 9950X3D), but giving each model its own thread pool leads to context‑switch overhead. [1]  
- **Prompt processing vs. generation:** Early turns spend most time parsing and embedding; large batches increase prompt preprocessing load. 96 GB DDR5 helps, but mmap‑ed GGUF files compete for RAM bandwidth. [2]  
- **NUMA/CCD pinning:** Ryzen X3D’s V‑Cache CCD splits L3 across cores; placing models on nearby cores improves cache hits. Explicit pinning (`--cpu-threads-per-core`) assists but needs profiling. [2]  
- **Priority classes:** “Below‑normal” priority lowers scheduling preference for background jobs, helping keep games and UI responsive. Not yet exposed in router config; may require OS‑level throttling.  

## 3. One model doing multiple roles?  

A single small model can host several services because the server picks the right model per request. However, each role needs distinct prompts and outputs. Candidate small models:  

- **Qwen3.5‑2B / 4B** – good for general chat and translation in English.  
- **Gemma‑small** – solid for Hebrew and watchdog logic.  
- **Phi‑mini** – compact English model, useful for embeddings.  
- **SmolLM3‑0.5B** – tiny, fast for low‑resource devices.  

Published token‑per‑second figures are absent; rough estimates for a 2 B model on a Ryzen 9 CPU are ~150–300 tok/s (early turns) and rise with larger context windows. Separate models give safer isolation and allow tuned behavior per role. For example: router → Qwen3.5‑2B (English), watchdog → Gemma‑small (Hebrew), translator → TranslateGemma‑4B, embeddings → 0.6 B model, hub chat → Gemma‑large or Qwen3.5‑4B. [3]  

## 4. Scheduler design  

- **RAM budget:** A 2 B GGUF ≈ 500–800 MB; 4 B ≈ 1.5 GB. Four models together ≈ 6–7 GB. Adding OS page cache and buffers stays well under 10 GB on a 96 GB system. Monitor with `psrscpu` or `htop`.  
- **Thread budget:** Use `--models-preset` with `threads` per model. For CPU‑only, split the 16 cores (≈8 threads per model) or let the router decide. Keep total active threads ≤ 32 to avoid oversubscription.  
- **Queue & concurrency:** Implement a simple round‑robin or weighted queue. When the queue is empty, select the next ready model. If `--models-max` is hit, drop the least recently used (LRU) – matching router’s default eviction. [1]  
- **Priorities:** Highest priority for interactive chat (hub) and routing; lowest for background tasks (embeddings, watchdog). Apply `nice`/`renice` or OpenRAID to boost foreground processes.  
- **Pause/Shrink:** Detect high CPU load (e.g., game frame time > 30 ms) and temporarily reduce `threads` for non‑critical models or lower their priority. Disabling `keep_alive` frees memory faster; see Ollama’s issue. [4]

## Conclusion  

Llama‑server’s router mode offers a production‑ready way to run several small models on a single CPU process, each in its own child, with dynamic load/unload and tunable thread counts. On a Ryzen 9 9950X3D the practical ceiling is a couple of models per core before memory bandwidth becomes the bottleneck, especially with long contexts. One model can serve multiple roles, but separate instances give finer control and better isolation. A lightweight scheduler—configuring `--models-max`, limiting total threads, and assigning niceness levels—keeps the system responsive during gaming. Detailed tuning for language and hardware begins with measuring per‑model token rates and memory footprints.
