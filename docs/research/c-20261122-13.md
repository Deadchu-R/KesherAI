# Deep Research: Free Cloud AI Model APIs and Hardware-Aware Distributed Inference for KesherAI

## Summary

This research delivers a comprehensive, dual-track investigation tailored for **KesherAI**—an open-source, local-first AI desktop application (Electron, React web interface, Node server, local llama.cpp / stable-diffusion.cpp / ComfyUI) used for creative workflows, game development, and everyday chat from home PCs and mobile phones (390 px viewport). 

**Part A (Free Cloud AI Model APIs):** Evaluates 20+ cloud AI providers under a strict safety criterion matching Google AI Studio's billing-free key: zero credit card required, zero risk of surprise overdraft or automated recurring billing, verifiable free rate limits, data privacy/training implications, Hebrew language proficiency, OpenAI API compatibility, and terms regarding automated agentic workloads. Major findings highlight that while providers like **Groq**, **Cloudflare Workers AI**, and **OpenRouter (`:free`)** provide genuinely safe, card-free, non-expiring allocations with OpenAI-compatible endpoints, others like **Cerebras Cloud**, **SambaNova Cloud**, **Together AI**, and **Alibaba Cloud** have either eliminated permanent free tiers, mandated credit cards upfront, or instituted auto-converting pay-as-you-go billing. Crucially, **GitHub Models** was fully retired on July 30, 2026. Specialized non-LLM providers (**ElevenLabs** for TTS, **Deepgram** and **AssemblyAI** for STT, and **Voyage AI** / **Jina AI** for embeddings) offer generous, safe free allotments with strong Hebrew support.

**Part B (Distributed Local AI and Multi-Device Workload Splitting):** Analyzes state-of-the-art distributed architectures (**exo**, **llama.cpp RPC**, **Petals**, **distributed ComfyUI**, **Ollama clusters**, and **LocalAI federation**) across a heterogeneous home environment consisting of a high-end desktop workstation (24 GB VRAM GPU), a lightweight mobile laptop, and a smartphone. The technical benchmark demonstrates that fine-grained intra-token tensor or pipeline parallelism across standard home Wi-Fi or 1 Gbps Ethernet suffers catastrophic latency penalties (a 30%–50%+ drop in generation speed) and serious unauthenticated socket vulnerabilities (`ggml-rpc-server`). Consequently, KesherAI should not attempt ad-hoc layer sharding across the network. Instead, KesherAI should implement **hardware-aware task and model routing**: treating the primary PC as the heavy compute engine (running 70B LLMs, Flux/SD checkpoints, and complex ComfyUI workflows), utilizing the laptop for lightweight assistance (3B–8B models, local embeddings) or as a pure client, and coordinating sessions via an asynchronous, capability-aware orchestrator with circuit-breaker fault tolerance.

## Part B: Splitting Work Across Connected Computers by Hardware

### 1. Landscape of Distributed Local AI Architectures

When coordinating multiple local devices—a primary home PC with a 24 GB GPU (e.g., RTX 3090 / 4090), a laptop (CPU or low-tier GPU), and a mobile phone—distributed inference frameworks operate across distinct architectural paradigms:

```
+----------------------------------------------------------------------------------------------------+
|                                 DISTRIBUTED INFERENCE TAXONOMY                                     |
+-------------------------------------------------+--------------------------------------------------+
|          PARALLEL TENSOR/LAYER SPLITTING        |           HARDWARE-AWARE TASK ROUTING            |
|       (exo, llama.cpp RPC, Petals)              | (ComfyUI-Distributed, Ollama Clusters, LocalAI)  |
+-------------------------------------------------+--------------------------------------------------+
| Slices a single model across multiple machines. | Dispatches whole inference tasks to the node     |
| Continuous inter-layer network communication    | best equipped to execute them. Zero inter-layer  |
| required for every single token generated.      | network overhead; full execution speed.          |
+-------------------------------------------------+--------------------------------------------------+
```

#### 1.1 `exo` (`exo-explore/exo`)
*   **Architecture:** P2P cluster orchestration targeting consumer hardware (MacBooks via Apple Silicon MLX, PCs via CUDA).
*   **Parallelism Strategy:** Supports both **Pipeline Parallelism** (slicing model layer-by-layer across a ring topology) and **Tensor Parallelism** (splitting individual matrix multiplications across nodes). 
*   **Discovery & Networking:** Employs dynamic peer discovery (zero-configuration local gossip protocol) and topology-aware auto-partitioning based on live VRAM/RAM polling. Supports RDMA over Thunderbolt 5/networking for low-latency interconnects.
*   **Failure Handling:** If a node drops out of the pipeline ring, inference fails mid-token. Recovery requires recalculating the topology, redistributing the sharded layer weights across surviving nodes, and rebuilding the prompt KV-cache from scratch.
*   **OpenAI Compatibility:** Exposes unified OpenAI and Ollama-compatible HTTP endpoints.

#### 1.2 `llama.cpp RPC` (`llama-rpc-server` / `ggml-rpc`)
*   **Architecture:** Client-server backend within `llama.cpp`. A master `llama-server` delegates specific tensor operations across network sockets to one or more `ggml-rpc-server` instances.
*   **Operational Mechanism:** Serves exclusively as a **memory-pooling tool**, allowing a master node to offload transformer layers that do not fit into its own VRAM onto a secondary machine's VRAM or system RAM.
*   **The Latency Bottleneck:** Autoregressive token decoding is strictly sequential. For *each generated token*, intermediate activations must complete round trips across the local network. 
    *   On standard Gigabit Ethernet (1 GbE) or Wi-Fi, network latency ($\sim$0.2–1.5 ms per packet) causes a catastrophic **30% to 50%+ reduction in generation throughput (tokens/sec)** compared to running the same model on local hardware.
    *   While upgrading to 10 GbE or RDMA (RoCEv2) accelerates initial model weight distribution, token decode pacing remains latency-bound.
*   **Security Vulnerability:** `ggml-rpc-server` accepts and executes raw computational graphs and remote memory pointers **without authentication or encryption**. Exposing an RPC server outside an isolated, trusted network interface allows arbitrary remote memory manipulation.

#### 1.3 `Petals` (`bigscience-workshop/petals`)
*   **Architecture:** BitTorrent-style decentralized P2P swarm built on the Kademlia Distributed Hash Table (DHT) via the `Hivemind` framework.
*   **Fault Tolerance:** Slices large models (up to 405B parameters) into multi-layer blocks. Nodes announce held blocks on the DHT. If an intermediate node crashes or stalls mid-generation ("the straggler problem"), the client dynamically reroutes activation tensors to an alternative volunteer node holding the identical block.
*   **Security & Byzantine Failure:** Designed for cooperative volunteer networks, Petals lacks Byzantine Fault Tolerance (BFT). Malicious nodes can inspect passing hidden activation states (prompt privacy risk) or inject numerical noise (NaNs) to corrupt output tokens. Public swarms have largely stagnated in 2025/2026, with practical deployments limited to private, authenticated swarms behind corporate firewalls.

#### 1.4 Distributed ComfyUI (`ComfyUI-Distributed`)
*   **Architecture:** Master-worker execution model across LAN nodes, secondary local GPUs, and cloud runtimes.
*   **Splitting Model vs. Routing Whole Jobs:** `ComfyUI-Distributed` **does not pool VRAM**. It cannot split a 16 GB diffusion checkpoint across two 8 GB cards. Instead, it dispatches independent workflow jobs across available workers (batch generation acceleration, tile-based upscaling across nodes, or parallel variant rendering).
*   **Data Flow:** Master pushes the node graph JSON and input images to workers; workers execute natively and stream completed image/video tensors back to the master.

#### 1.5 Ollama Clusters & Inference Load Balancers
*   **Architecture:** Ollama does not feature native distributed mesh clustering. Multi-node Ollama setups rely on model-aware reverse proxies (e.g., Travis AI Load Balancer, LiteLLM Proxy, Olla, or OpenZiti LLM Gateway).
*   **VRAM-Aware Routing:** Traditional round-robin routing fails for LLMs because swapping models in VRAM introduces heavy cold-start delays (10–30 seconds to reload weights from NVMe). Intelligent routers maintain live registries of which models are warm in each node's VRAM and route traffic with a **warm-first** policy.
*   **Hardware Tiering:** Small requests (`llama3.2:3b`) route to lower-spec nodes, while large reasoning or coding requests route strictly to high-VRAM server nodes.

#### 1.6 LocalAI Federation
*   **Federated Mode:** Independent LocalAI instances discover each other via `libp2p` (IPFS stack), forming a federation that exposes a single virtual endpoint. Workloads balance across nodes via least-connections algorithms with automatic failover.
*   **Worker Mode:** Uses `llama-cpp-rpc` or `mlx-distributed` to shard layers across nodes joined via secure, single-use cryptographic invite links (`local-ai worker --join <link>`), mitigating unauthenticated socket risks.

### 2. Comparative Analysis: Splitting a Model vs. Routing Whole Jobs

| Feature | Fine-Grained Model Splitting (`exo`, `llama.cpp RPC`) | Hardware-Aware Job Routing (Task Dispatch) |
| :--- | :--- | :--- |
| **Primary Purpose** | Run a single giant model (e.g., 70B+) that exceeds any single machine's VRAM. | Maximize throughput and efficiency across heterogeneous devices. |
| **Network Overhead** | **Severe.** Megabytes of activation tensors transferred per token over LAN/Wi-Fi. | **Minimal.** Only the initial prompt and final completion cross the network. |
| **Generation Speed** | Slowed down by network latency (drops from ~30 t/s to ~5–12 t/s over 1 GbE). | Full native GPU speed on the processing node (~35–70 t/s). |
| **Failure Vulnerability**| High. If any node in the pipeline disconnects, the entire active generation aborts. | Low. If a worker drops, queued jobs transparently fail over to another node. |
| **Hardware Heterogeneity** | Poor. Bound by the slowest node's clock cycle and memory bus in the pipeline. | High. Fast PC runs heavy models; laptop runs small utility tasks; phone views UI. |
| **Security Surface** | Raw unauthenticated socket protocols (`ggml-rpc`) execute arbitrary compute graphs. | Standard authenticated HTTP/HTTPS or WebSockets with JSON payloads. |

### 3. Concrete Architecture Recommendation for KesherAI

KesherAI's operating environment is a game developer's home workstation ecosystem:
1. **Primary PC:** 24 GB VRAM GPU (RTX 3090/4090), multi-core CPU, fast NVMe, LAN connected.
2. **Laptop:** Moderate CPU, integrated or low-tier GPU (4–8 GB VRAM), connected over Wi-Fi.
3. **Phone:** 390 px viewport mobile client connecting remotely via Tailscale, Cloudflare Tunnel, or home Wi-Fi.

#### 3.1 Why KesherAI Must Avoid Layer Splitting Across the Home Network
Attempting to run a 70B model by putting 40 layers on the 24 GB PC and 20 layers on the laptop over home Wi-Fi/Ethernet results in an abysmal user experience:
* The laptop's fans will run at maximum speed, draining the battery and overheating the machine.
* Wi-Fi latency jitter will throttle token generation to unreadable speeds (1–3 tokens/second).
* If the laptop goes to sleep or changes rooms, the PC's session crashes.

#### 3.2 What KesherAI Should Build First: Capability-Aware Orchestration

```
+----------------------------------------------------------------------------------------------------+
|                                    KESHERAI ROUTING TOPOLOGY                                       |
+----------------------------------------------------------------------------------------------------+
|                                                                                                    |
|    [ Mobile Phone (390px) ]          [ Laptop Client ]                                             |
|        Web UI Controller                 Web UI / Lightweight Agent                                 |
|               |                                  |                                                 |
|               +-----------------+----------------+                                                 |
|                                 |                                                                  |
|                                 v (Authenticated SSE / HTTP REST)                                  |
|               +------------------------------------+                                               |
|               |  KesherAI Core Orchestrator Server |                                               |
|               |      (Running on Main 24GB PC)     |                                               |
|               +------------------------------------+                                               |
|                     |                            |                                                 |
|         [ Hardware Fit Checker ]        [ Dynamic Model Dispatcher ]                               |
|                     |                            |                                                 |
|                     v                            v                                                 |
|      +------------------------------+     +-------------------------------+                        |
|      | Heavy Local Compute (24GB)   |     | Safe Free Cloud Fallback      |                        |
|      | - llama.cpp (70B / 32B LLMs) |     | - Groq (Llama 3.3 70B)        |                        |
|      | - ComfyUI (Flux, SDXL, Video)|     | - Cloudflare Workers AI       |                        |
|      | - Local Whisper / Embeddings |     | - OpenRouter :free            |                        |
|      +------------------------------+     +-------------------------------+                        |
|                                                                                                    |
+----------------------------------------------------------------------------------------------------+
```

1.  **Hardware Profile Discovery:**
    *   On startup, each KesherAI node inspects its environment: GPU vendor, available VRAM, total system RAM, and power state (AC power vs. battery).
    *   The primary 24 GB PC registers as a **Tier-1 Compute Provider** (`heavy: true, max_vram: 24GB`).
    *   The laptop registers as a **Tier-3 Light Provider / Client** (`heavy: false, max_vram: 0-4GB, battery_aware: true`).
2.  **Strict Device Protection (Laptop Safeguard):**
    *   The orchestrator enforces a hard rule: **No heavy GGUF models (>8B) and no diffusion/ComfyUI jobs are ever assigned to the laptop.**
    *   If the user runs KesherAI on the laptop while away from the desk, the laptop web UI acts as a thin remote client connecting back to the 24 GB desktop PC over the existing tunnel/network.
    *   If disconnected from the main PC, the laptop is restricted to ultralight local models (e.g., `Llama-3.2-3B`, `Qwen-2.5-Coder-3B`, or BGE-small embeddings) or safe free cloud APIs.
3.  **Per-Chat Engine & Device Selection UI:**
    *   Add an explicit device badge on the Chat and Image generation views in `apps/web`:
        *   `Target: Main PC (RTX 4090 - 24GB)` [Green]
        *   `Target: Free Cloud (Groq Llama 3.3)` [Blue]
        *   `Target: Local Laptop (3B Fast)` [Amber]
    *   Responsive layout: On mobile phones (390 px), this selector collapses into a compact status icon showing compute destination and active VRAM load.
4.  **Resilient Failure Handling (Circuit Breaker):**
    *   If a local engine fails to respond within 8 seconds or crashes due to out-of-memory (OOM), KesherAI's core server traps the error, resets the engine process, and offers a one-click reroute: *"Main PC GPU busy or disconnected. Reroute via Groq (Free Cloud)?"*
5.  **Zero-Trust Local Security:**
    *   Never expose unauthenticated raw TCP ports (`ggml-rpc-server`).
    *   Inter-machine communication must utilize KesherAI's authenticated REST and SSE channels secured with bearer tokens.

## Conclusion

KesherAI has a remarkable opportunity to expand its model ecosystem without risking user charges and without forcing complex network clustering:

1.  **Cloud APIs:** By integrating **Groq**, **Cloudflare Workers AI**, and **OpenRouter (`:free`)**, KesherAI users gain immediate, card-free access to high-speed Llama 3.3 70B, DeepSeek R1, vision models, and Flux image generation without any possibility of billing overdrafts. Integrating **Deepgram** ($200 non-expiring credit) unlocks native Hebrew voice transcription, while **ElevenLabs** (10,000 chars/month) delivers top-tier Hebrew voice synthesis.
2.  **Distributed Compute:** Slicing single model weights across consumer Wi-Fi using tools like `llama.cpp RPC` or `exo` is a false economy—it introduces massive network latency penalties, fragile dependencies, and security vulnerabilities. KesherAI's winning architecture is **capability-aware task dispatch**: leveraging the 24 GB workstation as the local AI powerhouse, utilizing free cloud providers as instantaneous overflow buffers, and keeping laptops and phones lightweight, responsive, and cool.
