# Research Report: Local Hebrew TTS with Kokoro-82M and Low-Latency Voice Cloning for KesherAI

### Summary

## Architectural Footprint, Latency, and Hardware Performance

Kokoro-82M is an open-source, Apache 2.0-licensed text-to-speech foundation model consisting of 82 million parameters [2]. Its decoder-only design avoids the iterative generation bottlenecks common in diffusion or older multi-stage models, producing direct audio waveforms efficiently [1]. 

* **Model Footprint and Quantization:** The model size varies by precision tier. * **Hardware Performance:** Kokoro-82M consumes less than 500 MB of RAM/VRAM, achieving real-time factors (RTF) below 0.15x on standard consumer CPUs and sub-30ms generation latency on NVIDIA GPUs [2]. It runs smoothly across Linux, macOS (Apple Silicon M1–M4 via MPS), Windows WSL2, and Python 3.10+ environments using ONNX Runtime or PyTorch [2].

## Hebrew Accuracy, Prosody, and SASPEECH Fine-Tunes

For Hebrew language generation, the community `kokoro-hebrew` project provides fine-tuned weights (`avris/kokoro-hebrew-saspeech` on Hugging Face) built on top of a patched StyleTTS2 + Kokoro recipe (`kikiri-tts`) [11]. 

* **Speaker and Quality:** The model is trained on the SASPEECH dataset (featuring single speaker Shaul Amsterdamski from the Israeli Public Broadcasting Corporation) at 24 kHz [11, 21]. It achieves a ~3% word error rate (evaluated via Whisper large-v3 round-trip) on optimal checkpoints, producing clear and intelligible Hebrew [11].
* **Prosody:** Because the underlying architecture retains StyleTTS2's adversarial style modeling, the fine-tune handles conversational pacing and natural pauses well [1, 11]. However, both the SASPEECH dataset and derivative model weights carry non-commercial restrictions inherited from the IPBC license [11].

## Offline G2P Vowelization and Nikkud Pipeline

Kokoro requires phonemized text inputs. For Hebrew, raw unvocalized text lacks explicit vowels, necessitating an automated grapheme-to-phoneme (G2P) and diacritic (nikkud) pipeline before speech generation [11].

* **The Pipeline:** KesherAI implements Hebrew G2P via `phonikud` (or `phonikud-onnx`), which is utilized consistently during both training and inference to maintain phonetic alignment [11]. Alternatively, systems can leverage tools like Dicta Nakdan [11].
* **Workflow:** Unvocalized user text passes through `phonikud` to add diacritics (`add_diacritics`), converting string inputs into fully vocalized Hebrew text (e.g., transforming plain text into vocalized strings like `שָׁלוֹם, מָה שְׁלוֹמְךָ הַיּוֹם?`) [11]. This vocalized text is subsequently processed by the inference engine into phonemes [11].

## Audio Streaming Architecture for KesherAI

To serve Roee with low-latency voice feedback in KesherAI, synthesis chunks must stream directly to the web client:

* **Client-Server Integration:** Python backends executing ONNX runtime inference or specialized JavaScript implementations (such as `kokoro-js` or WebGPU-backed streaming models) chunk generated audio frames [1, 7].
* **Delivery:** Audio segments are transmitted incrementally over WebSockets or handled directly in the browser via the Web Audio API [7], bypassing large file generation delays and securing a conversational response experience.

## Conclusion
Kokoro-82M combined with the `avris/kokoro-hebrew-saspeech` fine-tune and an offline `phonikud` G2P pipeline provides KesherAI with an efficient, low-latency, and zero-VRAM solution for Hebrew TTS [2, 11]. While the codebases and runtimes remain open-source under MIT or Apache-2.0 licenses, developers must account for the non-commercial constraints of the SASPEECH weights and dataset [11]. Implementing WebSocket-based chunk streaming ensures that Roee experiences seamless, near-instantaneous local speech synthesis [2, 7].
