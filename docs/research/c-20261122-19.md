# Autonomous In-Engine Playtesting and Automated QA Exploration Agent

An architecture for an autonomous agent inside KesherAI that boots a Unity or Unreal scene in Play mode, navigates the environment, detects bugs and hangs, and outputs structured bug receipts with screenshots.

## Existing KesherAI Foundation

KesherAI already has significant infrastructure that this agent would extend:

- **`unity-test.ts`** — `runUnityTest()` enters Play Mode for 1–60 s, enables auto-tick (so an unfocused Editor still runs), captures a Game-view screenshot, diffs the Console log (before vs. after Play), and always stops Play Mode, even on error. Returns a `TestRun` with `played`, `log: TestLine[]`, `picture`, and `seconds`.
- **`blueprint-test.ts`** — `runBlueprintTest()` does the equivalent for Unreal: compiles the Blueprint, optionally places an Actor in front of the player, runs PIE for 1–60 s, captures a screenshot from `Saved/KesherAI/test-run.png`, cleans the log (filtering engine noise like `LogSlate`, `LogRenderer` etc.), and returns a `TestRun`. A `judgeRun()` function sends the Blueprint-as-code, the log, and the screenshot to a vision model to judge pass/fail.
- **`TestLine`** and **`TestRun`** are shared interfaces used by both engines, with fields: `kind` (log/warning/error), `category`, `text`, `played`, `compile`, `log`, `picture`, `seconds`.
- **`tools.ts`** — Agent tools return a `ToolOutput` with text, diffs, `images` (for vision), `files`, and `assetIds`. The `view_image` tool sends a picture to the model. The `ToolContext` provides `signal` (abort), `progress` (live output), and `recordChange` (undo).
- **WORK_LIST.md** notes the existing "Test" button for Unity (line 269) and Unreal/Blueprint (line 282), compile-fix loops (line 273), intent routing (line 280), and a backlog item for specialised engine agents (line 285).

The autonomous playtesting agent extends the current single-shot "press Test" into a **looped exploration** that feeds input, moves a player character, monitors for anomalies, and files structured bug reports — all within the existing `TestRun` / `ToolOutput` pipeline.

## Input Injection Architecture

### Unity — Input System (`InputTestFixture` / Virtual Device Feeding)

Unity's Input System package provides `InputTestFixture`, a base class for Play Mode tests that completely disconnects the runtime from physical hardware and creates an isolated virtual input environment [1].

**Architecture for KesherAI:**

1. **Virtual device creation** — The KesherAI Unity bridge package (`com.kesherai.bridge`) would add a `PlaytestInputDriver` MonoBehaviour that, on entering Play Mode, calls `InputSystem.AddDevice<Keyboard>()` and `InputSystem.AddDevice<Gamepad>()` to create virtual devices.
2. **Command channel** — KesherAI's existing bridge socket (the same one `unity-test.ts` uses for `editor.playmode/start` and `capture/screenshot`) would accept an `inject_input` command carrying a serialised input frame: `{ device: "gamepad", control: "leftStick", value: [0, 1] }` or `{ device: "keyboard", key: "W", action: "press" }`.
3. **Key API surface:**
   - `InputSystem.AddDevice<T>()` — spawns a virtual Keyboard, Mouse, Gamepad, or Touchscreen [1].
   - `Press(ButtonControl)` / `Release(ButtonControl)` — digital input [1].
   - `Set(InputControl<T>, value)` — analog sticks, triggers, mouse delta [1].
   - `BeginTouch` / `MoveTouch` / `EndTouch` — mobile [1].
4. **Tick model** — KesherAI already enables `set_auto_tick` before entering Play Mode (line 28 of `unity-test.ts`), so frames advance even when the Editor is unfocused. The bridge flushes injected input each frame using `InputSystem.Update()`.
5. **Fallback for legacy Input Manager** — Projects that still use `UnityEngine.Input` (the old system) can be driven via `Input.simulateMouseWithTouches` and `SendMessage("OnGUI")`, but coverage is limited. The agent should check `PlayerSettings.activeInputHandler` and warn if legacy-only.

### Unreal — Enhanced Input Simulation

Unreal's recommended path for automated input testing is **direct injection via `UEnhancedInputLocalPlayerSubsystem`**, not the low-level `FGenericApplicationMessageHandler` [2].

**Architecture for KesherAI:**

1. **Action-level injection** — The KesherAI Unreal bridge plugin (already at version 0.1.27 per the work list) would expose an `inject_input` MCP command. On the C++ side it calls:
   ```
   Subsystem->InjectInputForAction(InputAction, FInputActionValue(true));   // digital
   Subsystem->InjectInputVectorForAction(InputAction, FVector2D(1, 0));     // axis
   ```
   This is superior to `FGenericApplicationMessageHandler` because it is decoupled from physical key bindings: if a designer remaps "Jump" from Space to a gamepad button, the injection still works [2].
2. **Why not `FGenericApplicationMessageHandler`** — It operates at the native OS/Slate layer, requires a focused viewport window, ignores `UInputMappingContext` priorities, and breaks in headless testing [2]. Enhanced Input injection bypasses all of this.
3. **Supplementary approaches:**
   - `FAutomationDriver` — for black-box UI interaction (Slate clicks, keyboard typing) [2].
   - `UWidgetInteractionComponent` — for UMG widget interaction during playtesting [2].
4. **Tick model** — The existing `blueprint-test.ts` already waits in a 500 ms polling loop while PIE runs (line 84). The autonomous agent would instead issue input commands between ticks via the bridge socket.

### Comparison

| Aspect | Unity | Unreal |
|---|---|---|
| Injection point | `InputTestFixture` / `InputSystem.AddDevice` | `UEnhancedInputLocalPlayerSubsystem::InjectInputForAction` |
| Abstraction level | Control-level (button, stick) | Action-level (IA_Move, IA_Jump) |
| Legacy fallback | `UnityEngine.Input` (limited) | `FGenericApplicationMessageHandler` (fragile, not recommended) |
| Existing KesherAI hook | `unity-test.ts` → bridge socket `command` | `blueprint-test.ts` → bridge `request("play", ...)` |

## Exploration Heuristic Evaluation

Three candidate strategies for autonomous navigation, evaluated for KesherAI's use case (a solo developer's project, one machine, quick feedback loop):

### 1. NavMesh Random Walk

The agent samples random reachable points on the engine's navigation mesh and pathfinds to each one [3].

| Pros | Cons |
|---|---|
| Zero training time, instant startup | Only tests developer-designated walkable areas |
| Lightweight, runs in real-time | Completely misses off-mesh exploits, wall clips, physics glitches |
| Uses built-in engine pathfinding (Unity NavMeshAgent, UE NavigationSystem) | No interaction with mechanics (doors, buttons, pickups) |
| Deterministic and reproducible | Poor at finding the bugs players actually hit |

**Verdict for KesherAI:** Best as the **base layer** — cheap, fast, covers the happy path. Not sufficient alone.

### 2. Curiosity-Driven Exploration (Intrinsic Curiosity Module / ICM)

An RL agent rewards itself for visiting novel states, using a self-supervised prediction-error model [3][4].

| Pros | Cons |
|---|---|
| Discovers edge cases, boundary exploits, physics glitches | Requires millions of frames of training per level |
| Handles sequential mechanics (key → door → button) | "Noisy TV" problem: grass, particles, random VFX distract the agent |
| True black-box, no game-specific scripting | Needs GPU-accelerated training loop, heavy for a solo dev's PC |
| Finds bugs NavMesh walkers cannot reach | Long setup per project; not "press Test and go" |

**Verdict for KesherAI:** Too heavy for the target use case (a single developer, one machine). Would only be viable if KesherAI offered a cloud training service, which is out of scope.

### 3. Visual Reinforcement Agents (Pixel-Based Deep RL)

The agent observes raw rendered frames and learns to navigate via CNN/ViT feature extraction + PPO/curiosity rewards [5].

| Pros | Cons |
|---|---|
| Platform-agnostic: same pipeline for PC, mobile, console | Even more sample-hungry than ICM with structured observations |
| Can detect visual glitches (T-pose, z-fighting) alongside navigation | Requires heavy GPU for both rendering and training |
| No engine API access needed beyond screenshots | Latency: screenshot → inference → action is slow |

**Verdict for KesherAI:** Not practical for real-time single-machine use. Useful as a future cloud-based enhancement.

### Recommended Hybrid for KesherAI

The pragmatic architecture is a **NavMesh-bootstrapped heuristic walker with rule-based interaction**:

1. **Phase 1 — NavMesh sweep:** random-walk to N waypoints, covering the level's walkable surface. Cheap, fast, catches geometry and performance issues.
2. **Phase 2 — Interaction probing:** at each waypoint, raycast for interactable objects (tagged or with known component types like `Button`, `Trigger`, `Pickup`), approach them, and inject the interaction input.
3. **Phase 3 — Boundary stress:** at level edges (NavMesh boundary polygons), inject movement toward walls and off-mesh to test collision and fall-through.
4. **Optional Phase 4 — LLM-guided exploration:** KesherAI's `judgeRun()` already sends screenshots to a vision model. The model could suggest "go toward the red door" or "try jumping off the cliff", replacing RL with KesherAI's existing model infrastructure. This avoids training entirely.

## Automated Anomaly Detection Criteria

The agent monitors during each exploration tick and flags anomalies:

### 1. Zero-Velocity Stuck Detection (stuck for >5 s)

- **Method:** Every 500 ms (matching the existing poll loop), record `transform.position`. If `|Δposition| < ε` (e.g. 0.01 units) for 10 consecutive samples (5 s) while the agent is injecting non-zero movement input, flag `STUCK`.
- **Unity:** Read `transform.position` via the bridge's `script_eval` or a dedicated `get_player_position` command.
- **Unreal:** Read `GetActorLocation()` via the bridge's `play_status` command (extend the existing `play_stop` response to include per-tick position).
- **Threshold:** >5 s is the default; configurable per project. Reset the counter on any position change >ε.

### 2. Physics Clipping / Fall-Through-Floor Detection

- **Method:** Track `position.y` (Unity, up axis) or `position.z` (Unreal, up axis). If `position < kill_z` (a project-defined floor threshold, default −100 units), flag `FALL_THROUGH`.
- **Supplementary:** If the player's collider overlaps with a static mesh collider (penetration depth >0), flag `CLIP`. Unity: `Physics.ComputePenetration`. Unreal: `SweepSingleByChannel` or overlap events.
- **Trigger:** Immediate on detection (a single frame below `kill_z` is enough).

### 3. Shader Error Logs

- **Unity:** Filter `TestLine[]` for `kind === "error"` and text matching `/shader error|compilation failed|shader variant/i`. The existing `parseConsole()` in `unity-test.ts` already captures all Console entries; the anomaly detector just adds a regex pass [6].
- **Unreal:** Filter `TestLine[]` for `category === "LogShaderCompilers"` or `category === "LogMaterial"` with `kind === "error"`. The existing `cleanLog()` in `blueprint-test.ts` already preserves `LogShaderCompilers` errors (line 41–48: errors from noise categories are kept).
- **Output:** Include the shader name and platform from the error text when available.

### 4. Framerate Drop Tracking (<20 FPS Hitching)

- **Unity:** The bridge queries `1.0f / Time.unscaledDeltaTime` each second (or uses `FrameTimingManager.GetLatestTimings`). If instantaneous FPS drops below 20 for >3 consecutive frames, flag `FPS_DROP` with the min FPS, duration, and player position.
- **Unreal:** Use `stat unit` data via `FPlatformTime::Seconds()` or the `stat DumpHitches` console command which automatically logs frame spikes above a threshold to `Saved/Logs/` [7]. Alternatively, Unreal Insights tracing (`-trace=cpu,gpu,frame`) generates a `.utrace` file for post-run analysis [7].
- **Threshold:** Default <20 FPS for ≥150 ms (3 frames at 20 FPS). Configurable; mobile targets might use <30 FPS.

### Detection Summary

| Anomaly | Trigger | Data Needed | Priority |
|---|---|---|---|
| `STUCK` | `|Δpos| < 0.01` for >5 s while input active | Position stream | High |
| `FALL_THROUGH` | `pos.y < kill_z` (default −100) | Position stream | Critical |
| `CLIP` | Collider penetration depth >0 with static geo | Physics query | Medium |
| `SHADER_ERROR` | Console/log regex match | Existing TestLine[] | High |
| `FPS_DROP` | <20 FPS for ≥3 frames | Frame timing | Medium |

### Integration with Existing KesherAI Types

The receipt is designed to map directly onto the existing `ToolOutput` interface:

- `output` — a human-readable summary of the receipt (one paragraph).
- `images` — the viewport screenshot as `{ mimeType: "image/png", data: base64 }`, matching `view_image`'s format.
- `files` — the full JSON receipt saved to disk, shown as a downloadable card.

The existing `judgeRun()` flow in `blueprint-test.ts` can consume receipts: send the screenshot + log + reproduction steps to a vision model, which triages severity and suggests a fix — exactly as it does today for single test runs.

## Conclusion

KesherAI's existing test infrastructure (`unity-test.ts`, `blueprint-test.ts`, bridge socket, `judgeRun()` with vision models) provides a strong foundation. The autonomous playtesting agent extends it with three additions: (1) an `inject_input` bridge command for both engines — `InputTestFixture` virtual devices for Unity, `InjectInputForAction` on the Enhanced Input subsystem for Unreal; (2) a NavMesh-bootstrapped heuristic walker with rule-based interaction probing and optional LLM-guided exploration (avoiding the training cost of full RL); and (3) five anomaly detectors (stuck, fall-through, clip, shader error, FPS drop) that produce structured JSON bug receipts with screenshots, input replay streams, and engine logs — all fitting into KesherAI's existing `ToolOutput` / `TestRun` pipeline.

The LLM-guided exploration variant (Phase 4) is unique to KesherAI: instead of training an RL policy, the agent screenshots the viewport, asks the chat model "where should I go next?", and injects the suggested input. This leverages infrastructure KesherAI already has and avoids the sample-efficiency and GPU-cost problems of curiosity-driven or visual RL agents.
