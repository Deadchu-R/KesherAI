# Local Video In-Betweening and Motion Continuity with Wan 2.1 in ComfyUI Desktop

## Summary

This research establishes the complete technical architecture for integrating local video in-betweening and shot continuation into KesherAI's non-linear video editor (`plugins/video-editor/`) via ComfyUI Desktop. Operating locally on a 24GB VRAM workstation (e.g., NVIDIA RTX 3090/4090 with 96GB system RAM), the pipeline enables creators to extend existing shots, generate coherent transitional motion between discontinuous clips, and stream real-time generation previews directly onto the editing playhead. 

To overcome hardware limits without compromising system stability, the architecture coordinates a zero-collision memory swap protocol between the active `llama.cpp` inference engine (which powers KesherAI's agentic chat) and ComfyUI's diffusion execution graph. Generation requests are formatted into a native ComfyUI API JSON payload leveraging the Wan 2.1 Image-to-Video (I2V) architecture (14B FP8 or 1.3B FP16), tracked through a persistent WebSocket stream for step progress and interim latent frames, and automatically ingested into the NLE timeline with frame-accurate trim compensation to eliminate conditioning freezes.

## 1. ComfyUI API JSON Workflow Architecture for Wan 2.1 I2V

Wan 2.1 introduces a flow-matching 3D video diffusion transformer architecture developed by Alibaba Tongyi Lab, available in 1.3B and 14B parameter scales [4, 6]. Unlike older video models that required complex cascaded super-resolution pipelines, Wan 2.1 natively handles spatiotemporal patch compression via a causal 3D VAE and cross-attention text/image conditioning [6].

### 1.1 Core Node Graph Anatomy

In ComfyUI's native execution graph, the Image-to-Video workflow departs from standard Stable Diffusion pipelines [1, 2]. Rather than relying on simple latent noise concatenation, Wan 2.1 requires explicit conditioning expansion where image embeddings and initial frame tensors are injected directly into the temporal latent sequence [1, 5].

The complete pipeline requires seven fundamental stages:
1. **Model Weight Ingestion:** `UNETLoader` loads the diffusion transformer weights (e.g. `wan2.1_i2v_480p_14B_fp8.safetensors` or `wan2.1_t2v_1.3B_fp16.safetensors`), while `ModelSamplingSD3` applies a flow-matching variance schedule shift (typically $\text{shift} = 8.0$) [1, 2].
2. **Dual Conditioning:** `CLIPLoader` loads the multilingual `umt5_xxl_fp8_e4m3fn_scaled.safetensors` text encoder (type `wan`), passing tokens to `CLIPTextEncode`. For enhanced visual fidelity, an optional `CLIPVisionLoader` (`clip_vision_h.safetensors`) encodes high-level visual features via `CLIPVisionEncode` [1, 2].
3. **Spatiotemporal VAE Setup:** `VAELoader` initializes `wan_2.1_vae.safetensors`, a causal autoencoder designed to compress video across both spatial ($8\times8$) and temporal ($4\times$) dimensions [2, 6].
4. **I2V Latent Preparation (`WanImageToVideo`):** This native node consumes the positive/negative conditioning, VAE, spatial dimensions, frame length, and source image. It injects the initial frame into the first temporal slice of the latent tensor and produces masked conditioning blocks [1, 5].
5. **Flow-Matching Sampler (`KSampler`):** Executes iterative reverse-diffusion. The recommended parameters are $20–30$ steps, CFG scale $5.0–6.0$, using the `uni_pc` or `euler` sampler with the `simple` scheduler [1, 2].
6. **Temporal Latent Decoding (`VAEDecode`):** Decompresses the 16-channel 3D latent tensor back into RGB frame arrays.
7. **Video Packaging (`CreateVideo` / `SaveVideo`):** Encodes uncompressed image frames into an H.264/MP4 container at 16 or 24 frames per second [1].

### 1.2 Mathematical Frame Constraints ($4n + 1$)

Due to Wan 2.1's temporal 3D VAE downsampling factor ($4\times$), generated frame counts must strictly obey the mathematical sequence:
$$F = 4n + 1 \quad \text{where } n \in \mathbb{N}_{\ge 1}$$
Standard allowed lengths include 33 frames (~2.06 s at 16 fps), 49 frames (~3.06 s at 16 fps), 65 frames (~4.06 s at 16 fps), 81 frames (~5.06 s at 16 fps), and 121 frames (~5.04 s at 24 fps) [1, 8]. Submitting arbitrary frame numbers (e.g., 60 or 100) causes latent shape mismatches during temporal convolution passes in the VAE decoder.

## 2. VRAM Allocation Budgets & Dynamic Model Swapping

### 2.1 Memory Footprints on 24GB GPUs

A single 24GB GPU (RTX 3090 / 4090) operates in an overcommitted state if multiple generative neural engines reside simultaneously in VRAM [8]. In KesherAI, the primary local LLM chat engine (`llama.cpp` hosting models such as Qwen 2.5 14B/32B or DictaLM) occupies 10GB to 16GB of VRAM when loaded with active KV caches [8]. 

Simultaneously, Wan 2.1 presents heavy resource requirements [3, 8]:
- **Wan 2.1 14B (Native FP16):** Weights alone consume ~28GB VRAM. In inference, peak activation and attention buffers require >38GB VRAM, resulting in immediate CUDA OOM crashes on 24GB cards [3, 8].
- **Wan 2.1 14B (FP8 Quantized):** Weights require ~14.2GB. Combined with the UMT5-XXL text encoder (~6.7GB in FP8) and the 3D VAE (~1.4GB), the static weight footprint totals ~22.3GB [2, 8]. Dynamic inference activations require an additional 4GB–6GB VRAM [8].
- **Wan 2.1 1.3B (Native FP16):** Weights require only ~2.8GB. Total VRAM footprint during 480p sampling stays under 7.5GB [4].

To run the flagship 14B FP8 model on 24GB hardware without crashing, ComfyUI relies on **CPU Offloading**, leveraging the workstation's 96GB system RAM [8]. ComfyUI streams the text encoder into VRAM to compute prompt embeddings, purges it back to host RAM, loads the 14B diffusion transformer into VRAM for sampling, and subsequently swaps the transformer out to host RAM to load the VAE decoder [2, 8].

```
+--------------------------------------------------------------------------+
|                       24GB VRAM GPU ALLOCATION                           |
+--------------------------------------------------------------------------+
| [State A: Active LLM Chat]                                               |
| |======= llama.cpp (14GB) =======|== KV Cache (3GB) ==|-- Free (7GB) --| |
+--------------------------------------------------------------------------+
|                          MUTEX SWAP TRANSITION                           |
| 1. llama.cpp releases GPU allocations (evicts context / slots)           |
| 2. GpuGuard verifies free VRAM > 21GB via nvidia-smi                     |
+--------------------------------------------------------------------------+
| [State B: Wan 2.1 14B Video Generation]                                  |
| Stage 1: |=== UMT5 Text Enc (6.7GB) ===|-- Host RAM Stage --| Free (17GB) |
| Stage 2: |====== Wan 14B FP8 DiT (14.2GB) ======|== Act (5GB) ==| Free (4GB) |
| Stage 3: |=== Wan 3D VAE (1.4GB) ===|==== Frames (6GB) ====| Free (16GB) |
+--------------------------------------------------------------------------+
|                          RESTORATION TRANSITION                          |
| 1. POST /free {"unload_models": true, "free_memory": true} to ComfyUI     |
| 2. llama.cpp re-engages GPU layers and restores cached conversation      |
+--------------------------------------------------------------------------+
```

### 2.2 Model Swapping Protocol Implementation

KesherAI enforces execution safety through `GpuGuard` (`packages/core/src/gpu-guard.ts`) and `HeavyGate` (`packages/core/src/heavy-gate.ts`). Under this protocol, video synthesis is classified as an exclusive heavyweight task.

The four-phase lifecycle functions as follows:

```typescript
/**
 * Executes a Wan 2.1 video continuation job with strict VRAM arbitration.
 */
export async function executeVideoSwapPipeline(
  comfyUrl: string,
  llamaEngine: LlamaEngine,
  guard: GpuGuard,
  workflow: ComfyWorkflow,
  onProgress?: (p: JobProgress) => void
): Promise<GeneratedFile[]> {
  return heavyGate.run({ en: "Video generation (Wan 2.1)", he: "יצירת וידאו (Wan 2.1)" }, async () => {
    // Phase 1: Standby llama.cpp and evict VRAM
    await llamaEngine.standby();
    await waitForVramHeadroom(20 * 1024 * 1024 * 1024); // Ensure 20GB free

    try {
      // Phase 2: Dispatch ComfyUI Workflow
      const provider = new ComfyUIProvider({ id: "comfy-local", baseUrl: comfyUrl });
      const results = await provider.runFlow(workflow, undefined, 30 * 60_000, onProgress);
      return results;
    } finally {
      // Phase 3: Flush ComfyUI VRAM Allocations
      await fetch(`${comfyUrl}/free`, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ unload_models: true, free_memory: true })
      }).catch(() => undefined);

      // Phase 4: Resume llama.cpp Chat Engine
      await llamaEngine.resume();
    }
  });
}
```

#### Protocol Guarantees:
1. **Re-entrant Exclusivity:** `HeavyGate` prevents concurrent triggers from the chat UI or background tasks while a 20-minute video generation job is active.
2. **Thermal Hysteresis:** If the GPU core temperature exceeds `maxTemp` (default 80°C), `GpuGuard` delays the start of the next workflow until temperature settles below `resumeTemp` (default 68°C).
3. **Graceful Cancellation:** If the user presses "Stop" in the NLE, an HTTP `POST /interrupt` or `POST /queue { "delete": [promptId] }` is dispatched immediately, followed by `POST /free` to ensure zero orphaned tensors remain in VRAM [7].

## 3. WebSocket Client Architecture: Progress & Interim Latents

ComfyUI exposes a bi-directional WebSocket interface at `/ws?clientId={UUID}` that delivers execution events and previews [1, 7].

### 3.1 Protocol Specifications & Frame Demuxing

The WebSocket stream multiplexes two distinct data formats:
1. **Text UTF-8 JSON Frames:** Convey operational telemetry, queue state transitions, and step counters.
2. **Binary Frames (Interim Latent Previews):** Convey real-time approximations of the video latent as denoising proceeds [7].

The binary preview format conforms to an 8-byte binary header followed by raw image bytes:
- **Bytes 0–3 (`uint32`, big-endian):** Event type identifier. `1` indicates an interim preview image (`PREVIEW_IMAGE`).
- **Bytes 4–7 (`uint32`, big-endian):** Image format encoding. `1` indicates JPEG format; `2` indicates PNG format.
- **Bytes 8+:** Image payload data.

### 3.2 Robust Client Implementation

Below is the specialized client implementation designed for KesherAI's frontend and core layer:

```typescript
import { WebSocket, MessageEvent } from "ws";

export interface LatentPreviewUpdate {
  phase: "sampling";
  step: number;
  totalSteps: number;
  percentage: number;
  nodeId: string;
  previewDataUrl?: string;
}

export class ComfyVideoSocketClient {
  private ws?: WebSocket;
  private currentPromptId?: string;
  private activeSamplingNode?: string;
  private currentStep = 0;
  private totalSteps = 1;

  constructor(
    private readonly baseUrl: string,
    private readonly clientId: string,
    private readonly onUpdate: (update: LatentPreviewUpdate) => void,
    private readonly onError: (err: Error) => void
  ) {}

  public connect(promptId: string): void {
    this.currentPromptId = promptId;
    const wsUrl = `${this.baseUrl.replace(/^http/, "ws")}/ws?clientId=${encodeURIComponent(this.clientId)}`;
    
    this.ws = new WebSocket(wsUrl);
    this.ws.binaryType = "arraybuffer";

    this.ws.onmessage = (event: MessageEvent) => {
      if (typeof event.data === "string") {
        this.handleTextMessage(event.data);
      } else if (event.data instanceof ArrayBuffer) {
        this.handleBinaryMessage(event.data);
      }
    };

    this.ws.onerror = (evt) => {
      this.onError(new Error("ComfyUI WebSocket communication failure"));
    };
  }

  private handleTextMessage(jsonString: string): void {
    try {
      const msg = JSON.parse(jsonString);
      const data = msg.data ?? {};
      
      // Filter messages belonging to other queued jobs
      if (data.prompt_id && data.prompt_id !== this.currentPromptId) return;

      switch (msg.type) {
        case "executing":
          this.activeSamplingNode = data.node ?? undefined;
          break;

        case "progress":
          this.currentStep = Number(data.value);
          this.totalSteps = Number(data.max);
          this.onUpdate({
            phase: "sampling",
            step: this.currentStep,
            totalSteps: this.totalSteps,
            percentage: Math.round((this.currentStep / this.totalSteps) * 100),
            nodeId: String(data.node ?? this.activeSamplingNode)
          });
          break;

        case "execution_error":
          this.onError(new Error(`ComfyUI Node Error [${data.node_type}]: ${data.exception_message}`));
          break;
      }
    } catch {
      // Ignore unparseable frames
    }
  }

  private handleBinaryMessage(buffer: ArrayBuffer): void {
    if (buffer.byteLength < 9) return;
    const view = new DataView(buffer);
    
    const eventType = view.getUint32(0); // 1 = PREVIEW_IMAGE
    if (eventType !== 1) return;

    const formatCode = view.getUint32(4); // 1 = JPEG, 2 = PNG
    const mime = formatCode === 2 ? "image/png" : "image/jpeg";
    const imageBytes = Buffer.from(buffer, 8);
    
    const previewDataUrl = `data:${mime};base64,${imageBytes.toString("base64")}`;
    
    this.onUpdate({
      phase: "sampling",
      step: this.currentStep,
      totalSteps: this.totalSteps,
      percentage: Math.round((this.currentStep / this.totalSteps) * 100),
      nodeId: this.activeSamplingNode ?? "KSampler",
      previewDataUrl
    });
  }

  public close(): void {
    if (this.ws) {
      this.ws.close();
      this.ws = undefined;
    }
  }
}
```

## 4. NLE Timeline Ingestion, Alignment, & Trim Calibration

Once ComfyUI completes execution, the generated asset (e.g. `kesher_continuation_00001.mp4`) must be integrated into the project's edit decision list (EDL).

### 4.1 Frame Duplication & Trim Compensation

A critical artifact occurs in raw Image-to-Video generation: **conditioning frame duplication**. 

In Wan 2.1, the anchor frame supplied via `start_image` is encoded directly into frame $t=0$ of the generated video [1, 5]. If the synthesized clip is inserted directly after the source clip without adjustment, frame $t=0$ of the generated video is visually and temporally identical to the final frame of the preceding clip. During 24 fps playback, this causes a jarring $41.6\text{ ms}$ motion freeze (stutter) before movement resumes.

To guarantee seamless kinematic continuity, the editor must apply an automatic head trim:
$$\text{trim}_{\text{head}} = \frac{1}{\text{FPS}_{\text{target}}}$$
For a 16 fps render, the first $0.0625\text{ s}$ is trimmed. For a 24 fps render, the first $0.0416\text{ s}$ is trimmed.

```
Source Clip A Timeline:
[======================= Clip A =======================| (Anchor Frame extracted at A.to)
                                                        |
Raw Wan 2.1 Output:                                     |
                                                        [Frame 0 (Duplicate)] [Frame 1] [Frame 2] ...
                                                        |<- Trim Offset (1/fps) ->|
Adjusted Timeline Insertion:                            |
[======================= Clip A =======================][Frame 1] [Frame 2] [Frame 3] ... (Smooth Motion!)
```

### 4.2 In-Betweening (Interpolation Between Two Existing Clips)

When generating transitional footage between Clip A and Clip B:
1. **Anchor Selection:** The tail frame of Clip A ($t_{\text{tail}} = A.\text{to}$) serves as `start_image` in `WanImageToVideo` [1].
2. **Motion Prompting:** The prompt describes the camera transition and subject transformation leading toward Clip B's visual context.
3. **Transition Insertion:** The synthesized video is placed after Clip A (with head-trim applied). At the junction between the synthesized clip and Clip B, an automated 8-frame cross-dissolve (`xfade` transition in FFmpeg export, or `veil` canvas shader in the web player) blends the synthesized tail into Clip B's head, masking any minor structural divergence.

### 4.3 NLE Timeline Insertion Algorithm

The timeline state within KesherAI is structured as:
- `media`: Array of asset definitions: `[{ path, kind: "video" | "image", url, duration, name }]`
- `clips`: Edit Decision List (EDL) sequence: `[{ id, from, to, m, into? }]`

The automated ingestion procedure operates as follows:

```typescript
export interface InsertContinuationParams {
  sourceClipIndex: number;
  generatedFilePath: string;
  generatedDuration: number;
  targetFps: number;
}

export function insertSynthesizedContinuation(
  mediaList: MediaItem[],
  clipsList: ClipItem[],
  params: InsertContinuationParams
): { updatedMedia: MediaItem[]; updatedClips: ClipItem[]; newClipId: number } {
  const { sourceClipIndex, generatedFilePath, generatedDuration, targetFps } = params;
  const targetClip = clipsList[sourceClipIndex];
  if (!targetClip) throw new Error("Invalid source clip reference");

  // 1. Register new video asset in the project media registry
  const newMediaIndex = mediaList.length;
  const newMediaItem: MediaItem = {
    path: generatedFilePath,
    kind: "video",
    url: `/api/plugin-files/video-editor/${encodeURIComponent(generatedFilePath)}`,
    duration: generatedDuration,
    name: generatedFilePath.split(/[\\/]/).pop() ?? "Synthesized Clip"
  };
  const updatedMedia = [...mediaList, newMediaItem];

  // 2. Compute frame-accurate head trim offset to eliminate duplicate anchor frame
  const trimHeadSeconds = 1.0 / targetFps;
  const effectiveDuration = Math.max(0.1, generatedDuration - trimHeadSeconds);

  // 3. Construct new timeline clip
  const newClipId = Date.now();
  const continuationClip: ClipItem = {
    id: newClipId,
    m: newMediaIndex,
    from: trimHeadSeconds, // Skip duplicate frame 0
    to: generatedDuration,
    into: { kind: "cut", seconds: 0 }
  };

  // 4. Perform magnetic ripple insertion directly after source clip
  const updatedClips = [
    ...clipsList.slice(0, sourceClipIndex + 1),
    continuationClip,
    ...clipsList.slice(sourceClipIndex + 1)
  ];

  return { updatedMedia, updatedClips, newClipId };
}
```

## 5. Architectural Comparison & Technical Trade-offs

| Criterion | Wan 2.1 1.3B (FP16) | Wan 2.1 14B (FP8 Quantized) | Wan 2.2 TI2V 5B |
| :--- | :--- | :--- | :--- |
| **VRAM Footprint (Inference)** | 7.2 GB – 8.5 GB | 18.5 GB – 22.0 GB (with CPU offload) | 11.0 GB – 13.5 GB |
| **System RAM Requirement** | 16 GB | 64 GB+ (Offload paging) | 32 GB |
| **Generation Latency (81 frames)** | 2.5 – 4.5 minutes | 18 – 35 minutes | 7 – 12 minutes |
| **Motion Continuity Fidelity** | Moderate; slight micro-jitter on fast camera moves | Exceptional; cinematic trajectory preservation | Strong; good edge adherence |
| **Native Resolutions** | 832×480, 480×832 | 832×480, 1280×720, 720×1280 | 1280×704, 704×1280 |
| **Memory Swap Requirement** | Optional; can coexist with 8B LLMs | **Mandatory; must evict LLM weights** | Recommended on 24GB cards |

### Resolution of Technical Disagreements:
1. **FP16 vs FP8 for 14B on 24GB Cards:** Sources universally agree that unquantized FP16 cannot execute on 24GB GPUs without out-of-memory failure [3, 8]. FP8 quantization (`e4m3fn`) is mandatory for local 14B synthesis [2, 8].
2. **Text Encoder Precision:** Loading UMT5-XXL in FP16 consumes >11GB VRAM alone [8]. Using `umt5_xxl_fp8_e4m3fn_scaled` reduces this to 6.7GB, enabling swift offload transfers across PCIe Gen4 buses [2, 8].
3. **Client-Side vs Server Decoding:** Decoding high-dimensional 3D causal latents cannot run in WebGPU shaders inside standard browsers; decoding must remain on the ComfyUI server daemon before streaming the assembled MP4 container back to the web client.

## Conclusion

Integrating Wan 2.1 into KesherAI's video editor delivers automated, professional-grade motion extension and in-betweening without cloud dependencies or subscription costs. By combining:
1. A strictly formatted ComfyUI API payload utilizing native `WanImageToVideo` and causal 3D VAE nodes,
2. An orchestrated VRAM swapping protocol managed by `HeavyGate` and `GpuGuard` that unloads `llama.cpp` before execution and clears PyTorch caches via `POST /free`,
3. A bi-directional WebSocket client streaming progress telemetry and binary preview latents to the NLE monitor, and
4. An automated timeline ingestion routine that applies frame-accurate $1/\text{FPS}$ trim compensation to eliminate anchor frame stutter,

KesherAI achieves seamless video continuation and motion continuity within the physical operating limits of a 24GB desktop workstation.
