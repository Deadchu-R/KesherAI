# Technical Architecture: Mobile WebRTC and Touch-First Control for 3D Viewports and Game Playtesting (KesherAI / Roee)

## Summary
Hosting and streaming game engine web builds and interactive 3D viewports to mobile phones (optimized for a 390px viewport width) requires navigating strict platform constraints. This architecture report specifies the necessary HTTP server headers for `SharedArrayBuffer` and WASM64 execution, details memory mitigation strategies to keep canvases beneath iOS Safari’s harsh 512MB RAM ceiling, outlines a gesture arbitration state machine to decouple camera navigation from object selection, and establishes a touch-first virtual gamepad specification.

---

## ## Required HTTP Server Headers for SharedArrayBuffer and WASM64
To unlock multithreaded WebAssembly (`SharedArrayBuffer`, WASM atomics, and WASM64 execution) across modern mobile browsers, the application origin must be **cross-origin isolated** [17, 18]. Without these explicit security headers, the browser hides `SharedArrayBuffer`, causing engine runtimes to throw allocation or initialization errors.

The web server must emit the following response headers on the main document and asset endpoints [18]:
```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

### Subresource and Asset Implications
Enabling `Cross-Origin-Embedder-Policy: require-corp` (COEP) enforces that all subresources (shaders, textures, audio files, Web Workers, and WASM binaries) loaded from cross-origin domains must explicitly opt-in via CORS (`Access-Control-Allow-Origin: *` or specific origin) or Cross-Origin Resource Policy (`Cross-Origin-Resource-Policy: cross-origin` or `same-origin`) [18]. 

Verification can be executed programmatically inside the client environment via [18, 19]:
```javascript
if (self.crossOriginIsolated) {
    // SharedArrayBuffer and WASM64/Threads are fully unlocked
}
```

## ## Memory Mitigation Strategies for iOS Safari's 512MB Ceiling
iOS Safari is the most restrictive WebGL and WebAssembly host, enforcing a strict heap/memory limit roughly between 300MB and 500MB [2]. Exceeding this boundary instantly crashes the tab to a blank page [2]. To maintain stability on a 390px mobile viewport for KesherAI playtesting, apply the following mitigation techniques:

1. **Heap Allocation Bounds:** 
   - Configure engine export templates (such as Unity/Unreal/Godot WebGL or custom engines) to cap initial WebAssembly memory size. Set `memorySize` parameters to **256MB** or a maximum of **384MB** to leave headroom for browser overhead, DOM elements, and WebGL buffers [2].
2. **Aggressive Code and Asset Stripping:**
   - Enable high levels of managed code stripping and link-time optimization (LTO) to eliminate unused engine modules [2].
   - Compress all build assets using **Brotli** or Gzip to reduce transport size and avoid large memory spikes during uncompression [2].
3. **Canvas Resolution Scaling (DPI Management):**
   - High-density Retina displays (e.g., 3x scaling on iPhones) multiply fragment shader workloads and frame-buffer sizes exponentially [8]. 
   - Cap the canvas drawing buffer resolution multiplier to a maximum of `1.0` or `1.5` relative to the CSS layout size (390px width), rather than matching `window.devicePixelRatio` (which reaches 3x on modern iPhones). This prevents high-res canvas frame buffers from exhausting the 512MB limit [8].
4. **Texture and Audio Optimization:**
   - Use compressed texture formats compatible with mobile WebGL/WebGPU (e.g., ASTC or ETC2).
   - Gate all audio context initialization and sample decoding strictly behind explicit user interaction to prevent memory leaks and `NotAllowedError` blocks [2].

## ## Gesture Arbitration State Machine
To handle 3D viewports where touch input must selectively control camera navigation (orbit/pan/zoom) or individual 3D object picking/manipulation, an explicit gesture arbitration state machine is required. Raw pointer events feed into competing recognizers that evaluate data against movement thresholds (touch slop) and timing limits [9].

```
                 [ Pointer Down ]
                        │
         ┌──────────────┴──────────────┐
         ▼                             ▼
   (Within Slop)                (Exceeds Slop / 28px)
         │                             │
  [ Hold Timer Active ]                ├─► Dominant Axis X/Y? 
         │                             │   ├─► Horizontal/Vertical Drag (Pan)
   Elapsed > 600ms?                    │   └─► Free Pan / Orbit
         │                             │
         ├─► [ Long Press Selected ]   └─► Multi-touch active?
         └─► [ Tap (Pending Release) ]       └─► Pinch-to-Zoom / Rotate
```

### Arbitration Rules and States:
- **Touch Slop Tolerance:** A movement radius threshold (e.g., 28px) defines the ambiguity window [9]. Minor drift within this radius preserves `Tap` or `Long Press` candidates [9].
- **Axis Dominance:** If movement breaks the touch slop threshold, vector analysis compares axes. If one axis is significantly stronger (e.g., $|{\Delta}x| > 1.75 \times |{\Delta}y|$), directional navigation (Pan or Orbit) takes priority, instantly rejecting tap interpretations [9].
- **Cancellation Handling:** Operating systems or UI overlays can fire `pointercancel` events. The state machine must handle cancellation as a distinct terminal outcome—cleaning up active interaction loops and resetting pointers without triggering false release/click events [9].

## ## Responsive Virtual Gamepad / Joystick Overlay Specification
For remote mobile playtesting of interactive 3D viewports on a 390px-wide screen, the interface requires a touch-first virtual control overlay designed to minimize thumb obstruction of the viewport.

### Layout & Sizing (390px Viewport Reference):
- **Left Thumb Zone (Virtual Joystick / D-Pad):** 
  - Position: Bottom-left corner (`bottom: 24px`, `left: 24px`).
  - Dimensions: Outer container diameter of **120px** (touch target zone), with an inner thumbstick knob diameter of **56px**.
  - Behavior: Floating or fixed origin. Dynamic activation spawns the base at the initial touch coordinate if touched within the left half of the screen.
- **Right Thumb Zone (Action & Camera Swivel Pad):**
  - Position: Bottom-right corner (`bottom: 24px`, `right: 24px`).
  - Dimensions: Free-form drag area covering the lower-right quadrant of the 390px screen
