# KesherAI Research Report: Tauri vs Electron, Rust Inference Engines, and Napi-rs Integration

KesherAI is currently an Electron application utilizing a TypeScript monorepo, a Fastify backend server, a React web UI, and a phone remote. This research report evaluates the feasibility of migrating the desktop shell to Tauri 2, adding an alternative native inference engine alongside `llama.cpp`, and accelerating performance bottlenecks using Rust via `napi-rs` without a full application rewrite.

---

## ## 1. Desktop Shell: Staying on Electron vs. Moving to Tauri 2

### Performance and Footprint
* **Installer Size:** Electron applications routinely bundle Chromium and Node.js, resulting in installer sizes between 80 MB and 120 MB (measured at 106.1 MB in comparative benchmarks) [1, 2]. Tauri 2 utilizes OS-native WebViews (WebView2 on Windows), dramatically reducing installer footprints down to 5 MB to 15 MB (and under 3 MB for minimal configurations), achieving roughly a 100x size reduction [1, 2].
* **RAM & CPU Usage:** Electron apps typically consume 200–500 MB on startup and hover around 149 MB idle [1, 2]. Tauri 2 reduces idle memory consumption down to 50–150 MB (around 142 MB in direct comparisons, yielding about a 5% to multi-fold savings depending on window counts) [1, 2]. Tauri also reduces idle CPU utilization to 0–1% (compared to Electron's 2–5%) due to Rust's efficient background execution [1].
* **Startup Time:** Tauri launches in approximately 0.5 to 1 second, whereas Electron requires 2 to 4 seconds, representing roughly a 3x speedup [1].

### Architecture and Native Integration
* **Windows Support:** Fully supported via Tauri 2 using the native Windows WebView2 runtime [1].
* **Auto-Update:** Electron benefits from mature, drop-in tools like `electron-updater` [5]. Tauri 2 includes an official built-in updater system, though setting up code signing and secure endpoints requires manual configuration.
* **Native Modules & Sidecars:** 
  * Node-specific native modules like `node-pty` (used for terminal emulation) cannot run directly inside Tauri's Rust core without replacement. They must be ported to native Rust terminal libraries (such as `alacritty` backend components or portable PTY crates) or run inside a decoupled sidecar process.
  * Child processes (spawning `llama.cpp` or ComfyUI binaries) map cleanly to Tauri's Sidecar API, which bundles external binaries securely alongside the application package.
* **Node Server & Migration Effort:** The Fastify Node server cannot execute natively inside Tauri's frontend context. It must either be rewritten into Tauri's Rust backend commands/state, or kept running as a local Node.js sidecar process spawned on startup. 
* **Migration Stories & Effort Estimate:** Real-world migrations for medium-sized apps (approx. 50k lines of code, similar to architecture shifts seen in modern tooling) typically demand **2 to 3 months** of engineering effort [1]. The primary cost lies in abstracting Node.js-specific backend services and swapping native bindings (`node-pty`) rather than moving the React UI [1].

**Recommendation:** **Stay on Electron for now.** While Tauri 2 offers superior installer sizes and startup speeds [1, 2], the engineering cost of decoupling the Fastify server, rewriting `node-pty` into Rust equivalents, and modifying process management workflows outweighs the immediate performance gains for a complex AI application like KesherAI.

## ## 2. Inference Engines: mistral.rs and Candle vs. llama.cpp

### Performance on RTX 3090 (24 GB) & Ryzen 9 9950X3D
* **llama.cpp:** Highly optimized for consumer hardware. On an RTX 3090, standard Q4_K_M quantized 8B models achieve roughly 85–145 tokens/sec, 32B models achieve 20–40 tokens/sec, and 70B models (fully offloaded across dual 3090s) run at 10–17 tokens/sec [9]. CPU-only execution on high-end desktop processors yields single-digit token rates (5–8 tokens/sec for 8B models) [9].
* **mistral.rs & Hugging Face Candle:** Both provide pure-Rust inference ecosystems. While Candle offers exceptional low-level tensor primitives, `mistral.rs` builds a full-featured engine on top of it with robust paged attention, speculative decoding, and native OpenAI-compatible server endpoints. However, on standard GGUF quantizations and single-GPU setups (RTX 3090), `llama.cpp` maintains a mature lead in raw streaming throughput and stability.

### Feature Matrix
| Feature | `llama.cpp` | `mistral.rs` / Candle |
| :--- | :--- | :--- |
| **Model Coverage & Speed** | Industry standard; immediate day-1 support for new architectures. | Rapid growth, but lags behind `llama.cpp` for niche or newly released model variants. |
| **Quantization Formats** | Extensive GGUF variants (IQ2, Q4, Q5, Q8, etc.). | Supports GGUF, AWQ, GPTQ, and EXL2 through underlying libraries. |
| **OpenAI-Compatible Server** | Native (`llama-server`). | Native built-in server implementation. |
| **Tool Calling & Speculative Decoding** | Extensively supported and battle-tested. | Supported, though configuration varies by model architecture. |
| **CPU Offload & Windows Support** | Exceptional CUDA and Windows MSVC support. | Fully supports Windows and CUDA via Candle backends. |
| **Maturity** | Extremely high; dominant standard in local LLM runtimes. | Moderate; rapidly maturing open-source ecosystem. |

**Recommendation:** **Do not add `mistral.rs` or Candle as an optional engine at this stage.** `llama.cpp` remains superior in quantization variety, memory management stability on a single RTX 3090, and day-1 model coverage. Adding a secondary Rust engine introduces unnecessary maintenance overhead without providing a performance advantage over `llama.cpp`.

## ## 3. Targeted Performance Optimization via `napi-rs`

Without rewriting KesherAI, heavy JavaScript/TypeScript operations can be offloaded to compiled native Rust modules using **`napi-rs`**, which bridges Node.js and Rust via the stable Node-API with zero-copy data passing and zero `node-gyp` configuration friction [16, 17, 18].

### Candidates to Measure First
1. **Log Search:** Scanning and filtering massive local JSON/text log files inside the Fastify server. Moving regex filtering and text matching to multi-threaded Rust code (`rayon` + efficient string searching) will eliminate event-loop blocking.
2. **File Indexing:** Traversing directories, hashing file contents, and building search trees for KesherAI’s workspace context. Rust's native file-system performance significantly outperforms Node.js `fs` iteration modules.
3. **Diffs:** Computing line or token-level diffs for code generation and chat history tracking. Implementing Myers diff or similar algorithms in Rust avoids heavy memory allocations on the Node.js heap.

---

## ## Conclusion

KesherAI should remain on Electron to avoid high migration friction regarding native modules like `node-pty` and Fastify server encapsulation [1]. `llama.cpp` should remain the sole inference engine, as alternative Rust engines do not outpace its quantization flexibility or hardware integration on an RTX 3090. Finally, performance-critical bottlenecks (log searching, file indexing, and text diffing) should be targeted incrementally using `napi-rs` modules written in Rust [16, 17].
