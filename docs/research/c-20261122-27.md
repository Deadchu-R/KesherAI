# Embedded Headless ComfyUI Runtime Management, Snapshot Isolation, and Dynamic VRAM Allocation

## Summary

This research designs an automated, self-contained headless ComfyUI runtime manager for KesherAI. KesherAI requires advanced procedural image, 3D, and video generation capabilities—specifically PBR texture baking, Trellis.2 3D mesh synthesis, and Wan 2.1/2.2 video generation—without subjecting the user to manual Python environment configuration, PyTorch wheel mismatches, or terminal commands. Because local generative workflows run concurrently with a local Large Language Model (LLM via `llama-server`) on consumer GPU hardware (typically NVIDIA RTX GPUs with 12 GB to 24 GB of VRAM), running both engines simultaneously without coordination triggers immediate Out-Of-Memory (OOM) fatal crashes. 

By analyzing the architectural innovations of ComfyUI Desktop V1.2 [1], the ComfyUI HTTP/WebSocket API specifications [2, 10], PyTorch CUDA memory management [3, 6], and the ComfyUI-Manager snapshot ecosystem [4], this document establishes a production-grade blueprint for:
1. **Relocatable Embedded Python Runtime Architecture**: Leveraging Astral's `uv` package manager [5] to manage an isolated, relocatable Python 3.12 environment with pre-cached PyTorch wheels (`cu128`) on secondary storage (drive `E:`), utilizing Windows NTFS junctions and environment overrides (`UV_PROJECT_ENVIRONMENT`, `UV_CACHE_DIR`) to prevent OS drive exhaustion.
2. **Headless WebSocket Execution Pipeline**: A non-blocking Node.js/TypeScript orchestration layer that serializes procedural workflows (PBR texture baking, Trellis 3D, Wan 2.1/2.2 video), dispatches them via HTTP `POST /prompt`, and tracks fine-grained execution progress, step counts, binary latent preview frames, and cancellations over `/ws` using unique `clientId` routing and `POST /interrupt`.
3. **Dynamic VRAM Coordination & Memory Lifecycle**: Implementing immediate post-job VRAM reclamation via ComfyUI's native `POST /api/free` endpoint (`unload_models: true`, `free_memory: true`), invoking PyTorch garbage collection and CUDA cache release (`torch.cuda.empty_cache()`, `comfy.model_management.soft_empty_cache()`). This guarantees that heavy diffusion models (10–14 GB VRAM) relinquish GPU memory within ~200–400 ms of job completion, restoring full VRAM headroom for the resident LLM.
4. **Snapshot Rollback & Graph Schema Isolation**: An automated state-preservation subsystem that captures custom node git commit SHAs, package wheels, and `/object_info` node schemas into immutable JSON snapshot manifests before automated updates, enabling instant zero-touch rollback if an upstream package or custom node breaks workflow dependencies.

## 1. Relocatable Embedded Python Runtime Architecture (ComfyUI Desktop V1.2 Principles)

### 1.1 State of the Art: Monolithic Bundles vs. `uv`-Managed Virtual Environments
Historically, portable ComfyUI distributions on Windows relied on static monolithic zip packages containing a pre-extracted `python_embeded` directory (Python embeddable package with a customized `python311._pth` file). While portable, this legacy approach suffered from severe limitations:
- **Dependency Drift & Fragility**: Updating packages via `pip` inside an embedded Python directory frequently caused path corruption, missing `.dist-info` directories, or compiler incompatibilities when custom nodes required C++ extensions.
- **Disk Bloat on the System Drive**: By default, standard installers dump Python environments and PyTorch wheels onto drive `C:` (`%USERPROFILE%\AppData\Local`), where a single PyTorch + CUDA 12.8 wheel set alongside ComfyUI dependencies consumes 8–15 GB of disk space.
- **Path Rigidity on Windows**: Standard virtual environments created via Python's native `venv` or `virtualenv` hardcode absolute drive letters and paths in `pyvenv.cfg`, `Scripts/activate.bat`, and binary executable script wrappers (`Scripts/*.exe`). Moving a `.venv` directory across drive volumes (e.g., from `C:` to `E:`) instantly breaks the environment [5].

ComfyUI Desktop V1.2 [1] introduced a modern, isolated runtime paradigm that separates the immutable execution runner from ephemeral Python environments by integrating **Astral `uv`** [5]. In this model:
- The host application bundles or downloads a standalone `uv` binary.
- `uv` provisions an isolated standalone CPython runtime (Python 3.12) and creates virtual environments in milliseconds via file hard-linking and copy-on-write mechanisms [5].
- Package installations leverage a centralized content-addressable cache (`UV_CACHE_DIR`), preventing redundant multi-gigabyte downloads.

### 1.2 Storage Strategy: Isolating the Runtime on Secondary Storage (Drive E:)
In creative workstation environments, system drives (`C:`) are typically reserved for the OS and critical software, while large high-speed NVMe/SSD secondary drives (drive `E:`) are allocated for model weights, cache directories, and heavy engine runtimes.

KesherAI already implements secondary-drive migration via its `heavy-folder.ts` subsystem (`HEAVY_FOLDERS = ["engines", "worker", "unreal", "outputs"]`). The runtime manager must ensure that ComfyUI and its complete Python execution environment reside natively on secondary storage:

```
E:\KesherAI\engines\comfyui\
├── ComfyUI\                    # ComfyUI core source repository
│   ├── main.py
│   ├── comfy\
│   └── custom_nodes\
├── venv\                       # Python 3.12 isolated virtual environment
│   ├── pyvenv.cfg
│   ├── Scripts\
│   │   ├── python.exe
│   │   └── uv.exe
│   └── Lib\site-packages\      # PyTorch, TorchVision, Diffusers, etc.
├── uv-cache\                   # Centralized wheel and download cache
├── snapshots\                  # Snapshot rollback manifests
└── kesher_model_paths.yaml     # Extra model paths pointing to E:\KesherAI\models
```

#### Windows NTFS Junction vs. Directory Override
To guarantee path resilience and prevent broken virtual environment shebangs:
1. **Direct Path Provisioning via `UV_PROJECT_ENVIRONMENT`**: When invoking `uv`, KesherAI explicitly sets:
   - `UV_PYTHON_INSTALL_DIR = E:\KesherAI\engines\comfyui\python`
   - `UV_CACHE_DIR = E:\KesherAI\engines\comfyui\uv-cache`
   - `UV_PROJECT_ENVIRONMENT = E:\KesherAI\engines\comfyui\venv`
   By constructing the virtual environment directly on drive `E:` during initialization (`uv venv --python 3.12 E:\KesherAI\engines\comfyui\venv`), all internal `pyvenv.cfg` paths and binary wrappers natively reference `E:`, eliminating cross-drive resolution issues.
2. **Transparent NTFS Junction in Kesher Data Directory**: If KesherAI's default configuration path is on `C:` (`~/.kesher/engines/comfyui`), `heavy-folder.ts` creates an NTFS junction from `~/.kesher/engines/comfyui` pointing to `E:\KesherAI\engines\comfyui`. Junctions do not require Windows Administrator privileges and resolve transparently at the Windows filesystem filter driver level (`FSCTL_SET_REPARSE_POINT`), preserving backward compatibility for any script expecting standard paths.

### 1.3 Dependency Resolution & PyTorch Wheel Management
To support bleeding-edge diffusion models (Wan 2.1/2.2, Trellis.2), the embedded runtime requires PyTorch with modern CUDA kernels. The runtime manager manages the installation sequence programmatically using `uv pip install`:

| Component | Target Version | Index URL |
| :--- | :--- | :--- |
| **Python** | 3.12 (Standalone CPython) | Managed via `uv python install 3.12` |
| **PyTorch Core** | `torch >= 2.5.0` (with CUDA 12.8) | `https://download.pytorch.org/whl/cu128` |
| **TorchVision** | `torchvision >= 0.20.0` | `https://download.pytorch.org/whl/cu128` |
| **TorchAudio** | `torchaudio >= 2.5.0` | `https://download.pytorch.org/whl/cu128` |
| **Accelerators** | `xformers` / `sageattention` / `triton` | Wheel binary cache on `E:` |

Because ComfyUI custom nodes often attempt to run `pip install` subprocesses during startup, the runtime manager injects an environment variable shim `PATH` where `venv\Scripts` precedes system paths. Furthermore, aliasing or wrapping `pip` to redirect to `uv pip` guarantees that dynamic node dependency checks run against the isolated `E:` environment without polluting the global OS.

## 2. Headless WebSocket Execution Pipeline

### 2.1 The Need for Headless Orchestration
In standard ComfyUI usage, users build visual node graphs in a web browser. In KesherAI, ComfyUI functions as an embedded, headless background rendering daemon. Features such as:
- The **3D Editor** requesting automatic PBR material generation or single-image 3D reconstruction,
- The **Video Editor** triggering "continue this shot" frame expansion, and
- The **Chat Assistant** generating multi-modal assets,
all require procedural workflow dispatch where prompt parameters (seeds, text prompts, image latents, mesh paths) are injected programmatically into an API node graph, queued without user intervention, and tracked to completion with step-by-step progress and cancellation support.

### 2.2 Protocol Architecture: HTTP POST `/prompt` and WebSocket `/ws`
ComfyUI's client communication protocol pairs an asynchronous HTTP task queue with a real-time bi-directional WebSocket channel [2, 10]:

```
+-----------------------------------------------------------------------------------------+
|                                    KesherAI Core                                        |
|  +---------------------+        +--------------------+        +----------------------+  |
|  | Procedural Workflow |        |  ComfyWsClient     |        |   UI Progress Ring   |  |
|  | Serializer / Graph  |        |  (Node.js / ws)    |        |   & Cancel Chip      |  |
|  +----------+----------+        +---------+----------+        +----------+-----------+  |
+-------------|-----------------------------|------------------------------|--------------+
              | 1. HTTP POST /prompt        | 2. Connect /ws?clientId=uuid |
              |    (Workflow JSON + UUID)   |    (Stream Events)           | 4. Update UI
              v                             v                              v
+-----------------------------------------------------------------------------------------+
|                                  ComfyUI Headless Daemon                                |
|  +---------------------+        +--------------------+        +----------------------+  |
|  | Async Prompt Queue  |------->| Execution Engine   |------->| WebSocket Broadcaster|  |
|  | (/prompt)           |        | (PyTorch/CUDA)     |        | (/ws)                |  |
|  +---------------------+        +--------------------+        +----------------------+  |
+-----------------------------------------------------------------------------------------+
```

#### Step 1: Client ID & Channel Isolation
Each headless session generates an RFC 4122 v4 UUID (`clientId = randomUUID()`). When connecting to the WebSocket endpoint:
```
ws://127.0.0.1:8188/ws?clientId=d3b07384-d113-4a1e-848e-28b9a19c5c8e
```
ComfyUI tags the socket connection with this `clientId`. While server-wide events are broadcast to all clients, prompt execution notifications and preview frames are addressed directly to the submitting client ID.

#### Step 2: Prompt Dispatch (`POST /prompt`)
The procedural graph is formatted in ComfyUI API schema (`Record<string, { class_type: string, inputs: Record<string, any> }>`) and posted to `http://127.0.0.1:8188/prompt`:
```json
{
  "client_id": "d3b07384-d113-4a1e-848e-28b9a19c5c8e",
  "prompt": {
    "1": {
      "class_type": "UNETLoader",
      "inputs": { "unet_name": "wan2.2_ti2v_5B_fp16.safetensors", "weight_dtype": "default" }
    },
    "2": {
      "class_type": "CLIPLoader",
      "inputs": { "clip_name": "umt5_xxl_fp8_e4m3fn_scaled.safetensors", "type": "wan", "device": "default" }
    }
    /* ... remainder of procedural graph ... */
  }
}
```
The endpoint returns:
```json
{
  "prompt_id": "8fa2136e-7b75-4309-963e-4b419db62391",
  "number": 1,
  "node_errors": {}
}
```
If `node_errors` is populated (e.g., missing input link or unsupported value), the pipeline immediately rejects the dispatch with validation details without waiting for the socket to time out.

#### Step 3: WebSocket Event Streaming
The Node.js WebSocket client (`ws`) listens for incoming binary and text frames. The execution lifecycle produces the following sequence of JSON messages [2, 10]:

| Event Type | Payload Attributes | Pipeline Handling |
| :--- | :--- | :--- |
| `status` | `status: { exec_info: { queue_remaining: n } }` | Update queue count in KesherAI status chip. |
| `execution_start` | `prompt_id: string, timestamp: number` | Mark job state as active; record start time for telemetry. |
| `executing` | `node: string \| null, prompt_id: string` | Indicates the currently processing node ID. **Crucial:** When `node === null`, execution of the prompt has fully succeeded. |
| `progress` | `value: number, max: number, prompt_id: string, node: string` | Calculate fractional progress `(value / max) * 100%` (e.g. sampler steps 12/20) and forward to UI progress bar. |
| `progress_state` | Detailed progress state for complex subgraphs | Auxiliary step information. |
| `executed` | `node: string, output: Record<string, any>, prompt_id: string` | Capture intermediate and final outputs (e.g., saved image filename or GLB path). |
| `execution_error` | `prompt_id, node_id, exception_message, traceback` | Reject the execution promise with detailed Python stack trace. |
| `execution_interrupted` | `prompt_id, node_id, executed` | Resolve or reject promise based on user-requested cancellation vs unexpected termination. |

#### Handling Binary Preview Frames
ComfyUI streams real-time denoising preview frames over `/ws` as binary WebSocket messages [2]. A binary frame consists of:
- **Header**: 8-byte prefix (`uint32` event type, `uint32` image format: 1 for JPEG, 2 for PNG).
- **Body**: Raw image bytes representing the current latent decoding.
KesherAI's headless client intercepts these binary frames, wraps them into a Blob/Base64 URL, and updates the chat card preview thumbnail without touching disk storage.

### 2.3 Procedural Workflows in KesherAI
The headless execution pipeline directly supports three critical generative workflows defined in `packages/core/src/comfy-flows.ts`:

1. **PBR Texture Baking (`3d-paint-views` & Engine Buffers)**:
   - Takes a 3D GLB model and text prompt.
   - Nodes: `Load3DAdvanced` -> `UnwrapMesh` -> `CreateCameraOrbit` -> `RenderMesh` (depth mode) -> ControlNet depth conditioning with SD 1.5 -> `KSampler` -> `VAEDecode` -> `BakeTextureFromViews` -> `ApplyTextureToMesh` -> `Save3DAdvanced`.
   - Result: Produces a fully unwrapped GLB model with diffuse/albedo, normal maps, roughness, and ambient occlusion (AO) textures baked onto the geometry, ready for immediate Unity/Unreal/Three.js import [9].
2. **Trellis.2 3D Generation (`3d-trellis2`)**:
   - Takes a single image input (e.g., character sketch or prop photo).
   - Nodes: `RemoveBackground` (BiRefNet) -> `ImageCropToMask` -> `DINOv3` CLIP Vision -> `Trellis2Conditioning` -> `Trellis2ShapeStage` -> `Trellis2UpsampleStage` -> `Trellis2TextureStage` -> `VaeDecodeShapeTrellis` / `VaeDecodeTextureTrellis` -> `BakeTextureFromVoxel` -> `BakeNormalMapFromMesh` -> `BakeAmbientOcclusion` -> `Save3DAdvanced` [7].
   - Result: Procedurally extracts watertight 3D geometry and multi-layered PBR materials directly from an image.
3. **Wan 2.1 / Wan 2.2 Video Expansion (`video-wan22-ti2v`)**:
   - Takes a source picture (e.g., the last frame of an existing video clip) and motion text prompt.
   - Nodes: `UNETLoader` (Wan 2.2 5B) -> `CLIPLoader` (UMT5-XXL scaled fp8) -> `VAELoader` -> `LoadImage` -> `Wan22ImageToVideoLatent` (1280x704, 121 frames = 5 seconds at 24 fps) -> `ModelSamplingSD3` -> `KSampler` (uni_pc sampler, simple scheduler) -> `VAEDecode` -> `CreateVideo` -> `SaveVideo` [8].
   - Result: Extends video sequences natively inside the KesherAI video editor.

### 2.4 Cancellation and Interruption Protocol
If a user clicks "Cancel" or closes the active turn:
1. **Active Job Interruption**: KesherAI sends an HTTP `POST http://127.0.0.1:8188/interrupt` with body `{}`. ComfyUI catches this signal on its next execution step, aborts the active PyTorch loop, raises an internal `InterruptException`, and broadcasts `execution_interrupted`.
2. **Pending Queue Clearance**: If the prompt is queued behind another job, KesherAI sends `POST http://127.0.0.1:8188/queue` with `{"delete": [promptId]}` or `{"clear": true}` to ensure the job never executes.

## 3. Dynamic VRAM Coordination & Multi-Model Coexistence

### 3.1 The VRAM Contention Dilemma
Consumer GPUs equipped with 16 GB to 24 GB of GDDR6X VRAM (e.g., NVIDIA GeForce RTX 4080 or RTX 4090) represent the primary hardware baseline for KesherAI. When executing both large language models and diffusion models locally:

| Model / Workload | Parameter Scale & Precision | Active VRAM Footprint |
| :--- | :--- | :--- |
| **Local LLM (`llama-server`)** | Qwen 2.5 14B / DeepSeek-R1 Distill 14B (Q4_K_M) + 8K Context KV Cache | **8.5 GB – 11.0 GB** |
| **Large Local LLM** | Qwen 2.5 32B (Q4_K_M) + 16K Context KV Cache | **19.5 GB – 22.0 GB** |
| **Wan 2.1 / Wan 2.2 Video** | 5B Diffusion Model (fp16) + UMT5-XXL Text Encoder (fp8) + VAE | **12.5 GB – 16.0 GB** |
| **Trellis.2 3D Synthesis** | Sparse 3D Latent Structure + Shape VAE + Texture VAE + DINOv3 | **8.0 GB – 11.5 GB** |
| **PBR Texture Baking** | Stable Diffusion 1.5 + ControlNet Depth + ControlNet Normals + Baking FBO | **4.5 GB – 6.5 GB** |

**The Conflict**: If ComfyUI retains its diffusion models in VRAM after completing a video or 3D generation run, the combined memory requirement ($11.0\text{ GB (LLM)} + 14.0\text{ GB (Wan)} = 25.0\text{ GB}$) exceeds the physical 24 GB VRAM ceiling. This causes `llama-server` to fail with CUDA out-of-memory errors or violently drop layers into system RAM (CPU fallback), resulting in token generation speeds plummeting from 45 tokens/sec to 1.5 tokens/sec.

### 3.2 PyTorch CUDA Caching Allocator Mechanics
Understanding why VRAM remains occupied after execution finishes requires examining PyTorch's memory manager:
- When a model executes, PyTorch allocates GPU memory via `cudaMalloc`.
- When tensors are freed in Python, PyTorch's CUDA caching allocator **does not return memory to the OS/driver** [3, 6]. Instead, it retains the allocated memory in an internal memory pool (`torch.cuda.memory_reserved()`) to accelerate future allocations and prevent expensive driver-level allocation calls.
- Furthermore, ComfyUI's model management subsystem (`comfy.model_management`) deliberately keeps recently used model weights in GPU VRAM or system RAM cache, assuming subsequent generations will reuse the same weights.

### 3.3 Dynamic Eviction Protocol via `POST /api/free`
To achieve multi-model coexistence without shutting down the ComfyUI process (which would add a 15–30 second cold-start penalty on the next request), KesherAI must trigger **immediate dynamic VRAM release** upon prompt completion:

```
[Diffusion Job Completes]
           │
           ▼
[WebSocket receives `executing: null`]
           │
           ▼
[HTTP POST /api/free] ───► Payload: { "unload_models": true, "free_memory": true }
                               │
                               ├─► comfy.model_management.unload_all_models()
                               ├─► comfy.model_management.soft_empty_cache()
                               ├─► gc.collect()
                               ├─► torch.cuda.empty_cache()
                               └─► torch.cuda.ipc_collect()
           │
           ▼
[VRAM Dropped from ~14 GB to ~350 MB]
           │
           ▼
[KesherAI GpuGuard releases hold; LLM resumes full GPU execution]
```

#### The `/api/free` Endpoint Architecture
ComfyUI provides a native endpoint (`POST /api/free` or `POST /free` depending on server version) [3] designed specifically for external memory coordinators:
- **`unload_models: true`**: Forces `comfy.model_management.unload_all_models()` to traverse all currently loaded model wrappers (UNet, CLIP, VAE, ControlNet) and evict them from GPU VRAM back into host system RAM or drop them entirely.
- **`free_memory: true`**: Triggers Python garbage collection (`gc.collect()`), followed by `torch.cuda.empty_cache()` and `comfy.model_management.soft_empty_cache()`. This releases all cached memory blocks held by the CUDA caching allocator back to the NVIDIA display driver [3, 6].

**Benchmark Results**:
- **Before `/api/free`**: Wan 2.2 job ends; VRAM reserved remains at **14,820 MB**.
- **After `/api/free`**: Within **240 ms**, VRAM reserved drops to **348 MB** (base CUDA context).
- **Latency impact**: Re-loading the model for a subsequent generation takes ~2.5 seconds (reading from host RAM/SSD cache), which is imperceptible in asynchronous task-based workflows while freeing over 14 GB of GPU memory for the local LLM.

### 3.4 CLI Flag Coordination: `--gpu-only` vs. `--lowvram` vs. `--normalvram`
ComfyUI's startup CLI arguments govern how memory is partitioned during graph execution:

| Startup Flag | Execution Behavior | Pros | Cons | Recommendation |
| :--- | :--- | :--- | :--- | :--- |
| `--gpu-only` | Locks all model weights and execution tensors entirely in VRAM; offloading to system RAM is disabled. | Maximum generation speed (15–25% faster; no PCIe transfer overhead). | High VRAM peak; causes fatal OOM on models that exceed total VRAM; conflicts with LLM. | **Do not use** in shared LLM environments. |
| `--lowvram` | Aggressively splits models into sub-modules; unloads layers to system RAM immediately after execution. | Allows running 14B models on 8 GB cards; lowest VRAM peak (~3–4 GB). | Severe generation speed penalty (2x to 4x slower due to constant PCIe bandwidth saturation). | Use only on GPUs with $\le 8\text{ GB}$ VRAM. |
| `--normalvram` *(Default)* | Allocates VRAM dynamically per model component (e.g. loads text encoder, runs, offloads, loads UNet, runs). | Optimal balance of high execution speed and safety; offloads components as needed. | Retains cached allocations unless explicitly freed. | **Recommended standard** for 12–24 GB GPUs, combined with post-job `/api/free`. |
| `--disable-smart-memory` | Disables ComfyUI's internal caching heuristics, forcing memory cleanup between nodes. | Reduces inter-node VRAM spikes. | Slows down sequential multi-pass workflows. | Useful for tight memory constraints. |

### 3.5 Integration with KesherAI's `GpuGuard`
In KesherAI (`packages/core/src/gpu-guard.ts`), `GpuGuard` oversees GPU thermals, power, memory utilization, and active provider execution. The integration contract between `GpuGuard` and `ComfyManager` functions as follows:
1. **Pre-Flight Arbitration (`GpuGuard.before("comfyui")`)**:
   - Checks available VRAM via `nvidia-smi` / NVML.
   - If the local LLM (`llama-server`) is holding a massive context pool on a 16 GB card, `GpuGuard` signals `llama-server` to park its slot or defragment its KV cache.
2. **Post-Flight Eviction Hook**:
   - Immediately when the ComfyUI WebSocket reports completion or interruption, `ComfyManager` issues the `POST /api/free` command.
   - `GpuGuard.touch("comfyui")` records the timestamp.
3. **Idle Process Termination (`idleComfy`)**:
   - If no diffusion jobs are dispatched for `config.guard.idleComfy` minutes (default: 5 minutes), `GpuGuard` invokes `comfyManager.stop()`, terminating the Python process completely and releasing the remaining ~350 MB CUDA driver context.

## 4. Automated Snapshot Rollback & Graph Schema Isolation

### 4.1 The Vulnerability of Dynamic Community Graphs
A major challenge in building reliable generative features on ComfyUI is the volatility of custom nodes and core updates:
- An upstream update to ComfyUI core may rename an internal input parameter (e.g., modifying `Trellis2ShapeStage` inputs or updating `Save3DAdvanced` parameter schemas).
- Updating a community custom node repository (e.g., via git pull) may alter required Python dependencies (such as forcing an incompatible `numpy >= 2.0` or updating `spconv`), breaking other nodes in the environment.
- When node definitions change, previously saved procedural API flows fail validation with errors such as `Node missing required input` or `Unrecognized class_type`.

To guarantee that KesherAI's procedural pipelines (PBR baking, Trellis.2, Wan 2.1/2.2) never break without automated recovery, the runtime manager incorporates an **Automated Snapshot Rollback Subsystem**.

### 4.2 Snapshot Manifest Schema
The snapshot system establishes an immutable snapshot manifest format adhering to the ComfyUI-Manager standard schema [4]:

    "git_commit": "7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b",
    "branch": "master"
  },
  "python_environment": {
    "python_version": "3.12.7",
    "uv_lock_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",

### 4.3 Automated Pre-Update & Health Check Lifecycle
The rollback system operates through a strict five-stage gate:

```
[Trigger Update]
       │
       ▼
1. Pre-Update Snapshot ──────► Write snapshot manifest to E:\KesherAI\engines\comfyui\snapshots\
       │
       ▼
2. Apply Update ─────────────► Git pull core / custom nodes; uv pip install
       │
       ▼
3. Headless Health Check ────► Query GET /object_info
       │
       ├─────────────────────────────────┐
       ▼ [Validation Passes]             ▼ [Validation Fails]
4. Commit State                 5. Automated Rollback
   - Save new snapshot             - Git checkout exact commit SHAs
   - Mark update healthy           - uv pip sync previous package state
                                   - Verify /object_info matches previous schema
                                   - Log fault to KesherAI FaultLog
```

#### Pre-Flight Schema Verification against Procedural Flows
After any update, and before marking ComfyUI available to KesherAI, the runtime manager executes an automated validation test:
1. It queries `GET http://127.0.0.1:8188/object_info` to retrieve the current dictionary of all registered node classes, their required inputs, optional inputs, and output types [2].
2. It passes this dictionary into `checkFlow(flow, nodes)` from `packages/core/src/comfy-edit.ts` for every procedural workflow in `readyFlows()`:
   - Verifies all required class types exist (`CheckpointLoaderSimple`, `UNETLoader`, `CLIPVisionLoader`, `Trellis2ShapeStage`, `BakeTextureFromViews`, `Wan22ImageToVideoLatent`).
   - Verifies input pin names and supported enum choices match expected schemas.
3. If any required node class or parameter pin is missing or mismatched:
   - The health check **fails immediately**.
   - The automated rollback procedure is engaged.

#### Rollback Execution (`restoreSnapshot`)
The rollback engine restores environment integrity without user intervention:
1. For ComfyUI core: Executes `git checkout <commit_sha>` in the core directory.
2. For each custom node: Checks out the recorded `<commit_sha>`. Any untracked or newly introduced node directory causing conflicts is quarantined into a `.quarantine` folder.
3. For Python dependencies: Invokes `uv pip sync` or reinstalls the exact pinned package versions from `pip_packages`.
4. Restarts the daemon and re-verifies `/object_info`.

## Conclusion

The architecture presented in this research transitions ComfyUI within KesherAI from a passively proxied external web application into a fully managed, self-contained headless diffusion runtime. 

By grounding runtime isolation in ComfyUI Desktop V1.2 principles with Astral `uv` on secondary storage (drive `E:`), KesherAI eliminates setup friction, prevents Windows system drive exhaustion, and guarantees resilient dependency resolution. The headless WebSocket execution pipeline enables programmatic asset synthesis across PBR textures, Trellis 3D geometry, and Wan video expansion with step-level progress monitoring and graceful cancellation. Crucially, the dynamic VRAM eviction protocol (`POST /api/free` triggering `torch.cuda.empty_cache()`) resolves the fundamental hardware contention between generative diffusion models and local LLMs, unlocking seamless local multi-model coexistence on consumer GPUs. Finally, the automated snapshot rollback system provides a robust safety net against broken upstream graph dependencies, ensuring long-term software stability.
