# Live Co-Developer Overlay: Visible Computer Control, Engine-Native Hit-Testing, and Low-Footprint Dual-GPU Vision

## Summary

This research designs an end-to-end architecture for KesherAI's **Live Co-Developer Overlay**—a non-intrusive, hardware-accelerated desktop heads-up display (HUD) that delivers visible computer control, precise "point-to-confirm" object validation, and proactive, context-aware suggestions across desktop applications, creative suites, and game engines (Unity Editor, Unreal Engine 5, Blender).

While frontier agent systems (Anthropic Claude, OpenAI Operator, Google Project Mariner) have validated the necessity of visible actuation cues (orange borders, synthetic cursors, step captions, takeover states) [1, 2, 4], and coding environments (Cursor, GitHub Copilot) have proved the ergonomic value of proactive next-action completions [9, 10], no existing solution combines real-time transparent overlays, proactive visual assistance, and deep 3D game-engine hit-testing. Existing game-engine assistants (such as the Unity AI Assistant and Unreal Engine MCP plugins) remain confined to docked editor sidebars and cannot interact visually across the operating system [13, 15]. Conversely, desktop computer-use agents rely strictly on raw screenshot pixel inference, causing high latency (1.5–5.0 s), high GPU consumption, and frequent spatial misses in complex 3D viewports [2, 7].

KesherAI can become the first system to unify these capabilities through a four-pillar design:
1. **Universal Click-Through HUD:** A frameless, transparent layered window (`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE`) managed via Electron or DirectComposition that renders an orange execution boundary, a smooth interpolated model cursor, step-caption badges, and interactive popups without stealing focus or intercepting user clicks [19, 20].
2. **Dual-Path Point-to-Confirm Anchoring:** Prioritizes exact engine-native hit-testing over noisy vision models. When hovering over 3D actors, scene hierarchies, or node graphs in Unity or Unreal, KesherAI's editor bridges calculate the exact screen coordinates via `Camera.WorldToScreenPoint` or `FSceneView::WorldToPixel`, anchoring "Is this the object you meant?" speech bubbles with 100% geometric precision and zero inference latency. Windows UI Automation (UIA) handles standard desktop widgets, reserving local Vision-Language Models (VLMs) strictly as a fallback for uninstrumented creative canvases [13, 14, 17].
3. **Zero-Overhead Proactive Engine:** A passive watcher loop driven by DirectX Graphics Infrastructure (DXGI) Desktop Duplication (`IDXGIOutputDuplication`) that monitors hardware dirty rects and user input pauses (>1.5 s debounce) [22, 23]. It expends 0% GPU/CPU cycles when the screen is static, triggering lightweight contextual evaluation only when meaningful visual or editor state transitions occur [21, 24].
4. **Dual-GPU Isolation Architecture:** Complete workload isolation for workstations with two graphics cards (and single-GPU degradation paths). The primary GPU (GPU 0) remains dedicated to host workflows (Unreal Engine rendering, shader compilation, primary LLM chat), while the secondary GPU (GPU 1) is pinned via DirectML adapter enumeration (`device_id: 1`), CUDA device masking (`CUDA_VISIBLE_DEVICES=1`), and Windows Graphics Preferences to run the overlay compositing and small local vision models (Florence-2 / Qwen2.5-VL-3B / UI-TARS-1.5-7B), guaranteeing zero frame drops or viewport stutter for the developer [25, 26, 27].

### 1.1 Anthropic Claude Computer Use & Claude for Chrome
Anthropic introduced desktop computer use with the Claude 3.5 Sonnet release (October 2024), establishing the foundational visual syntax for modern autonomous computer agents [1]:
* **The Orange Perimeter Frame:** When Claude takes control of an execution environment (such as an isolated Docker container, virtual machine, or local desktop), the active workspace is bordered with a distinctive orange frame (typically 3–4 px in width with a subtle glow). This provides an unmistakable visual boundary indicating that mouse and keyboard actuation is currently driven by an automated model policy rather than the human user [1, 2].
* **Synthetic Cursor Rendering:** Rather than instantly jumping mouse coordinates, the execution host tracks the agent's target coordinates `(x, y)` and renders an artificial cursor (often rendered in contrasting red/orange or with a trailing motion vector) that moves smoothly to the destination before executing click, double-click, or drag events [1].
* **Step Captions and Action Badging:** Each action is preceded by an explanatory natural-language step caption (e.g., `"Clicking on the 'Build' dropdown menu"`, `"Typing command in terminal"`) displayed on a floating status badge [1]. In desktop client implementations and companion MCP tools (such as *ClickRelay*), brief capture flashes illuminate the display during screenshot capture passes [2].
* **Architecture and Limitations:** Claude’s computer use operates strictly via remote API loops. The host captures a PNG screenshot, downscales it to conform to API token budgets (long edge constrained to 1568 px in Sonnet 3.5 or up to 2576 px in Sonnet 3.7 / Opus 4.7), sends it over HTTPS, and awaits the model's coordinate output [1]. This roundtrip introduces 1.5–4.0 s of latency per action, consumes ~4,500 input tokens per step, and cannot provide real-time proactive suggestions or sub-100 ms confirmations [1, 2].

### 1.2 OpenAI Operator and ChatGPT Agent
OpenAI’s Operator (launched December 2024 / January 2025) and its integrated ChatGPT browser agent apply computer-use capabilities within cloud-hosted virtual browser containers [3]:
* **Framing and Cursor Dynamics:** Operator displays a live WebRTC or Canvas video stream of the remote browser session. A distinct colored boundary (blue when idle, shifting to red/orange during active actuation) encloses the viewport. The agent’s synthetic pointer glides visibly across DOM elements and interactive canvas controls [3, 4].
* **Takeover Mechanics:** A persistent `"Take Over"` button allows the user to immediately interrupt the agent and take direct manual control of the mouse and keyboard [3]. If Operator encounters an insurmountable roadblock, an authentication portal, or a CAPTCHA challenge, it voluntarily yields control and prompts the user to complete the step [3, 4]. During user takeover, automated screenshot logging and DOM event capture are temporarily suspended to protect sensitive inputs [3].
* **Confirmation Thresholds & Statistics:** Operator incorporates a trained safety gate requiring human confirmation before executing irreversible or high-stakes actions [4]. Empirical evaluations published by OpenAI document confirmation recall rates of:
  * **100%** on financial transactions and money transfers [4].
  * **99.9%** on high-stakes communications and permission adjustments [4].
  * **91.0%** overall across general state-changing web actions [4].

### 1.3 Google Project Mariner & Gemini in Chrome Auto-Browse
Demonstrated in December 2024 and integrated into Chrome browser preview channels throughout 2025, Google’s Project Mariner established key architectural patterns for browser agent safety and UI feedback [5]:
* **Visual Isolation:** The browser tab under agent control displays a persistent agent icon in the tab strip, accompanied by an origin-gated colored border around the viewport. A structured side drawer displays the execution plan alongside live step-by-step progress cards [5].
* **User Alignment Critic (UAC):** Google’s architecture decouples planning from safety verification by introducing an independent **User Alignment Critic** model [5, 6]. While the primary Gemini model parses untrusted webpage DOM trees and screenshots, the critic inspects *only high-level metadata* (the user’s original prompt, the proposed action verb, and the target element label) without exposure to raw page text [6]. This completely isolates the safety arbiter from indirect prompt injection attacks embedded in webpage copy [6].
* **Origin Sets:** A formal security perimeter restricts the agent's interaction scope to designated read-only or read-write domains, blocking unauthorized third-party redirects or background script calls [5, 6].

### 1.4 Microsoft Copilot Vision, Recall, and Windows Click to Do
Microsoft has embedded native screen perception directly into the Windows 11 operating system (2024–2026) [7, 8]:
* **Copilot Vision:** Built for Microsoft Edge and Windows desktop environments, Copilot Vision watches the active window in real time during continuous voice or text interactions [7]. When instructing a user on how to navigate a software application, Copilot Vision does not simply speak coordinates; it injects a real-time **pink/purple glowing highlight** directly around the target button, menu, or slider, guiding the user's attention visually [7, 8].
* **Click to Do:** Integrated with Windows Recall and Copilot+ PC architectures, Click to Do provides an interactive overlay accessible via a global modifier hotkey (e.g., `Win + Click`) [7]. The underlying subsystem analyzes the current screen frame using on-device neural processing units (NPUs) or DirectML, detects semantic entities (text blocks, image assets, recognized UI controls), and projects interactive bounding boxes that expose contextual actions (summarize, extract, visual search, erase objects) [7, 8].

### 1.5 ByteDance UI-TARS Desktop
The UI-TARS model family (Seed team, ByteDance, 2025) represents the state of the art in open-weights end-to-end GUI automation [2, 11]:
* **Unified Architecture:** Built upon Qwen2-VL and Qwen2.5-VL backbones (available in 2B, 7B, and 72B parameter variants), UI-TARS eliminates fragmented pipelines (disjoint OCR, object detection, and heuristic planning) in favor of a single unified VLM policy [11].
* **System-2 Reasoning ("Thoughts"):** Prior to emitting an action token, UI-TARS generates a structured reasoning trace (`Thought: ... Action: ...`), evaluating previous execution outcomes, validating whether the expected UI state materialized, and computing recovery plans [11, 12].
* **Unified Action Space and Grounding:** UI-TARS normalizes desktop, mobile, and web interactions into standard primitives: `click(x, y)`, `double_click(x, y)`, `right_click(x, y)`, `drag(x1, y1, x2, y2)`, `type(text)`, `press_key(combo)`, and `wait()`. Coordinates are predicted natively in a normalized 0–1000 coordinate grid (`rel1000`) or in downscaled patch-aligned pixel coordinates (`abs28`) [11, 12].
* **Performance Benchmarks:** On the rigorous OSWorld desktop evaluation benchmark, UI-TARS-7B achieves an execution success rate of **27.5%**, while the full UI-TARS-72B model reaches **42.5%** [2, 11]. On the ScreenSpot-Pro visual grounding benchmark, UI-TARS-7B achieves **49.6%** accuracy, outperforming generic vision models on complex GUI elements [2, 11].

## 2. Proactive Interaction Paradigms: From Text Editors to Desktop Co-Developers

### 2.1 Cursor Tab & GitHub Copilot Next Edit Suggestions (NES)
The ergonomic breakthrough of modern AI code editors (Cursor and GitHub Copilot) lies in transitioning from *reactive chat* to *proactive speculative completion* [9, 10]:
* **Trigger Conditions and Debouncing:** A predictive suggestion should never interrupt an active burst of human typing [9]. Cursor Tab and Copilot implement a dynamic debounce timer:
  * **Typing Burst:** While keypress intervals remain below 200 ms, suggestion generation is suppressed [9, 10].
  * **Natural Pause:** When typing ceases for **250–500 ms**, the system captures the recent edit history, cursor position, and surrounding buffer context, querying a low-latency speculative model [9, 10].
* **Ghost Overlays and Single-Key Acceptance:** Suggestions are presented in-place as non-modal, desaturated "ghost text" or inline diff decorations [9]. The cognitive friction of accepting a suggestion is minimized to a single keypress (`Tab`), while any subsequent typing or pressing `Esc` dismisses the prediction instantly without modal interruption [9, 10].
* **Next Edit Suggestions (NES):** In addition to completing the current line, advanced models predict the *subsequent edit location* in the project (e.g., updating a test file or interface declaration immediately after modifying a function signature), rendering a jump prompt [9, 10].

### 2.2 Continuous Passive Perception: Rewind/Limitless and Screenpipe
Continuous desktop awareness requires capturing and understanding screen activity without degrading system responsiveness [21, 24]:
* **Screenpipe Architecture:** Screenpipe is an open-source Rust framework for continuous 24/7 desktop audio and video capture [21]. On Windows, Screenpipe captures desktop frames at 1–2 frames per second (fps) using the Windows Graphics Capture API or DXGI Desktop Duplication [21]. It routes captured frames through an abstraction layer (`uniOCR`), querying the high-speed native Windows Media OCR API or Tesseract [21].
* **Rewind / Limitless Resource Constraints:** Continuous capture tools minimize system resource impact through:
  * **Hardware-Accelerated Compression:** Capturing frames directly into GPU surfaces and encoding them into low-bitrate H.264/HEVC video streams via NVENC or Intel QuickSync, consuming <1% CPU [24].
  * **Accessibility-Tree Priority:** Rather than running heavyweight OCR or vision models on every frame, Screenpipe reads text directly from operating system accessibility trees whenever possible, reserving OCR strictly for non-standard rendering surfaces (games, video players, remote desktops) [21].

### 2.3 Translating "Next Edit" to Visual Desktop Workflows
KesherAI extends the "Next Edit" paradigm from code text buffers to whole-desktop visual workflows:
1. **Activity-Gated Debounce:** The co-developer monitor captures user inputs via low-level Windows hooks (`WH_MOUSE_LL`, `WH_KEYBOARD_LL`). When the developer is actively dragging, clicking, or typing in Unreal, Unity, or Photoshop, the assistant remains passive.
2. **Idle Trigger Threshold:** When input activity pauses for **1.5 to 2.0 s**, and the screen state indicates an unfinished or newly placed element, the background co-developer engine activates.
3. **Non-Intrusive Speech Bubble:** Rather than opening an intrusive modal dialog or stealing keyboard focus, the overlay renders a subtle, translucent speech bubble adjacent to the relevant UI element or viewport object (e.g., `"Unassigned Normal Map in M_Character. Auto-link normal texture?"` with `[Accept (Tab)]` `[Dismiss (Esc)]`).

Relying on generic vision models to localize objects inside complex 3D viewports (such as the Unity SceneView or Unreal Engine Level Viewport) is fundamentally flawed: bounding box coordinates drift depending on camera zoom, perspective foreshortening, and anti-aliasing, while VLM inference incurs seconds of latency. Because KesherAI maintains dedicated in-editor bridge plugins, it can bypass vision models entirely, computing pixel-perfect 2D screen positions directly from engine scene data [13, 15].

### 3.1 Unity Editor Viewport Projection & UI Toolkit Inspection
The KesherAI Unity Bridge package (`com.kesherai.bridge`, located in `integrations/unity/`) interacts directly with `UnityEditor` APIs [13, 14]:
* **3D SceneView Object Projection:** To anchor an overlay speech bubble above an in-scene GameObject:
  ```csharp
  // 1. Locate the target object and extract its world bounds
  GameObject target = GameObject.Find("BP_DoorMesh");
  Vector3 worldCenter = target.GetComponent<Renderer>()?.bounds.center ?? target.transform.position;
  
  // 2. Project 3D world space into 2D SceneView camera viewport
  SceneView view = SceneView.lastActiveSceneView;
  Camera cam = view.camera;
  Vector3 screenPoint = cam.WorldToScreenPoint(worldCenter);
  
  // 3. Convert GUI coordinates to absolute OS screen pixels
  Vector2 sceneViewGuiPos = new Vector2(screenPoint.x, view.position.height - screenPoint.y);
  Vector2 absoluteScreenPixel = view.position.position + sceneViewGuiPos;
  ```
* **Hit-Testing under the Mouse:** When the model hovers its synthetic cursor over the SceneView, the bridge can execute native picking via `HandleUtility.PickGameObject(mousePosition, false)`, returning the exact GameObject identity under the pointer without visual ambiguity [14].
* **Visual Scripting & UI Toolkit Graph Coordinates:** For Visual Scripting graphs or UI Builder canvases, elements derive from `VisualElement`. The bridge reads `element.worldBound`, mapping local graph coordinates to editor window coordinates via `element.LocalToWorld()` and resolving to desktop pixels via `GUIUtility.GUIToScreenPoint()` [14].

### 3.2 Unreal Engine 5 Slate Viewport Projection
The KesherAI Unreal plugin (`KesherAIBridge`, located in `integrations/unreal/KesherAIBridge/`) utilizes Unreal Engine's C++ Slate and Editor subsystems [15, 16]:
* **3D Level Viewport Projection:**
  ```cpp
  // 1. Locate actor via Editor Actor Subsystem
  AActor* TargetActor = EditorActorSubsystem->GetActorReference(Path);
  FVector ActorOrigin, ActorBoxExtent;
  TargetActor->GetActorBounds(false, ActorOrigin, ActorBoxExtent);
  FVector TopCenter = ActorOrigin + FVector(0.0f, 0.0f, ActorBoxExtent.Z);
  
  // 2. Retrieve the active level editing viewport
  FLevelEditorModule& LevelEditor = FModuleManager::GetModuleChecked<FLevelEditorModule>("LevelEditor");
  TSharedPtr<ILevelViewport> ActiveViewport = LevelEditor.GetFirstActiveViewport();
  FSceneViewFamilyContext ViewFamily(FSceneViewFamily::ConstructionValues(
      ActiveViewport->GetViewportClient()->Viewport,
      ActiveViewport->GetViewportClient()->GetScene(),
      ActiveViewport->GetViewportClient()->EngineShowFlags));
  FSceneView* SceneView = ActiveViewport->GetViewportClient()->CalcSceneView(&ViewFamily);
  
  // 3. Project World to Viewport Pixel Coordinates
  FVector2D OutPixel;
  SceneView->WorldToPixel(TopCenter, OutPixel);
  
  // 4. Map Slate Local Viewport to Global Windows Desktop Pixel Space
  TSharedPtr<SWidget> ViewportWidget = ActiveViewport->GetWidget();
  FGeometry ViewportGeometry = ViewportWidget->GetTickSpaceGeometry();
  FVector2D AbsoluteDesktopCoords = ViewportGeometry.LocalToAbsolute(OutPixel);
  ```
* **Blueprint Node Graphs:** For Blueprint visual scripting graphs, each `UEdGraphNode` exposes integer graph coordinates `NodePosX` and `NodePosY` [16]. The active `SGraphEditor` Slate widget tracks pan offset and zoom factors (`GetViewOffset()`, `GetZoomAmount()`). The bridge transforms node graph bounds to absolute OS screen space in <1 ms, enabling point-to-confirm speech bubbles to frame individual Blueprint execution pins or math nodes effortlessly [15, 16].

### 3.3 Blender and Creative Tool Bridging
For creative software lacking a pre-installed C++ plugin (Blender, Adobe Photoshop, Substance Painter):
* **Blender Python IPC:** Blender exposes its full scene graph via `bpy.context`. A lightweight background Python script running on a local socket evaluates 3D view projections via `bpy_extras.view3d_utils.location_3d_to_region_2d()`, mapping active 3D coordinates to window-relative pixels.
* **Fallback without Scripting:** When tools provide neither a plugin bridge nor an accessibility tree (e.g., proprietary image editors), the system gracefully degrades to the local vision grounding pipeline (Florence-2 / Qwen2.5-VL) [17, 18].

## 4. Windows Overlay Architecture and Ultra-Low PC Footprint

### 4.1 Transparent Click-Through Windows: Electron vs Native Win32
Creating an overlay that renders visual frames and speech bubbles across the entire desktop without interfering with the user's active tools requires specific Windows Extended Window Styles [19, 20]:
* **Key Win32 Extended Window Styles:**
  * `WS_EX_LAYERED (0x00080000)`: Enables per-pixel alpha transparency and layered compositing [19].
  * `WS_EX_TRANSPARENT (0x00000020)`: Instructs the OS window manager that mouse click and hit-test messages must pass directly through this window to whatever window is positioned beneath it [19].
  * `WS_EX_NOACTIVATE (0x08000000)`: Prevents the overlay window from taking keyboard or mouse focus when displayed. Crucial for ensuring that typing in an active code editor or game viewport is never interrupted [19].
  * `WS_EX_TOPMOST (0x00000008)`: Pins the window above all normal desktop application windows [19].
  * `WS_EX_TOOLWINDOW (0x00000080)`: Prevents the overlay window from appearing in the Windows Alt+Tab application switcher or taskbar [19].
* **Desktop Window Manager (DWM) Blur and Glass:**
  Calling `DwmExtendFrameIntoClientArea(hwnd, &margins)` with margins `{-1, -1, -1, -1}` configures the Desktop Window Manager to treat the window surface as completely transparent glass, allowing DirectComposition or Chromium to paint translucent overlays smoothly [19].
* **Interactive Hit-Testing (Click-Through with Clickable Buttons):**
  If the entire overlay is set to `WS_EX_TRANSPARENT`, the user cannot click the "Yes" or "No" buttons inside a point-to-confirm speech bubble. Two technical solutions resolve this:
  1. **Win32 `WM_NCHITTEST` Routing:** In a native C++ / DirectComposition window, the window procedure intercepts `WM_NCHITTEST`. If the mouse coordinates fall within the bounding rect of an active interactive bubble or button, it returns `HTCLIENT` (allowing mouse events). For all other regions of the screen, it returns `HTTRANSPARENT` (-1), causing Windows to immediately forward the mouse message to the underlying window [19].
  2. **Electron `setIgnoreMouseEvents` Dynamic Forwarding:** In KesherAI's Electron desktop app (`apps/desktop`), the overlay window is created with `transparent: true, frame: false, alwaysOnTop: true`. By calling `win.setIgnoreMouseEvents(true, { forward: true })`, mouse move events continue to emit in Chromium without intercepting clicks [20]. When the cursor enters an interactive HTML element (`.interactive-bubble`), the renderer sends an IPC message to call `win.setIgnoreMouseEvents(false)`. When the mouse exits, it restores `setIgnoreMouseEvents(true, { forward: true })` [20].

### 4.2 Desktop Capture Performance: GDI vs DXGI vs Windows Graphics Capture
Continuous screen perception must not compete with Unreal Engine 5 or local LLMs for PCIe bus bandwidth or CPU cycles:

```
[ Traditional GDI CopyFromScreen ]
GPU Framebuffer (VRAM) ──(PCIe Readback: 30-80ms)──► CPU System RAM ──► Bitmap Processing
Result: Severe game stutter, 15-25% CPU usage, stalls GPU pipeline.

[ Modern DXGI Desktop Duplication / Windows Graphics Capture ]
GPU Framebuffer (VRAM) ──(Zero-Copy D3D11 Texture: 0.5-1.2ms)──► DirectML / CUDA Inference
Result: 0% CPU usage, zero PCIe bus saturation, zero viewport stutter.
```

* **GDI `CopyFromScreen` (BitBlt):** KesherAI's existing baseline implementation in `packages/core/src/computer.ts` relies on PowerShell invoking `Graphics.CopyFromScreen()` [2]. At 4K resolution (3840×2160), this forces a synchronous PCIe readback from GPU VRAM into CPU host memory, requiring **30 to 80 ms** per frame. In game engines, this locks the rendering pipeline, causing visible frame drops and audio hitching.
* **DXGI Desktop Duplication (`IDXGIOutputDuplication`):** Introduced in DirectX 11.1 [22]. Accesses the desktop compositor surface directly in GPU memory as an `ID3D11Texture2D` in **0.5 to 1.2 ms**. Frames never leave VRAM unless explicitly mapped, eliminating CPU overhead entirely [22, 23].
* **Windows Graphics Capture API (`Windows.Graphics.Capture`):** Supported on Windows 10 (1903+) and Windows 11 [8, 23]. Delivers hardware-accelerated Direct3D11 capture with two critical advantages:
  * Can capture *individual target windows* (e.g., only the Unreal Editor process) even when partially occluded or moved behind other windows [8].
  * Exposes `session.IsBorderRequired = false` (supported on Windows 10 build 20348 and Windows 11), disabling the default OS yellow recording border that would otherwise interfere with the visual presentation [8].

### 4.3 Zero-Cost Change Detection Pipeline
To achieve near-zero resource utilization when the screen is idle, KesherAI implements a multi-stage filtering pipeline [22, 23]:
1. **Hardware Dirty Rects (`GetFrameDirtyRects`):** When invoking `IDXGIOutputDuplication::AcquireNextFrame()`, the operating system populates a `DXGI_OUTDUPL_FRAME_INFO` descriptor [22]. If `AccumulatedFrames == 0` and `DirtyRectsBufferSize == 0`, the screen content is identical to the preceding frame. The capture thread immediately sleeps without performing any memory copies or image encoding, consuming **0.0% CPU and 0.0% GPU** [22, 23].
2. **Foreground Window Filter:** If dirty rects are detected, the system queries the active foreground window handle (`GetForegroundWindow()`). If changes occur solely in background windows (such as a clock ticking in the system tray or a background download bar), they are ignored unless the user has actively enabled multi-window monitoring.
3. **Perceptual Differencing (dHash / SIMD Downsampling):** When changes occur in the active workspace, the changed bounding box is downsampled via a fast compute shader to a 64×64 grayscale buffer. A perceptual difference hash (dHash) evaluates whether the change represents meaningful semantic content (an opened menu, a new node, a modified mesh) versus superficial noise (a blinking text caret or subpixel anti-aliasing shimmer) [21].
4. **Debounced Trigger:** Only after the visual change persists and human input ceases for >1.5 s does the system package the context for proactive analysis [9].

## 5. Small Local Vision Models: Footprint, Latency, and Precision

Running a continuous visual co-developer locally alongside heavy developer tools demands ultra-compact Vision-Language Models that respect stringent VRAM and latency constraints [17, 18, 28].

### 5.1 Model Taxonomy & Comparative Analysis
The local vision landscape offers distinct model classes optimized for edge perception, grounding, and reasoning:
* **Florence-2 (Microsoft):** Sequence-to-sequence encoder-decoder architecture based on a DaViT vision backbone and custom language decoder [17]. Operates via structured prefix tasks (`<OD>` for object detection, `<CAPTION_TO_PHRASE_GROUNDING>` for referring expression grounding, `<OCR>` for text extraction) [17]. It is one of the fastest vision models in existence, generating bounding boxes in 20–50 ms [17].
* **Moondream2 / Moondream3 (vikhyatk):** Purpose-built compact vision models (1.86B parameters) [18]. Designed specifically for fast spatial point estimation and edge execution, achieving sub-400 ms latency with under 1.5 GB VRAM utilization under FP16/INT4 [18].
* **SmolVLM (Hugging Face):** Available in 256M, 500M, and 2.2B parameter scales [28]. Highly efficient for small memory footprints, though its spatial coordinate grounding precision is lower than dedicated GUI agents [28].
* **Qwen2.5-VL 3B / 7B & Qwen3-VL 8B (Alibaba):** The premier open-weights multimodal series for UI understanding [2, 11]. Supports native dynamic resolution processing and outputs normalized coordinate tokens (`rel1000` or bounding boxes). The 3B variant offers an outstanding trade-off between semantic comprehension and memory footprint [2].
* **UI-TARS-1.5-7B (ByteDance):** Fine-tuned specifically for computer-use action trajectories and GUI element grounding [2, 11]. While highly accurate on desktop controls (ScreenSpot-Pro 49.6%), its 7B size requires ~7–8 GB VRAM in Q4_K_M quantization, making it suitable as a primary action model rather than a continuous passive monitor [2, 11].

### 5.2 Quantization & Memory Optimization
* **GGUF and AWQ Quantization:** 4-bit quantization (Q4_K_M in llama.cpp or AWQ in vLLM) compresses model weights by ~60% with less than 1.5% degradation in spatial grounding accuracy [2, 11].
* **Paged KV Caching:** Restricting the vision model's context window to 2048 or 4096 tokens and applying 8-bit KV caching caps attention memory overhead at under 250 MB VRAM.

## 6. Multi-GPU Pinning and Hardware Isolation on Windows

When developing in Unreal Engine 5 or compiling complex C++ code while running an active LLM, running a continuous vision loop on the same GPU risks introducing micro-stutters, dropping viewport frame rates below 60 fps, or triggering Out-Of-Memory (OOM) crashes. Architecting KesherAI to partition tasks across two GPUs provides complete isolation [25, 26, 27].

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                               WORKSTATION DUAL-GPU HARDWARE                            │
│                                                                                        │
│   PRIMARY GRAPHICS CARD (GPU 0)                   SECONDARY GRAPHICS CARD (GPU 1)      │
│   e.g., NVIDIA RTX 4090 / 3090 (24 GB)            e.g., NVIDIA RTX 3060 / 4060 (12 GB) │
│                                                                                        │
│   ┌───────────────────────────────────────┐       ┌──────────────────────────────────┐ │
│   │ • Unreal Engine 5 Viewport & Shaders  │       │ • llama.cpp Vision Slot          │ │
│   │ • Unity Editor 3D Rendering           │       │   (Florence-2 / Qwen2.5-VL 3B)   │ │
│   │ • Visual Studio / C++ Build Pipeline  │       │ • DirectML OCR & Downsampling    │ │
│   │ • Main Conversational LLM             │       │ • Transparent Overlay Compositor │ │
│   │ • Display Output (Monitors Connected) │       │ • Hardware Video Encoder (NVENC) │ │
│   └───────────────────────────────────────┘       └──────────────────────────────────┘ │
│                       ▲                                             ▲                  │
│                       │                                             │                  │
│                       └──────────── Cross-Adapter PCIe ─────────────┘                  │
│                                     Zero-Copy Texture Sharing                          │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 6.1 Workload Partitioning Scheme
* **GPU 0 (Primary Display & Production Card):** Connected to physical display monitors. Dedicated to high-demand host applications (Unreal Editor, Lumen/Nanite rendering, Unity Play mode, Blender cycles, IDE compilation) and the primary reasoning LLM [27].
* **GPU 1 (Secondary Coprocessor Card):** Headless (no physical monitors required). Dedicated entirely to KesherAI's background perception engine: hosting the local vision model in `llama.cpp` or ONNX Runtime, executing hardware frame diffing, and rendering overlay elements [25, 26].

### 6.2 Backend-Specific Device Selection
KesherAI enforces explicit GPU assignment across all supported execution backends:
1. **CUDA / PyTorch / llama-server:**
   * When launching the local vision server subprocess (`packages/core/src/vision-service.ts`), KesherAI injects the process-isolated environment variable:
     ```powershell
     $env:CUDA_VISIBLE_DEVICES = "1"
     ```
     Under this configuration, CUDA masks all other physical adapters, causing the child process to see GPU 1 as index `0` and preventing any memory allocation on GPU 0 [25].
   * In `llama.cpp` server arguments, device selection can also be passed directly via `--main-gpu 1` (`-mg 1`) with `--split-mode none` [2].
2. **DirectML / ONNX Runtime:**
   * DirectML maps adapter indices directly to DirectX Graphics Infrastructure (DXGI) enumeration order [25, 26].
   * In Python / Node.js native bindings:
     ```python
     import onnxruntime as ort
     providers = [('DmlExecutionProvider', {'device_id': 1})]
     session = ort.InferenceSession("model.onnx", providers=providers)
     ```
   * In C++ (`OrtSessionOptionsAppendExecutionProvider_DML`):
     ```cpp
     Ort::SessionOptions options;
     // deviceId 1 corresponds to the second adapter enumerated by IDXGIFactory::EnumAdapters
     OrtSessionOptionsAppendExecutionProvider_DML(options, 1);
     ```
3. **Vulkan:**
   * The Vulkan loader allows device filtering via `VK_LOADER_DEVICE_SELECT` or by iterating physical devices via `vkEnumeratePhysicalDevices()` and binding the `VkDevice` whose `VkPhysicalDeviceProperties.deviceID` matches the secondary adapter.

### 6.3 OS & Driver Level Isolation on Windows
* **Windows Graphics Preferences per Application:**
  Windows 10/11 allows assigning explicit GPU preferences for individual executables without modifying application code [26]. This configuration is stored in the Windows Registry under:
  ```
  HKEY_CURRENT_USER\Software\Microsoft\DirectX\UserGpuPreferences
  ```
  By writing `GpuPreference=2;` (or binding the explicit adapter LUID) to the entry for `kesher-vision-worker.exe`, the OS graphics scheduler automatically directs all D3D11/D3D12 device creation to GPU 1 [26].
* **Cross-Adapter Shared Surfaces:**
  Because the desktop display is physically driven by GPU 0, DXGI Desktop Duplication captures frames into surfaces resident on GPU 0 [22, 27]. Transferring captured frames to GPU 1 for model inference without touching CPU system RAM uses DirectX 12 Cross-Adapter Shared Surfaces:
  * GPU 0 creates a shared texture with `D3D12_RESOURCE_FLAG_ALLOW_CROSS_ADAPTER` in a `D3D12_HEAP_FLAG_SHARED_CROSS_ADAPTER` heap [27].
  * GPU 0 issues an NT handle via `IDXGIResource1::CreateSharedHandle()`.
  * GPU 1 opens the handle via `ID3D12Device::OpenSharedHandle()`, copying frame data directly across PCIe bus lines using GPU DMA engines synchronized by cross-adapter fences (`D3D12_FENCE_FLAG_SHARED_CROSS_ADAPTER`) [27]. CPU utilization remains at **0%**.

## Conclusion

The architecture presented in this research provides a complete, performant, and safe roadmap for KesherAI’s Live Co-Developer Overlay. By prioritizing engine-native RPC projections (via the existing Unity and Unreal bridge modules) and Windows UI Automation over brute-force vision models, KesherAI eliminates the latency, cost, and coordinate hallucination that plague existing computer-use agents. Pairing this semantic precision with a zero-copy DXGI change-detection pipeline, a non-intrusive click-through HUD, and explicit dual-GPU pinning ensures that the system runs smoothly alongside demanding game-development workflows.

### Open Questions for Future Implementation
* **DirectComposition vs Electron Multi-Window:** Evaluating whether the transparent overlay should run as an auxiliary BrowserWindow in `apps/desktop` using `setIgnoreMouseEvents(true, { forward: true })`, or whether a dedicated lightweight C++/DirectComposition sidecar executable yields lower background VRAM overhead (5 MB vs 80 MB).
* **Cross-Adapter Latency on PCIe 3.0 vs 4.0/5.0:** Measuring empirical DMA transfer latencies when streaming 4K capture surfaces from GPU 0 to GPU 1 across secondary motherboard PCIe slots running at x4 or x8 electrical bandwidth.
* **Proactive Suggestion False-Positive Suppression:** Tuning the heuristic threshold for proactive suggestions in game engines to prevent suggestion fatigue during creative artistic workflows.
