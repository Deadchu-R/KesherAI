# Research Report: Kaggle and Similar Free Notebooks as Cloud Workers for KesherAI

This research report evaluates whether free cloud notebook platforms (specifically Kaggle) can serve as remote cloud workers to run small coding tasks and local LLMs (`llama.cpp` with CUDA) for KesherAI. 

## Summary
Running a headless self-work node inside a free Kaggle notebook that connects outward to a private KesherAI hub is an appealing idea given the free hardware (e.g., 2x T4 GPUs with 32 GB VRAM). However, Kaggle's Acceptable Use Policy explicitly restricts turning sessions into long-running third-party API endpoints or server farms, and its interactive idle timeouts (20–60 minutes) and strict weekly quotas make it unreliable for persistent background workers. While alternative free tiers exist (Google Colab, Lightning AI, Hugging Face ZeroGPU, Modal), they impose similar or tighter restrictions. Therefore, using Kaggle as a persistent worker violates platform terms, though it remains viable for short, scheduled batch-training jobs.

## Kaggle Terms of Use, Acceptable Use Policy, and Compliance
Kaggle's Acceptable Use Policy and Terms of Use govern platform behavior [1, 2]. According to community interpretations and enforcement patterns, using a Kaggle notebook for personal experiments or batch inference is completely acceptable [6]. However, "turning the session into a public long-running API endpoint via tunnel (the setup in this thread) is what the Acceptable Use Policy flags as server farming / resource abuse" [6]. 

While Roee's proposed design uses an outbound connection (connecting *out* to his hub rather than hosting an inbound tunnel), maintaining a continuous, long-running worker daemon inside an interactive notebook violates the spirit and rules against persistent server hosting and server farming [3, 6]. Accounts engaging in persistent background server behaviors risk throttling, suspension, or bans.

## Limits, Sessions, and API Capabilities Today
Kaggle provides generous resources, but they come with strict operational boundaries:
* **Hardware Quotas:** Kaggle offers 2x NVIDIA Tesla T4 GPUs (the P100 was retired on September 15, 2026) [3]. The weekly GPU quota is approximately 30 hours, resetting weekly depending on demand [3].
* **Session and Idle Limits:** Maximum continuous interactive session length is 12 hours [3]. However, interactive sessions suffer from a strict idle timeout of 20 to 60 minutes if code is not actively running or edited [2, 3].
* **Execution Modes:** Long jobs can be managed via "Save & Run All" to execute end-to-end without an active browser tab [3]. Notebooks can also be scheduled to run daily, weekly, or monthly via the UI settings [3].
* **API and Secrets:** The Kaggle API and CLI (`kaggle kernels push`) allow automated script deployment [5]. A recent addition (`--no-run` / `QUICK_SAVE`) allows pushing notebook metadata and code without automatically triggering a full execution run [3]. Kaggle Secrets permit secure injection of API tokens without hardcoding credentials into scripts [3].

## Alternative Free Platforms
Several alternatives offer similar shapes with different limitations:
* **Google Colab (Free):** Offers sporadic T4 GPU access subject to strict, undisclosed usage quotas and shorter idle timeouts. Persistent background worker usage violates Google's Colab TOS.
* **Lightning AI Studios:** Provides free cloud studio environments with GPU options, but enforces strict idle termination and consumption limits.
* **Hugging Face ZeroGPU:** Excellent for running specific serverless GPU functions, but designed around short-lived function calls rather than persistent background workers.
* **Modal / Cloud Providers:** Offer free trial credits rather than indefinite free tiers, operating under strict pay-as-you-go commercial terms.

## KesherAI Cloud Worker Design & Architecture
To safely utilize ephemeral compute without violating terms or risking bans, a generic cloud worker design should pivot from a *persistent daemon* to an *ephemeral batch worker*:
* **Worker Runtime:** Written in a lightweight compiled language like **Go** or **Rust** to ensure fast startup times, minimal memory footprint, and seamless binary execution inside a Jupyter/Python wrapper [6].
* **Pairing and Task Scope:** The worker pulls small, non-sensitive coding tasks (strictly passing a leak guard to ensure zero private code exposure) from the KesherAI hub via secure outbound HTTPS/WSS [6].
* **Execution & Push:** Upon receiving a task, it spins up `llama.cpp` (CUDA-accelerated) locally, completes the coding/refactoring task, commits the work to an isolated git branch, reports progress back to the hub, and self-terminates.
* **Lifecycle Automation:** Because interactive sessions time out, auto-start/stop should rely on scheduled API triggers or batch-run scripts (`Save & Run All`) rather than maintaining an open background server [3]. Quota tracking must be monitored locally by logging GPU minute consumption against the 30-hour weekly limit [3].

## Conclusion and Next Steps
* **Verdict:** Not allowed for persistent, long-running worker nodes (violates AUP server-farming restrictions); not worth the risk of account bans for continuous operations [3, 6]. However, it is viable for scheduled batch workloads if kept short [3].
* **Recommended Design:** Implement an *ephemeral batch worker script* invoked via Kaggle's scheduled run features rather than a persistent background daemon.
* **First Steps:**
  1. Build a minimal Go/Rust worker binary that tests `llama.cpp` startup times and GGUF Q4 coding model token generation rates on a single T4 card.
  2. Test automated deployment via `kaggle kernels push` using the `--no-run` configuration and Kaggle Secrets [3].
  3. Implement strict leak-guard validation on the hub side before dispatching any tasks to remote free-tier compute nodes.
