# Local Autonomous Subagent Architecture and Git Worktree Isolation: Windows Concurrency, Streaming JSON Rollups, and Hunk-Level Merging

## Summary

This research delivers an end-to-end architectural blueprint for orchestrating local autonomous subagents within KesherAI. Operating on local developer workstations—specifically multi-core Windows environments equipped with local NVIDIA RTX GPUs running quantized GGUF models via `llama.cpp`—subagent execution demands a delicate balance between total filesystem isolation, strict memory/VRAM budgeting, and frictionless synchronization with the primary chat session [1, 3].

Frontier coding systems (Claude Code, Cursor, Codex, OpenCode) have demonstrated that decomposing complex tasks into focused, short-lived helper agents preserves context hygiene and prevents catastrophic regression [2, 6, 8]. However, implementing this pattern strictly on local hardware introduces four distinct engineering challenges:
1. **Windows Filesystem Lock Contention:** On Windows NTFS, aggressive background file indexers, lingering sub-processes, and current working directory (CWD) locks frequently trigger fatal `EPERM` and `EBUSY` errors when creating, pruning, or checking out Git worktrees [1, 9].
2. **Context Window Exhaustion:** Unlike cloud frontier models with 200k–1M token context windows, local models operate efficiently within 16k–32k token budgets. Passing full execution transcripts or verbose command outputs from subagents quickly overflows the parent's context, requiring a rigid 200–400 token structured rollup protocol [7, 8].
3. **Hardware & VRAM Starvation:** Running concurrent subagents without arbitration leads to llama.cpp slot contention, CUDA out-of-memory (OOM) faults, and system instability [3, 4].
4. **Merge Regressions:** Autonomous subagents working in parallel branches can easily introduce merge conflicts, silently overwrite adjacent developer edits, or introduce subtle regressions if branches are blindly merged into the host workspace [2, 5].

KesherAI resolves these bottlenecks by combining:
- A Windows-hardened worktree manager utilizing isolated `.kesher/worktrees/` directory structures, retry loops with jitter, and out-of-process CWD guards [1, 9].
- A Peg-native JSON Schema grammar protocol delivering streaming progress events and 200–400 token findings packs [7, 10].
- A deterministic slot-pinning concurrency arbiter mapping helper tasks to llama-server slots with KV cache partitioning and thermal/memory guarding via `HeavyGate` [3, 4].
- A per-hunk interactive diff review engine that decomposes subagent branch diffs into granular, relocatable patch blocks, allowing the lead agent or user to selectively approve, reject, or undo changes without git merge conflicts [5, 6].

### 1.1 Helper Roles and Capability Boundaries

To prevent unauthorized actions and token bloat, subagents are instantiated under strict capability profiles:
- **`lookup`:** Read-only exploration. Has access to `list_files`, `read_file`, `search`, and `code_map`. Runs on lightweight local models (e.g., Qwen2.5-Coder-1.5B/3B) loaded beside the primary model. Operates directly in the main workspace or shared repository read-only [7].
- **`research`:** Deep analysis across the repository and external documentation. Includes read-only browser tools (`browser_read`, `browser_screenshot`, `web_search`). Never mutates the codebase.
- **`build`:** Autonomous implementation and refactoring. Executed within an **isolated Git worktree**. Granted `write_file`, `edit_file`, and `run_tests`. Shell commands are strictly confined to the worktree path. Changes are captured as unified git diffs (`base..HEAD`) and returned to the lead agent [2, 5].
- **`operate`:** Desktop and application actuation. Uses computer control tools (`computer_click`, `computer_type`). Requires explicit per-action approvals [6].
- **`external`:** Delegated outside execution (e.g., Antigravity CLI via ACP). Operates inside a separate worktree under sandboxed user-grant gates.

## 2. Git Worktree Lifecycle and Windows OS Hardening

Git worktrees allow multiple working directories to be linked to a single Git repository (`git worktree add`). Each worktree maintains its own checked-out branch, staging index (`.git/worktrees/<name>/index`), and working tree, while sharing the object store (`.git/objects`) and refs [1, 2].

```
Main Repository Root:
├── .git/
│   ├── objects/                  <-- Shared across all subagents
│   ├── refs/heads/               <-- Shared branches
│   └── worktrees/
│       ├── wt-build-01/
│       │   ├── gitdir            <-- Points to .kesher/worktrees/wt-build-01/.git
│       │   ├── HEAD              <-- Branch ref (kesher/wt-build-01)
│       │   ├── index             <-- Independent staging index
│       │   └── index.lock        <-- Lockfile target during git operations
│       └── wt-build-02/
└── .kesher/
    └── worktrees/                <-- Excluded via .git/info/exclude
        ├── wt-build-01/          <-- Subagent 1 isolated workspace
        │   ├── .git              <-- Text file pointing back to main .git/worktrees/
        │   └── src/
        └── wt-build-02/          <-- Subagent 2 isolated workspace
```

While clean in POSIX environments, Windows NTFS imposes strict file locking semantics that create distinct failure modes in automated agent loops [1, 9].

### 2.1 Windows-Specific Failure Modes

1. **Mandatory File Locking (`EPERM` / `EBUSY`):** Unlike POSIX where open files can be unlinked, Windows locks files against deletion or renaming if any process holds an open handle without `FILE_SHARE_DELETE` [9]. Common culprits include:
   - Antivirus scanners (Windows Defender real-time protection scanning newly extracted `.ts`/`.dll` files).
   - Windows Search Indexer (`SearchIndexer.exe`).
   - Lingering Node.js test runners or build daemons (e.g., `esbuild`, `tsc -w`, `cargo`, Unreal build workers) spawned by the subagent.
2. **Current Working Directory (CWD) Locking:** If a spawned child process, subagent shell, or IDE tool has its active working directory inside `.kesher\worktrees\<name>`, the entire folder structure is pinned by the Windows kernel. Any subsequent call to `git worktree remove` or Node's `rmdir` fails instantly with `EPERM: operation not permitted` [1, 9].
3. **Stale Lockfiles (`index.lock` / `HEAD.lock`):** When a subagent process is abruptly terminated (e.g., user cancellation, timeout, or watchdog kill), Git leaves behind `.git/worktrees/<name>/index.lock`. Future Git operations in that worktree permanently fail until the lockfile is removed [1].
4. **Path Length Limits (`MAX_PATH`):** Deeply nested project structures combined with `.kesher/worktrees/<long-subagent-name>/...` can exceed the Windows 260-character path limit unless `core.longpaths` is configured [1].

### 2.2 Hardened Worktree Creation Pattern

To guarantee safe provisioning on Windows, `createSessionWorktree` must adhere to the following sequence:

```typescript
/**
 * Hardened Windows worktree provisioning pattern.
 */
export async function createSafeWindowsWorktree(
  repoRoot: string,
  slug: string,
  git: GitRunner,
  opts: { baseCommit?: string; copyEnv?: boolean } = {}
): Promise<AllocatedWorktree> {
  // 1. Ensure core.longpaths is active in the repository
  await git(repoRoot, ["config", "core.longpaths", "true"]);

  // 2. Validate clean naming (alphanumeric slug + timestamp + random hex)
  const name = worktreeName(slug);
  const worktreePath = resolve(repoRoot, ".kesher", "worktrees", name);
  const branchName = `kesher/${name}`;

  // 3. Prevent Git tracking of the internal worktree root
  await excludeWorktrees(repoRoot, git);

  // 4. Resolve exact base commit SHA to prevent HEAD drift
  const baseSha = (await git(repoRoot, ["rev-parse", "--verify", `${opts.baseCommit ?? "HEAD"}^{commit}`])).trim();

  // 5. Atomic worktree creation with detached HEAD or unique branch
  await mkdir(dirname(worktreePath), { recursive: true });
  await git(repoRoot, ["worktree", "add", "-b", branchName, worktreePath, baseSha]);

  // 6. Selective file copying (.worktreeinclude) with handle release
  if (opts.copyEnv !== false) {
    await copyIncludedFiles(repoRoot, worktreePath);
  }

  return { name, path: worktreePath, branch: branchName, baseSha };
}
```

Key hardening mechanisms:
- **Exclusion Isolation:** The directory `.kesher/worktrees/` is registered in `.git/info/exclude` rather than `.gitignore`. This ensures local agent infrastructure never dirties the developer's tracked repository state [1].
- **Copy Filtering:** Build caches (`node_modules`, `.next`, `target`, `Binaries`, `Intermediate`) must **never** be copied into subagent worktrees. Instead, only configuration and environment files defined in `.worktreeinclude` (e.g., `.env`, `.env.local`) are replicated, capping file copying at 500 entries to prevent I/O stalls.

### 2.3 Resilient Cleanup and Pruning Lifecycle

Teardown must be resilient to lingering handles:
1. **Process Tree Termination:** Before tearing down a worktree, terminate all child processes spawned within that tree using `taskkill /F /T /PID <pid>`.
2. **Directory Detachment:** Verify that KesherAI's core process working directory is anchored strictly to the repository root or application directory, never inside the child worktree [9].
3. **Retrying Safe Removal:** If `git worktree remove --force` fails with `EPERM`, initiate a retry loop with exponential backoff and jitter (3 attempts: 200 ms, 600 ms, 1800 ms) to allow Windows Defender or file handles to close [9].
4. **Stale Lock Cleanup:** If an operation aborts, check `.git/worktrees/<name>/index.lock`. If the process that created it is dead, unlink the lockfile directly.
5. **Forced Pruning:** Execute `git worktree prune --expire=now` to clean up dangling metadata in `.git/worktrees/` [1].

```
                      WORKTREE TEARDOWN FLOW
                                │
                    [Subagent Task Settled]
                                │
                                ▼
               Kill Child Process Tree (taskkill /T)
                                │
                                ▼
               Verify Host CWD is Outside Worktree
                                │
                                ▼
               Attempt: git worktree remove --force
                                │
                    ┌───────────┴───────────┐
                    │                       │
               [Success]                 [EPERM]
                    │                       │
                    │                       ▼
                    │            Exponential Backoff (3x)
                    │            (200ms -> 600ms -> 1800ms)
                    │                       │
                    │           ┌───────────┴───────────┐
                    │           │                       │
                    │      [Retry OK]             [Still Locked]
                    │           │                       │
                    │           │                       ▼
                    │           │            Rename dir to .trash-*
                    │           │            Schedule for idle purge
                    │           │                       │
                    └───────────┼───────────────────────┘
                                │
                                ▼
                    git branch -D kesher/<name>
                                │
                                ▼
                    git worktree prune --expire=now
```

## 3. Inter-Agent Communication Protocol & Context Budgeting

When subagents execute autonomously, they perform dozens of tool calls (reading multi-hundred-line files, executing compiler passes, querying symbols). Streaming this raw operational telemetry directly into the lead agent's conversation thread results in severe context pollution and rapid context window exhaustion [7, 8].

To maintain context hygiene for local models (capped at 16k–32k tokens), KesherAI enforces a **Structured JSON Protocol** with a strict **200–400 Token Findings Rollup** [7, 10].

### 3.1 Protocol Specification & Message Types

The parent-child communication model operates over four discrete packet types:
1. `TASK_DELEGATE`: Parent delegates assignment, constraints, context budget, and tool permissions.
2. `PROGRESS_STREAM`: Child emits real-time status pulses (step count, tool name, brief target) over internal Server-Sent Events (SSE). Displayed on the user's desktop/mobile UI card but **excluded from the lead model's LLM prompt context** [7].
3. `INTERVENTION`: Parent steers or cancels a running subagent mid-flight (via `helper_message` / `helper_stop`).
4. `FINDINGS_ROLLUP`: Child emits a compressed, structured payload upon completion, strictly limited to 200–400 tokens [7].

```
  Lead Agent (Parent)                           Subagent (Child in Worktree)
          │                                                  │
          │─────── 1. TASK_DELEGATE (JSON Schema) ──────────>│
          │                                                  │  [Executes Tools]
          │                                                  │  [read, edit, test]
          │<────── 2. PROGRESS_STREAM (SSE / Event) ─────────│  (Step 1/5: search)
          │<────── 2. PROGRESS_STREAM (SSE / Event) ─────────│  (Step 2/5: edit)
          │                                                  │
          │   [Optional Parent Steering: INTERVENTION]       │
          │─────── (e.g. redirect scope / abort) ───────────>│
          │                                                  │
          │                                                  │  [Passes Tests]
          │                                                  │  [Generates Diff]
          │<────── 3. FINDINGS_ROLLUP (200-400 Tok) ─────────│
          │                                                  │
   [Absorbs Rollup]                                   [Worktree Purged]
   [Gated Hunk Review]
```

### 3.4 Grammar-Constrained Output (Peg-Native / GBNF)

To ensure small local models (e.g., 3B to 8B parameter models) do not produce invalid JSON or conversational preamble (`"Here is the result..."`), `llama-server` is configured with a strict context grammar (GBNF / Peg-native schema constraint) [3, 7]. The engine constrains sampling logits so that every generated token conforms strictly to the `FindingsRollupMessage` schema. This eliminates format retry penalties and guarantees that rollup outputs remain bounded between 200 and 400 tokens [7].

## 4. Local Concurrency, llama.cpp Slot Pinning, and VRAM Arbitration

A primary danger of running autonomous subagents locally is hardware exhaustion:
1. **VRAM Saturation:** Spawning multiple model instances or allocating oversized context buffers causes CUDA allocation failures (`out of memory`), crashing the local engine [3, 4].
2. **KV Cache Fragmentation:** When multiple requests hit `llama-server` without slot coordination, prompt prefixes are evicted, destroying KV cache reuse and dropping token generation rates from 45 tok/s to under 5 tok/s [3, 4].
3. **Compute Contention:** Running heavy compiler checks (e.g., Unreal Engine build steps) alongside multi-slot LLM inference causes severe CPU and thread starvation [4].

### 4.1 llama-server Slot Architecture & Continuous Batching

Modern `llama-server` (part of `llama.cpp`) handles concurrency through **continuous batching** across discrete execution tracks called **slots** (`--parallel N` or `-np N`) [3, 4].

```
Total Context Allocation (-c 32768, -np 4) -> 4 Slots of 8192 Tokens Each
┌──────────────────────────────────────────────────────────────────────────────┐
│                            LLAMA-SERVER KV CACHE                             │
│                                                                              │
│  ┌───────────────────────┐  ┌───────────────────────┐  ┌──────────────────┐  │
│  │ Slot 0 (id_slot: 0)   │  │ Slot 1 (id_slot: 1)   │  │ Slot 2 (id_slot: │  │
│  │ [Lead Agent Session]  │  │ [Subagent 1: Build]   │  │ [Subagent 2: Loo │  │
│  │ KV: System + User Chat│  │ KV: Worktree Tool Loop│  │ KV: Code Search  │  │
│  │ State: IDLE / STREAM  │  │ State: ACTIVE         │  │ State: IDLE      │  │
│  └───────────────────────┘  └───────────────────────┘  └──────────────────┘  │
│  ┌────────────────────────────────────────────────────────────────────────┐  │
│  │ Continuous Batching Token Pipeline (Batch Size: 512, ubatch: 128)      │  │
│  │ [Tok S0] [Tok S1] [Tok S1] [Tok S2] ... Evaluated in single CUDA pass  │  │
│  └────────────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────────────┘
```

1. **Context Slicing (`n_ctx_slot`):** If the server starts with `-c 32768 -np 4`, the KV cache is partitioned into 4 distinct slots of 8,192 tokens each [3].
2. **Prefix Caching & Longest Common Prefix (LCP):** When a request targets a slot, the server matches the prompt against existing KV cache tokens. If the system prompt and tool definitions match, prompt evaluation is instantaneous (0 ms prefill) [3, 4].
3. **Continuous (In-Flight) Batching:** Tokens generated for Slot 0 and Slot 1 are processed together in unified hardware batches (`ubatch`), ensuring high GPU tensor core saturation [4].

### 4.2 Deterministic Slot Pinning Model

Without coordination, `llama-server` dynamically dispatches incoming requests to the first idle slot. If Subagent 1 lands on Slot 0, it overwrites the Lead Agent's cached prompt history, forcing a massive prompt re-computation on the user's next turn [3].

KesherAI introduces **Deterministic Slot Pinning**:
- **Slot 0 (Reserved):** Dedicated permanently to the **Lead Agent Session**. Its system prompt, tool definitions, and primary chat history remain locked in KV memory.
- **Slot 1..N-1 (Dynamic Pool):** Managed by the `SlotArbiter`. When a subagent is dispatched, it acquires a lease on a specific slot index, passing `"id_slot": slotIndex` in the request body [3].
- **Sorted Tool Specs (`sortSpecs`):** All subagents in a given role receive alphabetically sorted tool specifications. This guarantees 100% prompt prefix reuse across consecutive subagent runs [7].

```typescript
/**
 * Concurrency Arbiter managing llama.cpp slot leases.
 */
export class SlotArbiter {
  private availableSlots: number[];
  private activeLeases = new Map<string, number>();

  constructor(totalSlots: number) {
    // Slot 0 is reserved for the Lead Agent
    this.availableSlots = Array.from({ length: Math.max(0, totalSlots - 1) }, (_, i) => i + 1);
  }

  async acquireSlot(subagentId: string, signal: AbortSignal): Promise<number> {
    while (this.availableSlots.length === 0) {
      signal.throwIfAborted();
      await new Promise((resolve) => setTimeout(resolve, 50));
    }
    const slot = this.availableSlots.shift()!;
    this.activeLeases.set(subagentId, slot);
    return slot;
  }

  releaseSlot(subagentId: string): void {
    const slot = this.activeLeases.get(subagentId);
    if (slot !== undefined) {
      this.activeLeases.delete(subagentId);
      this.availableSlots.push(slot);
      this.availableSlots.sort((a, b) => a - b);
    }
  }
}
```

### 4.3 Hardware Guard & HeavyGate Integration

To prevent system lockups during multi-agent execution, dispatch is gated by KesherAI's `HeavyGate` and `GpuGuard`:
- **Load Concurrency Cap:** Local subagents requiring GPU inference are limited by VRAM capacity:
  - $\le 8\text{ GB VRAM}$: Max 1 local agent at a time. Concurrency $= 1$.
  - $12\text{--}16\text{ GB VRAM}$: Max 1 lead $+ 1$ helper (`parallel: 2`).
  - $24\text{ GB VRAM (RTX 3090/4090)}$: Max 1 lead $+ 2$ helpers (`parallel: 3` or `4`).
- **Heavy Operations Serialization:** Subagents running compilers (`tsc`, `dotnet build`, `make`) must pass through `HeavyGate.run()`. Only one heavy compilation or model load can execute on the workstation at any instant, preventing memory spikes that trigger power surges or OS reboots [4].
- **Thermal Backoff:** If the GPU temperature exceeds `maxTemp` (e.g., 82°C), active subagent turns are throttled until temperature drops below `resumeTemp` (74°C) [4].

## 5. Lead-Agent Inspection, per-Hunk Approval Gates, and Merging

Autonomous subagents executing in parallel branches can create merge conflicts or introduce regressions if changes are pushed directly to `main` [2, 5]. KesherAI implements a **Zero-Conflict, Hunk-Gated Merge Architecture** [5, 6].

```
Subagent Worktree (.kesher/worktrees/wt-1)
  │
  │ [Generates commits on kesher/wt-1]
  ▼
git diff baseSha..HEAD
  │
  ▼
Unified Diff Stream
  │
  ▼
parseDiff() -> Structured Diff:
  ├── File: src/server.ts
  │   ├── Hunk 0: lines 12-25 (Port configuration)
  │   └── Hunk 1: lines 88-104 (Route handler)
  └── File: src/config.ts
      └── Hunk 0: lines 45-52 (Timeout setting)
  │
  ▼
Interactive Approval Gate (Desktop UI & 390px Mobile Interface)
  │
  ├── [User / Lead Action]: Accept Hunk 0, Reject Hunk 1 on src/server.ts
  │
  ▼
applyHunk() Engine (Pure Relocatable Patch Applier)
  │
  ├── 1. Read target file currently in Main Workspace
  ├── 2. Match exact old context lines via findBlock() (nearest line offset)
  ├── 3. Verify no intermediate edits occurred (Atomic re-read)
  ├── 4. Apply approved hunks directly to host file
  └── 5. Record rollback snapshot in UndoStore
```

### 5.1 Why Git Merge is Prohibited for Subagents

KesherAI forbids running `git merge`, `git cherry-pick`, or `git rebase` from subagents into the host branch. Traditional Git merges present three critical flaws in AI agent environments:
1. **Opaque Merge Conflicts:** Git injects `<<<<<<< HEAD`, `=======`, `>>>>>>>` conflict markers into source files. If an agent fails to resolve them, the project is left in an uncompilable state [2].
2. **All-or-Nothing Application:** Standard commits bundle multiple changes. If a subagent wrote 4 good functions and 1 buggy function, a branch merge forces acceptance of all 5 [5, 6].
3. **Workspace Invalidation:** Modifying tracked files out from under an open IDE (VS Code, Visual Studio, Unity) without fine-grained diff tracking disrupts file watchers and triggers sudden re-indexing [1, 9].

### 5.2 Hunk Decomposition & Application Engine

KesherAI utilizes the pure diff analysis engine implemented across `packages/shared/src/diff-review.ts` and `packages/core/src/helper-review.ts`:

1. **Diff Parsing (`parseDiff`):** The raw output of `git diff base..HEAD` is parsed into structured objects:
   ```typescript
   export interface DiffFile {
     path: string;
     kind: "modify" | "add" | "delete" | "binary";
     hunks: DiffHunk[];
     cut?: boolean;
   }
   export interface DiffHunk {
     header: string;
     oldStart: number;
     lines: string[];
   }
   ```
2. **Contextual Block Matching (`findBlock`):** When applying a hunk, the original line numbers (`oldStart`) might have shifted due to edits made by the developer in the meantime. The `findBlock` algorithm searches outward from `oldStart`:
   ```typescript
   function findBlock(lines: string[], block: string[], near: number): number {
     if (!block.length) return Math.min(near, lines.length);
     const fits = (at: number) => at >= 0 && at + block.length <= lines.length &&
       block.every((b, i) => lines[at + i] === b);
     for (let d = 0; d <= lines.length; d++) {
       if (fits(near - d)) return near - d;
       if (d && fits(near + d)) return near + d;
     }
     return -1;
   }
   ```
3. **Atomic Conflict Rejection:** If `findBlock` cannot locate the hunk's exact context lines (meaning the file changed incompatibly since the subagent branched), the hunk is flagged with `ok: false, reason: "This part of the file changed since the agent read it"`. The engine never forces a malformed write [5].
4. **Pre-Write Verification:** Right before writing to disk, the file is re-read. If another process modified it during the evaluation cycle, the write is aborted, guaranteeing zero corruption [5].

### 5.3 Mobile (390px) & Desktop Review Experience

In accordance with KesherAI's cross-device rules:
- **Desktop:** The Lead Agent presents an interactive diff card displaying file accordions, syntax highlighting, and per-hunk `[Keep ✓]` / `[Discard ✗]` buttons [5, 6].
- **Mobile Remote (390px):** The card stacks vertically. Long lines wrap with `<bdi>` bidirectionality protection for Hebrew and English. Each hunk provides swipe-to-accept/reject gestures and an instant `"Undo Hunk"` button [5].
- **Audit & Undo:** Every applied hunk logs its before/after state to `UndoStore`. The user can click `"Undo all changes from this helper"` at any time, restoring the files to their exact pre-review state [6].

| Strategy | Filesystem Isolation | Merge Conflict Risk | Windows NTFS Compatibility | Token Cost Overhead | Implementation Complexity |
| :--- | :--- | :--- | :--- | :--- | :--- |

| **Full Clones (`git clone`)** | Complete | Moderate (manual branch merge) | Moderate (slow I/O, heavy disk use) | Medium | Medium |
| **Docker / Container Sandbox**| Complete | Low | Poor on Windows Home; high VRAM/WSL2 overhead | High | High |
| **KesherAI Worktree + Hunk Gate** | **Complete (.kesher worktree)**| **Zero (atomic hunk approval)**| **High (retry loops + CWD guards)** | **Minimal (200-400 tok rollup)**| **Balanced & Production-Ready**|

## 7. Concrete Implementation Roadmap for KesherAI

### Phase 1: Windows Worktree Hardening (`packages/core/src/session-worktrees.ts`)
- Add `core.longpaths` configuration check on worktree initialization.
- Implement exponential backoff retry loop (200 ms, 600 ms, 1800 ms) around `git worktree remove` and `removeSessionWorktree` to eliminate Windows `EPERM` unlinking errors.
- Ensure host process working directory is asserted outside the child tree before unlinking.

### Phase 2: Peg-Native Grammar Constrained Rollup Protocol (`packages/agent/src/`)
- Introduce GBNF / JSON Schema logit constraint on `llama.cpp` helper endpoints enforcing the `FindingsRollupMessage` schema.
- Enforce the 400-token hard ceiling on subagent completions, preventing context bloat in parent chats.
- Strip intermediate subagent tool logs from the parent's LLM message history, directing them exclusively to UI SSE streams.

### Phase 3: llama-server Slot Arbiter (`packages/core/src/llamacpp.ts`)
- Expose deterministic slot allocation (`id_slot: 0` reserved for Lead Agent, `id_slot: 1..N` leased to helpers).
- Wire `SlotArbiter` to `ChatHelpers` and `HeavyGate`, dynamically adjusting slot concurrency based on available GPU VRAM.

### Phase 4: Cross-Platform Hunk Review UI (`apps/web/src/components/`)
- Connect `helper-review.ts` endpoints to desktop and mobile review cards.
- Implement per-hunk accept/reject buttons and swipe gestures with instant rollback via `UndoStore`.

## 8. Conclusion

By decoupling subagent execution into isolated Git worktrees and replacing traditional, conflict-prone branch merges with a per-hunk diff review pipeline, KesherAI provides a robust, zero-conflict multi-agent programming environment. Restricting child-to-parent communication to a 200–400 token JSON findings rollup preserves precious local LLM context, while llama-server slot pinning and `HeavyGate` concurrency arbitration guarantee that multiple local agents run efficiently without exhausting system RAM or GPU VRAM.
