# Deep Research: Game Engines — Engine-less Collaboration, Live Co-editing, Unity Muse / Unity AI, and Mobile Web Builds

## Executive Summary

Game development has traditionally demanded that every participant install massive, multi-gigabyte engine suites (Unity, Unreal Engine, Godot) along with matching compiler toolchains, SDKs, and tens of gigabytes of raw project assets. This deep research report establishes an exhaustive technical roadmap for KesherAI to enable **engine-less collaboration**, **real-time multiplayer co-editing**, **comprehensive local-first AI tooling (bringing the full Unity Muse / Unity AI suite locally)**, and **mobile browser game builds** (via Unity 6 WASM64/WebGPU and Unreal Engine 5.9 Web targets).

The four operational pillars investigated:
1. **Part A: Engine-less Collaboration:** Collaborators work without Unity, Unreal, or Godot installed. They view and edit levels via KesherAI's Three.js web stand-in, edit code and data, and sync changes back to the main developer workstation where KesherAI plugins apply modifications via native Undo transactions (or headless CLI runners). We evaluate Unity Version Control (Plastic SCM) Gluon, Perforce + Unreal OFPA, Diversion, Anchorpoint, Godot `.tscn`, Git LFS locking, UnityYAMLMerge, and cloud editors.
2. **Part B: Live Co-editing of Game Scenes:** Real-time presence, camera frustums, live transform manipulation, and conflict resolution across web clients and the host PC engine. We dissect Unreal Concert (Multi-User Editing), Roblox Team Create, Figma's server-authoritative Last-Writer-Wins (LWW) property architecture, Scene Fusion, Yjs/Automerge CRDTs vs. operation logs, and engine transaction batching.
3. **Part C: Unity Muse Suite & Local-First KesherAI Equivalents:** An exhaustive catalog of all Unity Muse tools (Muse Chat, Sprite, Texture, Animate, Behavior, Sketch/Canvas, Sentis), detailing the 2024–2026 sunsetting of standalone Muse into Unity 6's integrated "Unity AI Assistant", and mapping each capability to local open-source models (SDXL/Flux/Qwen-Image, TRELLIS 3D, Motion models, Kokoro/AudioLDM, ONNX/Sentis).
4. **Part D: Playing Game Web Builds on Mobile Phones:** Technical evaluation of mobile web deployment, including Epic Games' reintroduction of native WebAssembly/WebGPU in UE 5.9 Preview (and third-party solutions like SimplyStream/Wonder Interactive), Unity 6's WebGPU and WASM64 runtimes, mobile browser memory limits (iOS Safari 512MB threshold), touch controls, and secure local/hub hosting with COOP/COEP isolation.

### 2. File Safety Taxonomy: What Can Be Edited Without the Engine?

Game projects contain a heterogeneous mix of file formats. Understanding which can be safely authored and edited in KesherAI without the engine running is critical:

#### Category 1: Completely Safe for External Authoring
* **C# Scripts (`.cs`), C++ Code (`.cpp`, `.h`), Shaders (`.shader`, `.hlsl`):** Standard text files. Can be created, edited, and refactored using KesherAI’s built-in code editor or agent.
* **Text Data & Configs (`.json`, `.xml`, `.csv`, `.yaml`, `.ini`):** Fully safe for external authoring.
* **Raw 2D Media & Audio (`.png`, `.jpg`, `.wav`, `.ogg`):** Can be generated or modified outside the engine, provided that companion metadata (such as Unity `.meta` files) is created or preserved.
* **3D Interchange Formats (`.fbx`, `.obj`, `.gltf`, `.glb`):** Can be authored, inspected, and rendered in Three.js without the game engine.

#### Category 2: Semi-Safe with Parser Verification (Text YAML / Text Scenes)
* **Unity Scenes (`.unity`), Prefabs (`.prefab`), and ScriptableObjects (`.asset`):**
  * *Structure:* Formatted as custom YAML with stripped tags (e.g., `--- !u!1 &123456789`).
  * *External Editing Capabilities:* KesherAI can safely parse GameObject hierarchies, transforms, and primitive component properties (as implemented in `packages/core/src/unity-scene.ts`). Modifying transforms (position, rotation, scale) is safe because internal fileIDs and GUID references are preserved.
  * *Risks:* Adding new components or GameObjects directly to raw YAML without Unity running is prone to error because Unity generates specific 64-bit local fileIDs and class IDs (`!u!1`, `!u!4`, etc.). If a script reference is added without its exact `guid` and `fileID` from its `.cs.meta` file, the component loads as `Missing Script` in Unity.
* **Godot Scenes (`.tscn`) and Resources (`.tres`):**
  * *Structure:* Human-readable INI/TOML format.
  * *External Editing:* High safety for transform changes and parameter tweaks. Adding external resources requires matching `[ext_resource]` ID tags.

#### Category 3: Unsafe / Impossible Without the Engine
* **Unreal Engine Assets (`.uasset`) and Levels (`.umap`):**
  * *Structure:* Proprietary, highly serialized binary containers containing class default object (CDO) structures, export tables, import tables, and bulk binary payload data.
  * *Danger:* **Never modify `.uasset` or `.umap` files directly via binary manipulation or external hex edits.** Any mismatch in package header byte counts or serialization tables corrupts the asset registry, causing fatal editor crashes.
  * *The Engine-as-a-Service Requirement:* Modifying Unreal levels, actor transforms, or Blueprint nodes *must* be delegated to an Unreal Engine process (either an active editor via KesherAI’s bridge plugin or a headless command-line execution).

### 3. Recommended Design for KesherAI Engine-less Collaboration

To fulfill Roee's goal—where collaborators have zero engine software installed, viewing and editing scenes through KesherAI's Three.js stand-in while the main workstation applies changes—KesherAI should adopt the following end-to-end architecture:

```
[ Collaborator Web UI / Phone ]
   (Three.js Scene Stand-in)
   │
   │ WebSocket / HTTP REST (Transforms, Placements, Code edits)
   ▼
[ KesherAI Hub / Central Server ]
   ├── Presence & Soft Locks (Redis / In-Memory State)
   ├── Pending Changes Store (KesherAI/pending-moves.json)
   └── Git Sync Relay (Branch per collaborator or feature)
   │
   │ Local Network / WebSocket Tunnel
   ▼
[ Main PC (Host Workstation) ]
   ├── KesherAI Core Local Server
   ├── KesherAI Bridge Plugin (Unity com.kesherai.bridge / UnrealBridge)
   │     ├─ If Editor Open: Applies queued moves as native Undo transactions
   │     └─ If Editor Closed: Spawns Headless Engine CLI (-batchmode / -run)
   └── Validation & Feedback Loop
         ├─ Headless test compilation (C# / C++ diagnostics)
         ├─ Viewport camera render capture (PNG / WebP snapshots)
         └─ Syncs rendered feedback back to Collaborator Web UI
```

#### A. Sync Channel Architecture
* **Primary Delta Channel:** KesherAI’s own lightweight WebSocket hub handles low-latency live operations (transform adjustments, presence, selection states).
* **Durable Storage Channel:** Git repository. The main PC acts as the authoritative Git committer. Collaborators commit changes logically through KesherAI, which verifies metadata (generating valid `.meta` files for new assets before committing).

#### B. Locking and Conflict Handling
* **Soft Locks (Advisory):** When a collaborator clicks or drags an object in the Three.js stand-in, a soft lock is broadcast. The object displays a colored bounding box with the collaborator's name in all other connected viewports.
* **Exclusive Hard Locks:** For non-mergeable binary assets (FBX, textures, audio) and scene containers, KesherAI enforces an exclusive checkout lock stored in KesherAI’s hub database. Other users cannot initiate drag or override actions until released.
* **Merge Strategy:** Property-level Last-Writer-Wins (LWW) for transform coordinates (`position`, `rotation`, `scale`), combined with granular undo buffers per collaborator session.

#### C. Main PC Application and Feedback Loop
1. **Editor Open (Interactive Mode):**
   * The KesherAI Bridge plugin continuously listens or checks `KesherAI/pending-moves.json`.
   * When moves arrive, the plugin executes `Undo.RecordObject` (Unity) or `GEditor->BeginTransaction()` (Unreal), applies the transforms to the scene objects, and marks the scene dirty.
   * The developer on the main PC can inspect the live modifications and hit standard Undo (`Ctrl+Z`) if an adjustment is rejected.
2. **Editor Closed (Headless Execution):**
   * If Unity is closed, KesherAI Core invokes Unity in batchmode:
     `Unity.exe -batchmode -nographics -projectPath "<DIR>" -executeMethod KesherAI.Bridge.ApplyPendingMoves -quit`
   * If Unreal is closed, KesherAI Core invokes the commandlet:
     `UnrealEditor-Cmd.exe "<PROJECT_PATH>" -run=KesherAIApplyMoves -Map="<MAP_PATH>"`
3. **Automated Feedback to Collaborator:**
   * After applying changes, the plugin captures high-resolution viewport camera renders (via an offscreen camera render target) and streams the resulting WebP image back to the collaborator's web stand-in.
   * If scripts were edited, KesherAI runs background compilation checks (`dotnet build` or engine log parsing) and renders compiler error markers directly in the collaborator’s code view.

### 2. State Synchronization: CRDTs (Yjs / Automerge) vs. Server-Authoritative LWW Streams

A central technical decision in collaborative 3D editors is choosing between decentralized Conflict-free Replicated Data Types (CRDTs) and a server-authoritative operation stream:

#### Why Pure CRDTs (Yjs / Automerge) Introduce Friction in 3D Scene Graphs
1. **High-Frequency Transform Flooding:** During active manipulation (dragging a 3D gizmo), updates occur at 30–60 Hz. CRDTs track causal history, vector clocks, and operation tombstones. Generating CRDT items for every intermediate mouse move bloats memory and causes unnecessary history tracking [30].
2. **Hierarchy and Reparenting Hazards:** In 3D scene graphs, reparenting nodes concurrently can easily create dependency cycles (Node A becomes child of Node B, while Node B concurrently becomes child of Node A), causing render tree deadlock. General-purpose CRDTs require complex custom algorithms to guarantee cycle-free tree replication [25, 27].
3. **Decentralization Overhead is Unnecessary:** In KesherAI's model, the main PC (or central hub) is *already* the physical owner of the project files and game engine. A fully peer-to-peer decentralized model adds excessive architectural baggage without practical benefit.

#### The Ideal Model: Figma-Style Server-Authoritative Property LWW
Following Figma’s battle-tested multiplayer engine [25, 27]:
* **Flat Map of Scene Objects:** Represent the scene as a flat map `Map<string, SceneNode>`, where each node contains discrete properties:
  ```json
  {
    "id": "1049283",
    "name": "MainCamera",
    "parentId": "0",
    "position": [0.0, 1.5, -5.0],
    "rotation": [0.0, 0.0, 0.0, 1.0],
    "scale": [1.0, 1.0, 1.0],
    "version": 42
  }
  ```
* **Property-Level Granularity:** If Collaborator A edits `position` while Collaborator B edits `scale`, both edits succeed simultaneously without conflict [25].
* **Monotonic Sequence Arbitration:** All mutations are sent to the KesherAI server over WebSockets. The server assigns each operation a strictly incrementing sequence ID (`seq_id`) and broadcasts the authoritative state.
* **Separation of Ephemeral vs. Durable State:**
  * *Ephemeral Stream (No persistence):* Camera frustum positions, cursor rays, and intermediate transform drag coordinates are broadcast via a lightweight `awareness` channel without disk logging.
  * *Durable Transaction Log:* Only `drag_end` or explicit property commits generate a persistent transaction event.

### 3. Transport and Presence Networking

#### Network Transport Protocol Selection
* **WebSocket via KesherAI Hub:** The recommended default. Provides reliable, ordered delivery of transform transactions, full firewall and NAT traversal, and seamless coordination between the home PC and remote collaborators/phones.
* **WebRTC DataChannels:** Can optionally be layered for low-latency peer-to-peer ephemeral streaming (camera tracking and mouse movements) when collaborators are on the same local area network (LAN), falling back to WebSocket via the hub for wide-area connections.

#### Presence UI in the Three.js Stand-In
To give collaborators a shared sense of space:
1. **Camera Frustums & Avatars:**
   * Each connected collaborator is assigned a unique visual color (e.g., User 1 = Blue, User 2 = Orange, User 3 = Green).
   * In Three.js, a wireframe `CameraHelper` or custom pyramid mesh represents each collaborator’s viewport, showing their exact viewpoint, orientation, and focal distance.
   * A billboard nameplate displaying the collaborator's name floats above their camera.
2. **Per-Object Soft Locks During Dragging:**
   * When a user clicks a 3D gizmo on an object, a `lock_claim` event is fired.
   * The object is highlighted with an outline shader matching that user's color.
   * For other users, gizmo handles for that object are disabled, and a tooltip indicates `"Locked by [User]"`.
   * When dragging finishes, a `lock_release` event clears the lock. If a user disconnects abruptly, heartbeats automatically expire lingering locks within 3 seconds.
3. **Latency Compensation & Optimistic Updates:**
   * The local user's Three.js transform gizmo moves with 0ms lag (optimistic local execution).
   * Remote updates are smoothly interpolated across network ticks using linear interpolation (LERP for position and scale, SLERP for quaternion rotation) over 50–100ms buffers, avoiding visual jitter.

### 4. Engine Synchronization: Turning Live Sessions into Safe Engine Changes

Because the game engine (Unity or Unreal) runs only on the main PC, the bridge must safely ingest collaborator edits without corrupting the active editor session or crashing the project:

```
[ Collaborator 1 Drag End ]   [ Collaborator 2 Drag End ]
             │                              │
             └──────────────┬───────────────┘
                            ▼
             [ KesherAI Hub Server ]
             ├─ Assigns seq_id
             ├─ Merges into pending moves buffer
             │
             ▼ WebSocket / HTTP Push
     [ Main PC: KesherAI Bridge Plugin ]
             │
             ├─ 1. Validation & Schema Check (valid IDs, finite numbers)
             ├─ 2. Game Checkpoint Creation (snapshot scene state)
             ├─ 3. Begin Engine Transaction (Undo.RecordObject / GEditor->BeginTransaction)
             ├─ 4. Apply Transforms to Scene Actors
             ├─ 5. End Engine Transaction & Mark Dirty
             │
             ▼
     [ Offscreen Render Target Capture ]
             │
             ▼ WebP Stream
     [ Rendered Visual Feedback to Collaborators ]
```

#### Safe Batching Mechanisms
1. **Transaction Grouping:** Micro-movements during a single drag gesture are never sent as hundreds of individual engine moves. Only the final resting transform (`from` -> `to`) is submitted upon mouse release (`drag_end`).
2. **Native Undo Registration:**
   * *Unity:* `Undo.RecordObjects(modifiedTransforms, "Collaborator Transform Update");`
   * *Unreal:* `GEditor->BeginTransaction(LOCTEXT("CollabMove", "Collaborator Transform Update")); ... GEditor->EndTransaction();`
   This guarantees that the main workstation developer can press `Ctrl+Z` to immediately revert collaborator changes if desired.
3. **Selective / Isolated Undo Per User:**
   * Each collaborator’s client maintains an independent undo history stack.
   * When Collaborator A triggers Undo (`Ctrl+Z`), their client requests a revert of *their own* last action, calculating the inverse delta and dispatching it to the server without rewinding Collaborator B’s independent modifications.
4. **Safety Checkpoints & Rollbacks:**
   * Before applying any collaborator batch, KesherAI's checkpoint service (`packages/core/src/game-checkpoints.ts`) creates an automatic rollback snapshot of the scene file. If an engine error or invalid transform occurs, the scene can be restored instantly with zero data loss.

## Part C: Unity Muse Suite Analysis and Local-First KesherAI Equivalents

### 1. The Evolution, Sunset, and Current State of Unity Muse (2024–2026)

Launched initially in late 2023 as a standalone experimental generative AI suite for Unity creators, **Unity Muse** operated under a dedicated $30/month subscription model utilizing a pooled token/point consumption system [31, 32]. 

However, developer adoption suffered due to subscription friction, arbitrary point metering, and rapid advances in external open-source and commercial models [31, 33]. Consequently:
* **The Sunset (Mid-2025):** Unity officially sunsetted the standalone Unity Muse brand and retired individual experimental Muse packages coinciding with the General Availability of **Unity 6.2** [31, 34].
* **The Transition to "Unity AI" / Unity 6 AI Assistant (2025–2026):** Muse's core capabilities were restructured and absorbed into **Unity AI** and the native **Unity 6 AI Assistant** [31, 35].
* **Current Pricing Model:** Rather than a separate $30/month platform, AI capabilities are now gated via editor seat subscriptions: Personal plan users receive a 14-day trial with 1,000 credits, after which credits cost approximately $10/month per 1,000 credits; Pro and Enterprise tiers include bundled monthly allocations [33, 35].

#### How Results Land in the Unity Project
1. **Interactive Mode (Unity Open):**
   * The KesherAI Bridge package (`com.kesherai.bridge`) listens on local loopback.
   * KesherAI writes the generated bytes to disk under `Assets/KesherAI/Generated/` and calls the bridge endpoint `/api/unity/import`.
   * The bridge executes `AssetDatabase.ImportAsset(assetPath, ImportAssetOptions.ForceUpdate);`.
   * For textures, the bridge automatically configures texture import settings (Normal Map flag, Sprite 2D flag, WrapMode = Repeat for seamless textures) and instantiates a standard URP Lit Material.
2. **Headless / Stand-In Mode (Unity Closed):**
   * KesherAI writes the raw asset (`.png`, `.fbx`, `.cs`, `.mat`).
   * KesherAI synthesizes the companion `.meta` file directly. A Unity `.meta` file requires a unique 32-character hexadecimal GUID and default YAML importer settings. By generating deterministic GUIDs (v5 UUIDs based on the relative path), KesherAI prevents GUID collision.
   * When Unity is later opened by the developer, the engine detects the valid `.meta` files and imports the assets instantly without generating duplicate GUIDs.

#### The Hard Engineering Challenges
* **Humanoid Bone Retargeting:** Auto-generated animation clips often possess slightly different rest poses (T-pose vs. A-pose) or bone naming conventions. Mapping MDM output to Unity’s Humanoid Avatar requires a standardized Mecanim bone remapping template.
* **Tangent Space Normal Maps:** Calculating physically accurate MikkTSpace normal maps outside Unity requires executing a compliant normal generation shader; raw heightmap gradient Sobel filters produce slight lighting seams along UV borders if not properly padded.
* **Prefab Variant Serialization:** Writing complex nested prefab overrides directly to YAML without Unity's serialization engine is fragile due to internal fileID tracking. KesherAI should generate base prefabs or rely on the bridge plugin when complex variants are involved.

### 2. Mobile Browser Execution Constraints & Critical Bottlenecks

While modern smartphones boast powerful desktop-class SoCs (Apple A-series/M-series, Snapdragon 8 Elite), running game engine builds inside mobile web browsers introduces severe constraints:

#### A. The Memory Cliff (The 512MB Mobile Watchdog Barrier)
* **The Reality of Mobile WebKit & Android Chrome:** Even though a phone may have 8GB–16GB of physical RAM, mobile operating systems treat individual browser tabs as expendable.
* **Aggressive Tab Termination:** On iOS (WebKit/Safari), if a single browser tab’s total memory footprint exceeds **512MB to 768MB**, the OS watchdog silently kills the tab, displaying the dreaded *"This webpage was reloaded because a problem occurred"* crash [47, 51].
* **WASM64 vs. Mobile Reality:** While WASM64 allows desktop web builds to address massive memory spaces, enabling WASM64 on mobile web builds is counterproductive; the 64-bit pointers increase pointer table sizes and heap overhead, causing the app to hit the OS watchdog limit faster [47, 48]. Mobile builds must strictly target a tuned WASM32 heap with initial allocations capped at **256MB–384MB** [50, 51].

#### B. Graphics: WebGPU vs. WebGL 2 on Mobile
* **WebGPU Advantage:** WebGPU maps directly to modern mobile graphics APIs—**Metal** on iOS and **Vulkan** on Android. It bypasses WebGL’s single-threaded state machine bottlenecks, drastically reduces driver CPU overhead, and enables compute shaders in the browser [46, 47].
* **WebGPU Mobile Availability:** WebGPU is enabled by default in Android Chrome (v121+) and is available behind flags or enabled in iOS Safari 18+. Unity 6’s dual-target build generates WebGPU with an automatic WebGL 2 fallback [46, 47].

#### C. Mobile Audio & Input Quirks
* **Autoplay Audio Policy:** All mobile browsers block audio playback until the user explicitly interacts with the canvas. The engine’s `AudioContext` starts in a suspended state; KesherAI’s launcher must resume the `AudioContext` on the first touch event [49].
* **Touch Event Virtualization:** Desktop game builds expecting WASD keyboard input and mouse look will fail on phones. The mobile launcher must overlay a touch-friendly virtual dual-analog joystick (left stick = move, right stick = camera look) and synthesize virtual keyboard/pointer events.

### 3. Streaming vs. Monolithic Download: Architectural Comparison

| Dimension | Monolithic Download (Standard Export) | Progressive Asset Streaming (Addressables / SimplyStream) | Cloud Pixel Streaming (WebRTC Video) |
| :--- | :--- | :--- | :--- |
| **Initial Download Size** | 200MB – 1.5GB upfront. | **15MB – 35MB initial bootstrap payload**; rest streamed on demand. | 0MB game download; video stream only (~5–15 Mbps bandwidth). |
| **Time to Interactive** | 1–5 minutes (causes 80%+ mobile drop-off). | **3–8 seconds** to splash screen and main menu. | **1–2 seconds**. |
| **Mobile Memory Risk** | Extreme; full uncompressed `.data` file resides in browser RAM [50]. | Low; unloads unused assets dynamically from heap. | Zero client memory risk (rendered on host PC). |
| **Network Sensitivity** | Tolerates offline play once downloaded. | Requires stable connection during world traversal. | Severely affected by network latency and jitter. |
| **Server Cost** | Static file hosting (cheap CDN / local host). | Static asset chunk hosting (cheap CDN / local host). | Extremely expensive (requires dedicated host GPU running 24/7). |

**Verdict for KesherAI:** Monolithic web downloads fail on mobile phones. KesherAI must enforce **Progressive Asset Streaming** (Unity Addressables or Unreal chunked paks) for local client-side execution, with fallback to local **WebRTC Pixel Streaming** (from the developer's home PC GPU) when playing massive non-optimized desktop-class scenes.

#### Step-by-Step Implementation Guide

1. **Required HTTP Security Headers for WebAssembly Multi-Threading:**
   Modern WebAssembly builds (utilizing C++ pthreads or Unity Burst Web Workers) require `SharedArrayBuffer`. Browsers mandate strict cross-origin isolation. The KesherAI Fastify server must serve all build files with:
   ```http
   Cross-Origin-Opener-Policy: same-origin
   Cross-Origin-Embedder-Policy: require-corp
   Access-Control-Allow-Origin: *
   ```
2. **Brotli Compression & Caching:**
   WASM binaries and asset data files must be compressed using Brotli (`.br`). The server must respond with `Content-Encoding: br` and `Content-Type: application/wasm` to allow native streaming instantiation (`WebAssembly.instantiateStreaming`), which compiles the bytecode while downloading, cutting load times by 60%.
3. **The Mobile Launcher UI (`GameLauncher.tsx`):**
   * Built specifically for the 390px phone interface according to KesherAI rules.
   * Features a full-screen toggle utilizing the HTML5 Fullscreen API (`document.documentElement.requestFullscreen()`).
   * Renders a lightweight virtual joystick (left thumb for movement, right thumb for camera look) that injects simulated DOM keyboard and pointer events directly into the game canvas.
   * Automatically displays an in-game telemetry badge showing real-time FPS, WebGPU/WebGL active status, and current heap memory consumption.

1. **Engine-less Collaboration (Part A):** Collaborators require zero engine installs. 4. **Mobile Browser Builds (Part D):** With Unity 6's native mobile WebGPU/WebGL2 support and Epic's reintroduced UE 5.9 WebAssembly target, game web builds can run client-side on mobile devices. However, strict adherence to mobile OS memory limits (<512MB RAM watchdog threshold), chunked asset streaming, and COOP/COEP isolation headers is essential to prevent tab termination.
