# Distributed Local AI Architecture: Hardware-Aware Task Routing, Model Partitioning, and Multi-Device Coordination

## Summary

This research establishes the comprehensive architectural and engineering blueprint for distributing AI workloads across a heterogeneous personal device fleet in KesherAI. The target deployment environment consists of three interconnected nodes:
1. **Primary Compute Rig (Main PC):** High-performance desktop workstation equipped with a 24 GB VRAM GPU (e.g., NVIDIA GeForce RTX 3090/4090), high sustained thermal headroom, and wired Gigabit Ethernet.
2. **Mobile Workstation (Laptop):** Portable device with constrained VRAM (integrated graphics or 6–8 GB mobile GPU), constrained cooling, and dynamic power states (AC mains vs. battery).
3. **Thin Client (Smartphone):** Remote mobile interface running over Wi-Fi or cellular networks with a 390 px viewport in Hebrew and English (`L(he, en)`), zero local inference capability, and intermittent connectivity.

Across the current state of the art in distributed local AI—spanning **exo**, **llama.cpp RPC**, **Petals**, **distributed ComfyUI**, **Ollama clusters (Olla, Ollama Herd, LiteLLM)**, and **LocalAI federation**—two fundamentally distinct paradigms exist:
- **Intra-Model Partitioning (Tensor & Pipeline Parallelism):** Splitting layers or weight matrices of a single model across multiple machines over a network.
- **Inter-Task Job Routing (Workload & Model-Level Offloading):** Routing entire discrete inference or generation tasks to the optimal hardware node based on hardware capability profiling, thermal/battery state, and warm cache residency.

The quantitative and architectural findings of this research conclusively demonstrate that **Inter-Task Job Routing with Asynchronous Workload Delegation** is exponentially superior for KesherAI's operating envelope. Intra-model partitioning over consumer local area networks (LANs) and Wi-Fi introduces crippling latency bottlenecks (reducing token generation speeds by 30% to 95%), catastrophic failure vulnerability (where a sleeping laptop crashes an entire 70B model execution), and severe security hazards (such as unauthenticated raw memory access in llama.cpp RPC). 

This report details the technical mechanics of existing distributed tools, provides mathematical formulations for network communication overhead, establishes hardware governance rules to ensure the laptop is never overburdened, designs a fault-tolerant per-chat device selection model, and defines an actionable 4-phase implementation roadmap for KesherAI.

## 1. Landscape of Distributed Local AI Architectures

To establish the optimal architecture for KesherAI, we analyze six leading distributed local AI systems, examining their discovery protocols, topology models, communication patterns, fault tolerance, and security profiles.

### 1.1 exo (`exo-explore/exo`)

**exo** is an open-source decentralized AI cluster system designed to pool everyday consumer hardware (Apple Silicon Macs, NVIDIA GPUs, AMD GPUs) into a unified compute mesh [1, 2].

- **Topology & Discovery:** exo utilizes a peer-to-peer (P2P) mesh topology built on `libp2p` and local network discovery protocols (mDNS/UDP broadcast) [1, 6]. It continuously constructs a live network graph mapping device memory, memory bandwidth, compute FLOPS, and interconnect latency [1].
- **Partitioning Strategy (`MlxRing`):** For model sharding, exo implements memory-weighted partitioning across a logical ring topology [3]. Layers are allocated proportionally to each device's available RAM/VRAM (e.g., an 80-layer model split 50 layers to a 24 GB GPU and 30 layers to a 16 GB laptop) [3, 8]. Intermediate activations circulate sequentially around the ring using backends such as `mlx.distributed` or PyTorch RPC [1, 3].
- **Recent Benchmarks (2025/2026):**
  - *Disaggregated Prefill/Decode:* In late 2025, Exo Labs demonstrated a hybrid architecture pairing NVIDIA DGX Spark systems (compute-bound prefill) with Apple Mac Studio M3 Ultra hardware (high unified memory bandwidth for autoregressive decode) over 10 GbE, achieving a **2.8× speedup** on Llama-3.1 8B with an 8K prompt compared to a standalone Mac Studio [11].
  - *Frontier Model Pooling:* Running DeepSeek-V3 (671B MoE) across an 8-node cluster of M4 Pro Mac Minis yielded **~5.37 tokens/second** [13].
  - *Interconnect Sensitivity:* Over Thunderbolt 5 with RDMA (inter-device latency $<50\ \mu\text{s}$), tensor parallelism scales with minimal degradation [14]. However, over standard Gigabit Ethernet or Wi-Fi ($1\text{--}25\text{ ms}$ latency), token generation speed degrades by 60% to 85% [6, 14].
- **Failure Behavior:** exo is highly vulnerable to node churn. When a node disconnects, enters sleep mode, or crashes from out-of-memory (OOM), the master node frequently leaves worker instances stuck in a stale `READY` state with zero shards, hanging subsequent client requests [7]. Re-establishing broken Thunderbolt or RDMA links often requires manual cable re-plugging and node sequence restarts [5, 7].
- **Security:** Operates under a trusted LAN assumption. Enterprise access controls, mutual TLS (mTLS), and token-based role-based access control (RBAC) are absent at the mesh transport layer [17].

### 1.2 llama.cpp RPC (`rpc-server` / `ggml-rpc`)

`llama.cpp` introduced the RPC backend (`-DGGML_RPC=ON`) to treat remote hardware accelerators exposed over TCP as local GGML backends [18, 19].

- **Architecture:** A remote worker runs the lightweight `rpc-server` binary, listening on a dedicated TCP port (default `50052`) [18, 20]. The primary node runs `llama-server` or `llama-cli`, loading the GGUF model file and offloading tensor operations and specific layer ranges to one or more remote RPC endpoints via `--rpc <ip>:<port>` [19, 20].
- **Communication Pattern:** Tensor operations are serialized directly over raw TCP sockets [19, 21]. Prompt evaluation (prefill) batches matrix multiplications and transmits large chunks, while token generation (decode) auto-regressively passes individual activation vectors back and forth across the network socket for every generated token [21].
- **Performance Characteristics:**
  - *Prefill (`pp`):* Highly scalable. An enterprise or high-end desktop GPU serving as an RPC worker can accelerate prompt ingestion for a weak host [21].
  - *Decode (`tg`):* Strictly latency-bound. Because each autoregressive token requires round-trip TCP handoffs, decode speeds suffer a **30% to 50% drop in tokens per second** over wired 10 GbE compared to local execution, and a catastrophic **70% to 90% drop over 1 GbE or Wi-Fi** [21, 22].
- **Fault Tolerance:** Zero fault tolerance. If an `rpc-server` process terminates or the network socket drops mid-generation, the host `llama.cpp` process immediately aborts with a socket error or segmentation fault.
- **Security Vulnerabilities:**
  - *No Authentication or Encryption:* `rpc-server` contains **no built-in authentication, no API keys, and no TLS encryption** [23, 24].
  - *Arbitrary Memory Access:* Any network peer able to reach port 50052 can issue raw GGML tensor instructions, inspect unencrypted activations in transit, or trigger arbitrary heap writes, making public or untrusted LAN exposure a critical vulnerability [24, 25].

### 1.3 Petals (`bigscience-workshop/petals`)

**Petals** is a decentralized, peer-to-peer system designed to run and fine-tune frontier models (such as Llama-3.1 405B and Mixtral 8x22B) collaboratively over the public internet [27, 28].

- **Architecture:** Uses a BitTorrent-style Swarm architecture built on the `hivemind` library and a Distributed Hash Table (DHT) [28, 30]. The model's transformer blocks are partitioned across hundreds of untrusted volunteer nodes [28, 29].
- **Dynamic Routing & P2P Pipelines:** Clients query the DHT to discover available nodes hosting specific layer spans [28, 30]. The client routes embeddings to Node A (layers 1–16), which forwards activations over libp2p to Node B (layers 17–32), continuing down the chain until final logits return to the client [28, 29].
- **Fault Tolerance:** Built specifically for unreliable public internet nodes. If a peer drops out mid-generation, the client detects the stream timeout, queries the DHT for an alternative node holding identical layer weights, and dynamically re-stitches the pipeline route [30, 31].
- **Trade-offs:** Optimized for public crowdsourcing, but incurs substantial network overhead. Decode speeds hover between **2 to 6 tokens/second** [27, 28]. It requires a heavy Python/PyTorch runtime environment, making it impractical for lightweight desktop apps with embedded C++ inference runtimes.

### 1.4 Distributed ComfyUI (`robertvoy/ComfyUI-Distributed`)

In image, video, and 3D diffusion workflows, intermediate latent tensors and attention maps are massive compared to LLM activations. Rather than attempting intra-model layer splitting across a network, the ComfyUI ecosystem has converged on **coarse-grained task and batch distribution** [32, 33].

- **Architecture:** Uses a Master-Worker topology. The master instance hosts the workflow UI and graph execution queue, dispatching independent execution graphs or sub-graphs to remote worker machines running `python main.py --listen --enable-cors-header` [32, 34].
- **Workload Partitioning:**
  - *Batch Parallelism:* Dispatches identical workflow graphs with different generation seeds across multiple GPUs/machines simultaneously [32].
  - *Distributed Tiled Upscaling:* Implements nodes such as *Ultimate SD Upscale Distributed*, dividing high-resolution images ($4\text{K}/8\text{K}$) into discrete spatial tiles and farming individual tiles out to remote worker GPUs for parallel latent diffusion before re-stitching on the master [32, 33].
  - *Sub-graph Offloading:* Pipeline workflows can split text encoding (CLIP/T5), diffusion UNet/DiT sampling, and VAE decoding across distinct nodes [32, 33].
- **Fault Tolerance:** Task-level retries. If a remote worker fails to report image tensors over HTTP/WebSocket, the master node flags the worker as degraded and reschedules the failed tile or batch to another active worker [32].

### 1.5 Ollama Clustering & Intelligent Gateways

Because the core Ollama daemon operates strictly as a single-node engine, the community developed multi-node load balancers and proxy gateways: **Olla**, **LiteLLM Router**, **Ollama Herd**, and **Marbor** [36, 37, 38].

- **Unified Catalog Aggregation:** Gateways poll the `/api/tags` or `/v1/models` endpoints of all registered cluster nodes, deduplicating model names and presenting a unified cluster catalog to client applications [36, 39].
- **Routing Strategies:**
  - *`least_conn` (Least Connections):* Crucial for LLM serving [40]. Standard round-robin fails because inference requests are long-lived and variable in duration [40].
  - *Warm-State & Cache-Aware Routing:* Routers inspect the model memory residency state across nodes [37, 39]. A request for `llama3:8b` is routed to a node where the model is already resident in VRAM, eliminating the 10- to 30-second cold-load delay from disk [37, 39].
- **Streaming Pass-Through:** Reverse proxies must disable HTTP buffering (`proxy_buffering off`) and raise socket read timeouts (`proxy_read_timeout 600s`) to prevent prematurely severing Server-Sent Events (SSE) token streams [36, 40].
- **Circuit Breakers:** Gateways track failure counters (`allowed_fails: 3`). If a node fails three consecutive health checks or requests, it is placed in a cooldown state (`cooldown_time: 30s`), and incoming traffic falls back to secondary nodes [41, 42].

### 1.6 LocalAI Federation & P2P Mode

LocalAI provides native multi-node clustering with two distinct operating modes backed by `libp2p` [43, 44]:

- **Federated Mode (Task-Level Balancing):** Autonomous LocalAI instances join a P2P swarm. Requests arriving at any node are proxied to the least-busy instance hosting the requested model [43, 44].
- **Worker Mode (Model Sharding):** A coordinator partitions model layers across worker nodes using backends such as `llama.cpp` RPC or distributed MLX [43, 45].
- **Security & Pairing:** Nodes authenticate using a pre-shared cluster secret (`LOCALAI_P2P_TOKEN`) and can be segmented into isolated virtual swarms using `LOCALAI_P2P_NETWORK_ID` [44, 46]. Transport connections are encrypted end-to-end via Noise or TLS 1.3 within `libp2p` [47].

## 2. Splitting a Model Across Machines vs. Routing Whole Jobs

A central architectural decision for KesherAI is whether to split a single model across the main PC and laptop, or to route entire jobs and models to dedicated machines.

### 2.1 The Mathematics of Parallelism Over Consumer Networks

#### 2.1.1 Tensor Parallelism (TP)
Tensor Parallelism splits individual weight matrices (Multi-Head Attention and Feed-Forward Networks) horizontally or vertically across GPUs [48].
- **Communication Frequency:** In standard transformer architectures (such as Megatron-LM), each transformer layer requires **2 All-Reduce operations** in the forward pass (one for self-attention, one for MLP) [48, 49].
- **Total Operations Per Token:** For an $L$-layer model, generating a single token requires:
  $$\text{SyncOps}_{\text{token}} = 2 \times L$$
  For Llama-3.1-70B ($L = 80$ layers), generating **one single token** requires **160 All-Reduce network synchronizations** [48, 49].
- **Network Overhead Calculation:**
  On a consumer Gigabit Ethernet network, ping round-trip time (RTT) is typically $t_{\text{RTT}} \approx 1.0\text{ ms}$. Over Wi-Fi, RTT fluctuates between $10\text{ ms}$ and $35\text{ ms}$.
  $$\text{Latency}_{\text{Ethernet}} = 160 \times 1.0\text{ ms} = 160\text{ ms/token} \implies \text{Throughput} \le 6.25\text{ tokens/sec}$$
  $$\text{Latency}_{\text{Wi-Fi}} = 160 \times 20.0\text{ ms} = 3,200\text{ ms/token} \implies \text{Throughput} \le 0.31\text{ tokens/sec}$$
- **Conclusion:** Tensor Parallelism requires intra-node microsecond interconnects (NVIDIA NVLink at $900\text{ GB/s}$ to $1.8\text{ TB/s}$, or direct Thunderbolt 5 RDMA) [14, 48]. Executing Tensor Parallelism over a standard home LAN or Wi-Fi is physically non-viable.

#### 2.1.2 Pipeline Parallelism (PP)
Pipeline Parallelism splits the model sequentially into $K$ stages across $K$ machines (e.g., layers $1\dots40$ on the main PC, layers $41\dots80$ on the laptop) [48, 50].
- **Communication Pattern:** Data is exchanged exclusively at stage boundaries via point-to-point transfers [48, 50]. For $K$ machines, there are only $K-1$ boundary handoffs per forward pass [48].
- **Activation Payload Size:** During autoregressive generation (batch size $B = 1$, sequence step $S = 1$), the transmitted payload is the hidden state vector:
  $$\text{Payload} = B \times S \times d_{\text{model}} \times \text{sizeof}(\text{dtype})$$
  For Llama-3.1-70B ($d_{\text{model}} = 8,192$, using 16-bit float $\text{dtype} = 2\text{ bytes}$):
  $$\text{Payload} = 1 \times 1 \times 8,192 \times 2 = 16,384\text{ bytes} \approx 16\text{ KB}$$
- **Transmission Latency:** Transferring 16 KB over a 1 Gbps LAN ($125\text{ MB/s}$) takes:
  $$t_{\text{transfer}} = \frac{16\text{ KB}}{125\text{ MB/s}} \approx 0.13\text{ ms}$$
  Adding link RTT ($1.0\text{ ms}$), the boundary handoff takes $\approx 1.13\text{ ms}$. For two machines ($K = 2$), network overhead adds only $\approx 1.5\text{ ms}$ per token.

#### 2.1.3 The Fatal Flaws of Pipeline Parallelism on Consumer Devices
While the theoretical network transfer overhead for Pipeline Parallelism appears manageable, three severe structural barriers emerge in consumer multi-device environments:
1. **The Heterogeneous Straggler Problem (Amdahl's Bottleneck):**
   The main PC features an RTX 3090/4090 GPU delivering $80\text{--}110\text{ tokens/sec}$ on quantized 8B/70B models. The laptop features an integrated GPU or low-TGP mobile chip processing at $8\text{--}12\text{ tokens/sec}$. In a sequential pipeline, the fast desktop GPU must sit 100% idle while waiting for the slow laptop to compute its half of the layers. The overall generation throughput collapses to the speed of the slowest node.
2. **The Single-User Pipeline Bubble:**
   In interactive single-turn chat ($B = 1$), only one pipeline stage can be active at any given millisecond. The theoretical hardware utilization of the cluster is capped at:
   $$\text{Utilization} = \frac{1}{K}$$
   For a 2-node cluster ($K = 2$), exactly 50% of the pooled hardware sits completely idle during inference [48, 50].
3. **Fragility and Cascading Failures:**
   Laptops sleep, close their lids, switch Wi-Fi bands, and throttle on battery power. In a pipeline-parallel configuration, a disruption on the laptop instantly breaks the TCP stream and aborts the desktop's active inference.

### 2.2 Whole-Job Routing (Task & Model-Level Offloading)

Under Whole-Job Routing, complete models and execution graphs are loaded on single machines according to hardware suitability.

```
                          +-----------------------------------+
                          |     Phone / Laptop Client UI      |
                          |  (390px React Mobile / Electron)  |
                          +-----------------+-----------------+
                                            |
                         HTTP / SSE / WS    | Remote Access Token
                         (JSON / Payloads)  | Tailscale / LAN
                                            v
                          +-----------------------------------+
                          |      KesherAI Dispatch Router     |
                          |      (Hardware-Aware Engine)      |
                          +--------+-----------------+--------+
                                   |                 |
                Heavy Tasks        |                 | Lightweight Tasks
                (70B LLM, FLUX,    |                 | (8B Chat, Embeddings,
                 Hunyuan3D, Video) |                 |  Whisper STT)
                                   v                 v
            +------------------------------+   +------------------------------+
            |    Main PC (Worker Rig)      |   |       Laptop Node            |
            | - 24 GB RTX 3090/4090 VRAM   |   | - 6-8 GB Mobile VRAM / CPU   |
            | - Wired 1GbE / Wake-on-LAN   |   | - Battery / Thermal Watchdog |
            | - Full GPU Compute Speed     |   | - Local Edge Fallback        |
            +------------------------------+   +------------------------------+
```

- **Zero Inter-Node Synchronizations During Inference:** Once the prompt is dispatched, all tensor calculations occur over local PCIe and high-speed VRAM buses ($936\text{ GB/s}$ to $1,008\text{ GB/s}$).
- **Streaming Efficiency:** The network transmits only the initial prompt ($<5\text{ KB}$) and outbound text tokens via HTTP Server-Sent Events (SSE) or WebSockets. Even over mobile 4G/5G connections with $80\text{ ms}$ latency, text streaming feels completely instantaneous to the user.
- **Full Compute Saturation:** The 24 GB GPU operates at 100% efficiency without waiting on slower hardware.

### 2.3 Architecture Comparison Matrix

| Evaluation Dimension | Tensor Parallelism (TP) | Pipeline Parallelism (PP) | Whole-Job Routing (KesherAI Target) |
| :--- | :--- | :--- | :--- |
| **Typical Tools** | exo (Thunderbolt RDMA) [1, 14] | exo (LAN), Petals, llama-rpc [18, 28] | LiteLLM, Ollama Herd, LocalAI [36, 43] |
| **Network Synchronization** | $2 \times L$ per token ($160\times$ for 70B) [48] | $K - 1$ per token ($1\times$ for 2 nodes) [48] | **0 per token** (Only initial prompt & SSE tokens) |

| **Impact of Laptop Sleeping** | Immediate cluster crash [7] | Immediate stream abort [7, 21] | **Zero impact** on desktop; tasks run in background |
| **Hardware Heterogeneity** | Fails completely [48] | Throttled to slowest device speed | **Optimal:** Heavy work to 24GB GPU, light to laptop |
| **Power & Battery Impact** | Drains laptop battery rapidly | Heavy laptop battery drain & heat | **Preserves laptop battery; zero drain on phone** |
| **Implementation Complexity** | Extreme (C++/CUDA kernels) | High (Distributed state/KV sync) | Moderate (HTTP Router & Capability Registry) |

## 3. Hardware Profiling & Enforcing "The Laptop Never Gets Heavy Work"

A core design requirement is ensuring that the user's laptop is never subjected to thermal throttling, fan noise, or battery exhaustion from heavy AI workloads when the 24 GB desktop workstation is available.

### 3.1 Hardware Capability Profiling

KesherAI already maintains a device tracking layer in `packages/core/src/devices.ts` that syncs device identity, platform, GPU string, and network presence via Google Drive and local UDP beacons. To achieve intelligent routing, this profile must be extended into a structured capability descriptor:

```typescript
export interface DeviceHardwareProfile {
  id: string;
  name: string;
  platform: NodeJS.Platform;
  tier: "heavy_compute" | "standard_edge" | "low_edge" | "thin_client";
  gpu: {
    name: string;
    vramTotalMb: number;
    vramFreeMb: number;
    cudaComputeCapability?: number;
    metalVersion?: number;
  };
  system: {
    ramTotalMb: number;
    ramFreeMb: number;
    cpuCores: number;
  };
  power: {
    isBatteryPowered: boolean;
    isOnBattery: boolean;
    batteryLevel?: number; // 0.0 - 1.0
  };
  warmModels: string[]; // Models currently loaded in VRAM
  activeJobs: number;
}
```

### 3.2 Multi-Tier Hardware Classification

KesherAI classifies connected nodes into four functional tiers based on physical hardware boundaries:

1. **Tier 1: Heavy Compute Node (Main PC)**
   - *Criteria:* Dedicated NVIDIA GPU with $\ge 16\text{ GB}$ VRAM (e.g., RTX 3090/4090 with 24 GB), wired power, high-throughput cooling.
   - *Allowed Workloads:*
     - Large Language Models: 70B+ Q4/Q5 models, 32B FP16 models, long-context ($32\text{K}\dots128\text{K}$) reasoning tasks.
     - Generative Image & Video: FLUX.1 (Dev/Schnell/Fill requiring $16\text{--}24\text{ GB}$ VRAM), SDXL, Wan 2.1/2.2 video diffusion.
     - 3D Generation: Hunyuan3D-2, Microsoft TRELLIS meshes and Gaussian splats.
     - Long-running Agent Tasks: Recursive coding sessions, Unreal Engine / Unity compilation, heavy build processes.
2. **Tier 2: Standard Edge Node (Laptop on AC Mains)**
   - *Criteria:* Connected to wall power, discrete GPU with $6\text{--}12\text{ GB}$ VRAM or Apple Silicon with $16\text{--}32\text{ GB}$ unified memory.
   - *Allowed Workloads:* 8B LLMs (Llama-3.1-8B, Qwen-2.5-Coder-7B), lightweight diffusion (SD 1.5, SDXL-Turbo), Whisper speech-to-text (Large-v3).
3. **Tier 3: Low-Power Edge Node (Laptop on Battery / Low VRAM)**
   - *Criteria:* Laptop running on battery power, or machine with integrated graphics only ($<4\text{ GB}$ usable VRAM).
   - *Allowed Workloads:* Sub-3B parameter models (SmolLM2-1.7B, Qwen-2.5-1.5B, Llama-3.2-3B), text embeddings (`bge-large`), Whisper Tiny/Base, or **complete delegation to Tier 1**.
4. **Tier 4: Thin Client (Smartphone / Remote Web Client)**
   - *Criteria:* Mobile device, browser tab, or handheld controller.
   - *Allowed Workloads:* **0 local inference**. Operates purely as a UI view and remote command dispatcher.

### 3.3 The "Laptop Guard" Dispatch Policy

KesherAI already incorporates two sophisticated local resource controls in `packages/core/src/`:
- `HeavyGate` (`heavy-gate.ts`): Enforces strict single-concurrency for heavy tasks (Unreal builds, model loading, picture generation) and manages queueing with localized status labels (`waiting for <job>`).
- `MemoryWatchdog` (`memory-watchdog.ts`): Periodically measures V8 heap usage and OS free memory, rejecting new heavy jobs with `LowMemoryError` if free system RAM drops below 10% or heap exceeds 92%.

To guarantee that the laptop never receives heavy work, KesherAI generalizes this gate into a network-aware **Cluster Dispatch Policy**:

```
                       Task Request Submitted
                                 |
                                 v
                     [ Inspect Task Metadata ]
                     - Min VRAM Required (MB)
                     - Estimated Compute TFLOPS
                     - Is Task Flagged "Heavy"?
                                 |
                                 +-----------------------+
                                 |                       |
                     Requires >= 12 GB VRAM      Requires < 6 GB VRAM
                     or Flagged "Heavy"          and Not Flagged Heavy
                                 |                       |
                                 v                       v
                      [ Target Main PC (Tier 1) ]    Can Execute Locally
                                 |                   on Laptop (If on AC)
                 +---------------+---------------+
                 |                               |
          Main PC Online                 Main PC Asleep / Offline
                 |                               |
                 v                               v
        Dispatch Job via HTTP           Trigger Wake-on-LAN (WoL)
        (Stream Tokens Back)            or Display Dual-Language Prompt:
                                        "Main PC is asleep. Wake it up?"
```

#### Policy Enforcement Rules:
1. **Rule 1 (VRAM Hard Ceiling):** If a model or task requires $\ge 12\text{ GB}$ VRAM (such as FLUX, Hunyuan3D, or a 70B LLM), it is strictly prohibited from running on the laptop, regardless of whether the user initiates the chat from the laptop UI.
2. **Rule 2 (Battery Power Intercept):** If the laptop is disconnected from AC power (`power.isOnBattery === true`), all local generative tasks (image diffusion, local LLM execution $>3\text{B}$) are blocked. The dispatch router transparently forwards requests to the desktop PC.
3. **Rule 3 (Local Gate Protection):** If the desktop PC is offline and the user attempts a heavy task on the laptop, the local `HeavyGate` intercepts the request and throws a localized error rather than risking an operating system freeze or thermal shutdown:
   - English: *"This task requires high-end desktop hardware (24 GB VRAM). The primary workstation is currently offline."*
   - Hebrew: *"פעולה זו דורשת מחשב חזק עם 24GB זיכרון מסך. תחנת העבודה הראשית אינה מחוברת כעת."*

## 4. Per-Chat Device Choice & User Experience

A seamless multi-device AI environment must provide transparent user control over where computation takes place, while delivering a unified interface across desktop and mobile form factors.

### 4.1 UI Design & Model Selector Integration

In KesherAI's React interface (`apps/web`), the chat header and model selection menu are enhanced to display device provenance badges alongside model identifiers.

```
+-------------------------------------------------------------------+
|  Chat: Project Level Design                     [ ⚙ Settings ]     |
|                                                                   |
|  Model: [ Llama-3.3-70B (Main PC - RTX 4090)               ▼ ]    |
|         +-------------------------------------------------------+ |
|         | Auto-Route (Recommended by Hardware)                  | |
|         |-------------------------------------------------------| |
|         | Llama-3.3-70B   • Main PC (RTX 4090 - 24GB)   [Online]| |
|         | Qwen-Coder-32B  • Main PC (RTX 4090 - 24GB)   [Online]| |
|         | FLUX.1 Schnell  • Main PC (RTX 4090 - 24GB)   [Online]| |
|         | Llama-3.1-8B    • Laptop (Local Device)       [Active]| |
|         | Whisper Large   • Laptop (Local Device)       [Active]| |
|         | Claude 3.5 Sonnet (Anthropic Cloud)           [Cloud] | |
|         +-------------------------------------------------------+ |
+-------------------------------------------------------------------+
```

#### Dual Modes of Operation:
1. **Auto-Route (Hardware-Aware Intelligent Routing):**
   The default mode. The user simply selects a task or general model class. The router evaluates the cluster state:
   - If the task is a complex coding question or game architecture review, it dispatches to `Llama-3.3-70B` on the Main PC.
   - If the task is a short translation, typo fix, or text summarization and the Main PC is asleep, it executes locally on the laptop's `Llama-3.1-8B` without waking the desktop.
2. **Pinned Device Choice (Manual Override):**
   The user explicitly binds a specific chat session to a particular device (e.g., pinning game asset generation strictly to the Main PC). The chat session entity stores:
   ```typescript
   interface ChatSession {
     id: string;
     title: string;
     pinnedDeviceId?: string; // undefined = auto-route
     preferredModel: string;
     fallbackPolicy: "wait_for_device" | "fallback_to_edge" | "cloud_fallback";
   }
   ```

### 4.2 Mobile Responsiveness (390 px Viewport)

On mobile devices (accessed via the smartphone browser through Cloudflare Tunnel or Tailscale), horizontal screen space is severely restricted. Following KesherAI's core design rules:
- **Device Badging on Mobile:** Rather than wide text banners, compact color-coded dot icons and device badges indicate status:
  - `PC [●]` (Green = Online, Amber = Asleep/Waking, Gray = Offline).
  - Short localized labels: `L("מחשב ראשי", "Main PC")` and `L("לפטופ", "Laptop")`.
- **Non-Blocking Away Banners:** If a chat is pinned to the Main PC and the PC goes to sleep, the mobile interface does not freeze or erase context. It displays an unobtrusive alert bar:
  - Hebrew: `המחשב הראשי במצב שינה. לחץ כאן להערה מרחוק (Wake-on-LAN).`
  - English: `Main PC is asleep. Click here to send Wake-on-LAN.`

## 5. Failure Handling, Disconnects, & Fault Tolerance

Consumer personal networks are inherently dynamic: laptops close, Wi-Fi connections experience packet drops, and desktop computers enter sleep states to conserve energy.

### 5.1 Heartbeat, Presence, & State Discovery

KesherAI already possesses a dual discovery architecture in `packages/core/src/devices.ts`:
1. **Local UDP Beacon (Port 7421):** Every minute (and immediately upon network interface change), each active KesherAI instance broadcasts a UDP packet with tag `kesher-here` and its device ID [lines 81–83, 208–240].
2. **Google Drive Cloud Discovery (`devices.json`):** Instances periodically synchronize their connection URLs (Tailscale HTTPS, Cloudflare Tunnel, and LAN IP addresses) and auth tokens through an encrypted JSON file in the user's private Google Drive storage [lines 498–540].
3. **Presence Notifications:** When a desktop or laptop enters sleep or shutdown, it invokes `/api/devices/announce` with state `"asleep"` and an `AwayNote` summarizing paused downloads and queued tasks [lines 49–58].

### 5.2 Stream Interruption and Reconnection Logic

When streaming tokens from the Main PC to the laptop or phone over Server-Sent Events (SSE) or WebSockets:
- **Connection Heartbeats:** The streaming endpoint emits a comment ping (`: keep-alive\n\n`) every 3 seconds to detect broken TCP sockets.
- **Client Auto-Reconnect:** If the phone temporarily disconnects (e.g., walking out of Wi-Fi range onto 5G):
  - The client retains the chat state and message history up to the last received token offset.
  - The client issues a reconnect request to `/api/chat/stream?session_id=<id>&resume_from=<token_idx>`.
- **Server-Side Buffering:** The host server on the Main PC retains the active response buffer in memory for 60 seconds after a socket drop. If the client reconnects within that window, streaming resumes seamlessly without re-running inference.

### 5.3 Asynchronous Task Decoupling for Generative Jobs

For long-running creative tasks (e.g., generating a batch of 4 FLUX images taking 45 seconds, or a Hunyuan3D mesh taking 3 minutes):
- **Never Tie Task Lifecycle to Client Connection:** The generation request is registered as a persistent background task in KesherAI's `taskInbox` service.
- **Idempotent Polling:** The phone or laptop receives an immediate task token (`task_id: "tsk_8f92a"`). If the user closes their phone or the laptop sleeps mid-generation, the generation continues uninterrupted on the Main PC. Upon reopening the app, the client queries `/api/tasks/status/:id` and downloads the completed asset.

### 5.4 Remote Wake-on-LAN (WoL) Integration

When the user is away from their home desk with their laptop or phone and issues a heavy task:
1. **Magic Packet Transmission:**
   The laptop or a small always-on low-power edge device (e.g., home router or Raspberry Pi, or the laptop when on the same LAN) constructs a standard Wake-on-LAN magic packet consisting of 6 bytes of `0xFF` followed by the Main PC's MAC address repeated 16 times [51, 52]:
   $$\text{MagicPacket} = \underbrace{\text{FF FF FF FF FF FF}}_{6\text{ bytes}} + \underbrace{\text{MAC} + \text{MAC} + \dots + \text{MAC}}_{16 \times 6 = 96\text{ bytes}}$$
   The packet is broadcast via UDP over port 9 to the local subnet (`255.255.255.255:9`) [51].
2. **Coordinated Waking State:**
   While the PC boots and loads KesherAI (typically 15–25 seconds from S3/S5 sleep), the UI displays a dual-language progress ring:
   - Hebrew: `מעיר את המחשב הראשי... המודל ייטען בעוד מספר שניות`
   - English: `Waking Main PC... Model will load in a few seconds`
3. **Automatic Presence Beacon Detection:**
   The moment the Main PC boots, its `startBeacon()` routine emits `kesher-here` on UDP port 7421, and its startup routine announces state `"awake"` to the network. The waiting client detects the beacon, registers the provider, and immediately dispatches the queued task.

## 6. Security & Zero-Trust Local Mesh

Distributing AI execution across multiple devices expands the potential attack surface. Security must be enforced across network transport, authentication, and execution boundaries.

### 6.1 Transport Layer Security & Encrypted Tunnels

- **Zero Unencrypted Public Ports:** Under no circumstances should raw TCP services (such as llama.cpp `rpc-server` on port 50052 or ComfyUI on port 8188) be exposed to public networks or unauthenticated interfaces [23, 34].
- **Encrypted Overlay Networking:**
  - *Tailscale (WireGuard):* KesherAI natively integrates Tailscale [lines 9, 20–22]. All inter-device traffic traversing the internet or local subnets is encrypted point-to-point via WireGuard using Noise protocol handshakes and ChaCha20-Poly1305 authenticated encryption [47].
  - *Cloudflare Tunnels:* Remote access outside the home without a VPN utilizes authenticated Cloudflare HTTPS tunnels, terminating TLS with modern ciphers.

### 6.2 Scoped Authentication & Capability Boundaries

In KesherAI's current architecture, remote computers are registered with an authentication bearer token generated locally and shared exclusively via the user's private Google Drive account (`devices.json`) [lines 20–23, 31–36].

To prevent a compromised edge device (e.g., a phone lost in transit or a compromised laptop) from executing destructive operations on the desktop PC:
- **API Endpoint Sandboxing:** Remote tokens must be strictly scoped to **Inference and Status Endpoints**:
  - Allowed Remote Routes:
    - `POST /v1/chat/completions` (LLM inference)
    - `POST /v1/embeddings` (Text embeddings)
    - `POST /api/comfy/generate` (Sanitized diffusion workflows)
    - `GET /api/tasks/status/:id` (Task tracking)
    - `POST /api/devices/presence` (Presence announcement)
  - Forbidden Remote Routes:
    - `POST /api/terminal/*` / `POST /api/shell/*` (Shell command execution)
    - `DELETE /api/files/*` (Arbitrary file system deletion)
    - `POST /api/tools/execute` (Arbitrary agent tools)
- **Local Confirmation for High-Privilege Actions:** If an agentic chat running from the phone requests file writes or shell commands on the desktop, the action must require explicit approval on the desktop UI or via a one-time push authorization code (`/api/quick-approve/:code`) [lines 57–60].

### 6.3 Model Weight & Serialization Safety

- **SafeTensors and GGUF Exclusivity:**
  Legacy deep learning formats (PyTorch `.pt`, `.bin`, `.ckpt`) rely on Python's `pickle` library, which allows arbitrary code execution upon unpickling. All models loaded across KesherAI nodes must strictly use **SafeTensors** (for diffusion and transformer weights) or **GGUF** (for llama.cpp). Both formats are raw binary tensor mappings that prohibit executable bytecodes.
- **ComfyUI Node Sandboxing:** When accepting workflows dispatched remotely, ComfyUI must execute with `--disable-all-custom-nodes` or restrict execution to vetted core nodes, preventing the injection of malicious custom Python scripts into the graph.

## 7. Disagreements and Trade-offs in Modern Practice

Across the research literature and community engineering discussions over the past 12 months, several key debates persist regarding multi-device AI architectures.

### 7.1 LAN Model Sharding vs. Centralized Workstation Hosting

- **The Sharding Advocates (exo, Petals, DisTorch):**
  Argue that consumer hardware is inherently memory-limited. The only way an enthusiast can run massive models (like Llama-3.1 70B FP16 or DeepSeek 671B MoE) without spending $15,000+ on enterprise server cards is to pool every available gigabyte of VRAM across every PC, Mac, and laptop in the home [1, 28].
- **The Routing Advocates (Ollama Fleet, LiteLLM, vLLM Clusters):**
  Argue that intra-model LAN sharding is an academic novelty that collapses in daily productivity. Network jitter, Wi-Fi latency, and straggler GPUs degrade interactive chat speeds to unusable levels ($<2\text{ tokens/sec}$) [21, 22]. In practice, quantizations (such as GGUF Q4_K_M or EXL2) allow a single modern 24 GB desktop GPU to run high-capability 70B models natively at $15\text{--}25\text{ tokens/sec}$, eliminating the need to incur network latency penalties.
- **The KesherAI Resolution:**
  For KesherAI's target user (a game developer with a 24 GB RTX GPU PC, laptop, and phone), **Whole-Job Routing is vastly superior**. A 24 GB GPU comfortably fits Llama-3.3-70B (Q4_K_M requires $\approx 42\text{ GB}$ system RAM/VRAM offloaded or fits Q3_K_L / 32B models fully in VRAM) and natively executes FLUX Schnell ($12\text{ GB}$). Forcing the laptop into a synchronized pipeline degrades performance without providing functional benefits.

### 7.2 Thunderbolt 5 RDMA as a Specialized Exception

- **The Exception:**
  Sources agree that model sharding across consumer devices *is* performant when devices are linked via **Thunderbolt 4 / 5 or direct 40 GbE interconnects with RDMA support** (e.g., between two Mac Studios or an NVIDIA workstation and a Mac Studio) [11, 14]. Inter-device latency drops below $50\ \mu\text{s}$, allowing tensor parallelism to scale effectively [14].
- **Why It Does Not Apply to the KesherAI Baseline:**
  A mobile laptop and a smartphone connected over household Wi-Fi cannot provide microsecond RDMA channels. Designing KesherAI's core architecture around high-speed point-to-point cables would exclude the phone and create a brittle, tethered laptop experience.

## 8. Conclusion & KesherAI Implementation Blueprint (What to Build First)

### 8.1 Summary Conclusion

Distributing AI workloads across a 24 GB desktop PC, a laptop, and a smartphone should **not** be implemented by slicing individual neural network layers across the local network using brittle tensor or pipeline parallelism. Doing so introduces unacceptable latency, destroys laptop battery life, and creates severe failure vulnerabilities.

Instead, KesherAI must implement a **Hardware-Aware Task & Model Routing Mesh**:
1. The **Main PC (24 GB GPU)** operates as the primary compute workhorse, hosting heavy models (70B LLMs, FLUX diffusion, Hunyuan3D mesh generation, complex agent tasks).
2. The **Laptop** operates as a lightweight satellite, hosting small edge models (8B LLM, Whisper speech transcription) when on AC power, and delegating all heavy tasks to the Main PC.
3. The **Smartphone** operates purely as a secure remote control and streaming client over a 390 px responsive interface.
4. If the Main PC is asleep, the system utilizes **Wake-on-LAN (WoL)** to awaken the desktop on demand, ensuring seamless performance from any room in the house or remotely over the internet.
