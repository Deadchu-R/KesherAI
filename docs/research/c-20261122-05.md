# Playing Game Web Builds on Mobile Phones: Unreal Engine 5.9 Web, Unity WASM64, Streaming vs. Download, and KesherAI Architecture

## Summary

This report provides a comprehensive technical analysis of running modern game engine web builds—specifically **Unreal Engine 5.9 Preview** (native Web target) and **Unity 6** (WebGL/WebGPU and WASM64)—on mobile smartphones (iOS Safari and Android Chrome), served locally or remotely through KesherAI. 

It investigates the current state of Unreal Engine's reintroduced WebAssembly/WebGPU pipeline alongside third-party platforms (SimplyStream by Wonder Interactive), evaluates Unity 6's WebGPU backend and 64-bit WebAssembly (Memory64) heap capabilities, and analyzes the hard constraints of mobile browser environments: iOS Safari Jetsam process termination (typically killing tabs between 350 MB and 1 GB), high-DPI fill rate bottlenecks, missing HTML5 Fullscreen API support on iPhones, and strict audio autoplay policies. It compares client-side WASM execution against WebRTC-based low-latency streaming (Unreal Pixel Streaming and Unity Render Streaming). Finally, it defines the hosting, security, and interface architecture KesherAI must implement to serve, sandbox, and render these games securely on a 390 px mobile viewport.

## 1. Unreal Engine Web Export: Current State and Architecture

### 1.1 Evolution from UE 4.24 to UE 5.8
* **Historical Deprecation:** Epic Games officially deprecated its native HTML5/WebGL 1.0/2.0 deployment pipeline in Unreal Engine 4.24 (2019), transitioning the codebase to an unsupported community repository [2, 3]. For subsequent engine releases (UE 4.25 through UE 5.3), Epic's recommended path for web delivery was strictly remote server rendering via **Pixel Streaming** [2, 10].
* **Third-Party & Community Revival (UE 5.4–5.8):** Between 2024 and 2026, the demand for client-side web deployment without per-minute cloud GPU costs led to specialized platforms:
  * **SimplyStream (Wonder Interactive):** Developed a custom Rendering Hardware Interface (RHI) mapping Unreal Engine rendering commands directly to **WebGPU**, paired with an automated cloud build agent (*Strata*) [2]. SimplyStream compiles C++ project source into 64-bit WebAssembly and streams game assets chunk-by-chunk over HTTP, demonstrating complex scenes (such as Epic's Game Animation Sample with Chaos physics and Motion Matching) running at 60–100+ FPS natively in browser tabs without video streaming [2].
  * **Community WebGPU Forks:** Open-source initiatives (such as `UnrealEngine-WebGPU`) maintained source-level patches for UE 5.4 through 5.8, using Emscripten to compile Slate, physics, and gameplay code to WASM while translating shaders to WebGPU Shading Language (WGSL) [3, 4].

### 1.2 Unreal Engine 5.9 Preview: Native Web Export
Epic Games officially reintroduced native browser-native deployment as an experimental platform target starting in the **Unreal Engine 5.9 Preview** (rolled out during the Epic MegaJam cycle) [3, 4].

* **Core Toolchain & Compiler:**
  * Uses the **Emscripten SDK (specifically version 6.0.10)** integrated directly into Unreal Build Tool (UBT) and the Unreal Automation Tool (UAT) [3, 4].
  * Compiles engine C++ code down to WebAssembly (Wasm) [2, 3].
  * Requires a C++ project. Blueprint-only projects cannot be packaged out of the box; developers must add at least one dummy C++ class to generate the necessary build targets and compilation manifests [3, 4].
* **Rendering Architecture (WebGPU RHI):**
  * Replaces legacy WebGL with a dedicated **WebGPU RHI** built over Dawn/Emscripten bindings [3, 4].
  * **Shader Pipeline:** Cooks High-Level Shading Language (HLSL) shaders down to SPIR-V, which are subsequently transpiled into WebGPU Shading Language (WGSL) via Tint [4].
  * **Rendering Tiers:** Because core UE5 desktop features like **Nanite** (virtualized geometry) and **Lumen** (global illumination) require desktop-class DirectX 12/Vulkan hardware features unavailable in the web platform, UE 5.9 adapts Unreal's mobile rendering architecture:
    * *Mobile-Forward:* Targeted automatically at mobile browsers and integrated/low-end graphics hardware [3, 4].
    * *Mobile-Deferred:* Targeted at desktop-class GPUs running modern desktop browsers [3, 4].
* **Operational Constraints and Caveats in UE 5.9:**
  * **Memory Limits:** The preview defaults to 32-bit WebAssembly memory spaces (~2 GB ceiling). Unoptimized projects that exceed this threshold crash the browser tab immediately [2, 3].
  * **Feature Gaps:** Bink video playback, proprietary audio codecs, and specialized post-process compute passes are unsupported [3, 4].
  * **Browser Reference:** Optimized primarily for Chromium-based browsers (Google Chrome, Microsoft Edge) where WebGPU and V8 WebAssembly engines are most mature [3, 4].

## 2. Unity WebGL / WebGPU and WASM64 (Memory64)

### 2.1 Unity 6 Web Platform Upgrades
Unity 6 represents a fundamental overhaul of Unity's web publishing platform, moving web from a desktop-only format to a first-class mobile deployment target [5, 7].

* **Official Mobile Browser Support:**
  * **iOS Safari:** Officially supported on **iOS 15 and newer** [7].
  * **Android Chrome:** Officially supported on **Chrome 58 and newer** [7].
  * Unity 6 integrates native mobile touch interaction, multi-touch gestures, accelerometer/gyroscope reading, and screen orientation handling directly into the Web runtime [7].
* **Experimental WebGPU Backend:**
  * Unity 6 (and subsequent minor updates such as Unity 6.1) includes an experimental **WebGPU graphics backend** [5].
  * In Player Settings (`Project Settings > Player > Web`), developers can configure a fallback hierarchy: placing `WebGPU` at the top and `WebGL 2.0` as the secondary fallback [5].
  * If a mobile browser or device driver does not support WebGPU, Unity 6 falls back transparently to WebGL 2.0 [5].

### 2.2 WASM64 / Memory64 Architecture and Mobile Reality
Unity 6 introduces support for the **WebAssembly 2023 / Memory64** standard, designed to break past the historic 2 GB / 4 GB address space barrier [6].

* **Activation Mechanism:**
  * In Unity 6 Player Settings, setting **Maximum Memory Size** to any value **greater than 4096 MB** (4 GB) automatically enables the Emscripten `-sMEMORY64=1` compiler flag [6].
  * The WebAssembly runtime switches from 32-bit linear memory pointers (`i32`) to 64-bit pointers (`i64`), theoretically scaling up to **16 GB** of heap [6].
* **The Reality of WASM64 on Mobile Phones:**
  * **Desktop vs. Mobile Disconnect:** While WASM64 functions on 64-bit desktop browsers (Chrome, Firefox, Edge on Windows/macOS/Linux), **it is unviable for mobile devices** [6, 8].
  * **The Threading Conflict:** Under current web standards, enabling Memory64 conflicts with WebAssembly multithreading (atomics and `-pthread`), requiring builds to run single-threaded on many platforms [6].
  * **Binary Overhead:** 64-bit pointers increase the size of the compiled `.wasm` binary by 15–25% due to wider address encoding, worsening network download times on mobile connections [6].
  * **OS Memory Enforcement:** Mobile operating systems (iOS and Android) enforce strict per-process memory caps. Any web build attempting to allocate a multi-gigabyte heap on a smartphone will be forcibly terminated by the operating system kernel before the first frame renders [8].

## 3. Mobile Browser Limits, Sizing, and Bottlenecks

### 3.1 Payload Sizes and Network Transfer
Game engine web builds are substantially larger than conventional web applications. Minimizing transfer footprint is critical for mobile networks:

| Engine / Target | Uncompressed WASM + Data | Brotli (`.br`) Compressed | Initial Boot Time (4G / 50 Mbps) | Recommended Asset Strategy |
| :--- | :--- | :--- | :--- | :--- |
| **Unity 6 (Minimal 3D)** | 25–40 MB | 8–12 MB | 2–4 seconds | Single package (`.data` + `.wasm`) [7, 13] |
| **Unity 6 (Standard Mobile Game)** | 60–150 MB | 20–45 MB | 6–12 seconds | Addressables with HTTP Brotli streaming [13] |
| **UE 5.9 Web (Minimal Scene)** | 90–180 MB | 28–50 MB | 8–15 seconds | Core engine WASM + packed PAK [2, 3] |
| **UE 5.9 Web (Game Animation Sample)**| 350–700 MB | 110–220 MB | 30–60 seconds | Chunked HTTP streaming / SimplyStream [2, 4] |

#### Transport & Asset Compression:
* **Brotli vs. Gzip:** Pre-compressing WebAssembly binaries (`.wasm`) and engine data (`.data`, `.pak`) with Brotli (`br`) reduces transfer sizes by **20% to 32%** compared to standard gzip [13].
* **Addressables and AssetBundles on Web:** In Unity WebGL/WebGPU, internal AssetBundle compression **must use LZ4** (chunk-based decompression) rather than LZMA, because LZMA decompresses the entire archive synchronously on the main JavaScript thread, freezing the browser UI [13]. Maximum compression is achieved by applying external Brotli compression at the HTTP server level and caching downloaded bundles in the browser's `IndexedDB` [13].

### 3.2 The iOS Safari Jetsam Memory Ceiling
The most severe constraint when running web games on Apple iOS devices (iPhones) is **Jetsam**, the Darwin kernel's low-level memory manager [8].

* **Per-Process Limit Crash:** When a tab exceeds its allocated memory ceiling, Jetsam issues a `per-process-limit` termination to `com.apple.WebKit.WebContent`. The browser does not catch an Out-Of-Memory exception; the webpage abruptly reloads with the message: *"A problem repeated with this webpage"* [8].
* **Empirical Limits Across Hardware:**
  * *iPhone 8 / SE (2nd Gen) (3–4 GB RAM):* Tab crash at **300 MB – 350 MB** [8].
  * *iPhone 12 / 13 / 14 / 15 Standard (4–6 GB RAM):* Tab crash at **450 MB – 650 MB** [8].
  * *iPhone 15 Pro / 16 Pro (8 GB RAM):* Tab crash at **800 MB – 1.2 GB** [8].
* **VRAM and Backing Store Amplification:** Jetsam counts not just the WebAssembly linear heap, but also WebKit's internal graphics buffers: canvas backing stores, uncompressed texture allocations, and render targets [8, 9]. Creating large textures or failing to explicitly invoke `buffer.destroy()` in WebGPU accelerates memory consumption directly toward the Jetsam termination threshold [9].

### 3.3 High-DPI Displays and Canvas Resolution Scaling
Modern smartphones feature Super Retina and AMOLED screens with high device pixel ratios (`window.devicePixelRatio = 2.0` to `3.5`) [14].

* **The Fill-Rate Trap:** If an engine canvas scales to 100% of the viewport on an iPhone with a 390×844 CSS viewport at `devicePixelRatio = 3.0`, the underlying WebGL/WebGPU render buffer is instantiated at **1170×2532 pixels** (nearly 3 million pixels per pass).
* **Consequences:** Rendering mobile 3D scenes at native 3x resolution immediately saturates mobile GPU fill-rate, causing severe thermal throttling, battery drain, dropped frame rates (dropping from 60 FPS to <20 FPS), and massive VRAM consumption that triggers Jetsam kills.
* **The Solution:** The web wrapper must explicitly clamp `devicePixelRatio` in the engine loader configuration [14]:
  ```javascript
  const isMobile = /iPhone|iPad|Android/i.test(navigator.userAgent);
  const scale = isMobile ? Math.min(window.devicePixelRatio, 1.5) : window.devicePixelRatio;
  ```
  Clamping to 1.25× or 1.5× preserves crisp rendering on mobile screens while reducing pixel shading workload by over 60%.

### 3.4 Fullscreen and Viewport Quirks on iOS vs. Android
* **iOS Safari Fullscreen Incompatibility:** Apple **does not support the HTML5 Fullscreen API (`element.requestFullscreen()`) on iPhones** [14]. Calling `requestFullscreen()` or Unity's `Screen.fullScreen = true` fails silently or throws an exception on iPhone Safari [7, 14].
* **Workarounds on iOS:**
  1. *CSS Full-Viewport Styling:* Applying `position: fixed; inset: 0; width: 100vw; height: 100dvh; overflow: hidden;` forces the canvas to occupy the maximum visible screen space.
  2. *Progressive Web App (PWA) / "Add to Home Screen":* By including Apple-specific mobile meta tags (`<meta name="apple-mobile-web-app-capable" content="yes">`), users who add the page to their iOS Home Screen launch the game as a standalone, borderless app without Safari's navigation or URL bars [14].
* **Android Chrome:** Supports the standard `document.documentElement.requestFullscreen()` API and allows programmatically locking screen orientation via `screen.orientation.lock("landscape")` upon user interaction [14].

### 3.5 Audio Autoplay Restrictions
Both iOS Safari and Android Chrome block web applications from playing audio automatically without prior user interaction.
* In WebAssembly games, the underlying Web Audio `AudioContext` initializes in the `"suspended"` state.
* The hosting web shell must register an event listener on the first user touch (`touchstart` or `pointerdown`) to call `audioContext.resume()` before game audio will output.

### 3.6 Touch Input vs. Pointer Lock
Desktop first-person and third-person camera controls rely on the `PointerLock API` to hide and lock the mouse cursor. Mobile browsers do not support `PointerLock`. Games compiled for the web must either implement native mobile virtual touch joysticks in-engine or rely on a web shell overlay that maps touch drag gestures to synthetic keyboard/mouse inputs.

## 4. Architectural Comparison: Client-Side Web vs. WebRTC Streaming

For a game developer running KesherAI on a home PC and accessing it from a smartphone, two distinct technical pathways exist:

| Architectural Metric | Client-Side Web (Unity WebGL / UE 5.9 Web) | Host Streaming (Unreal Pixel Streaming / Unity Render Streaming) |
| :--- | :--- | :--- |
| **Execution Location** | Phone CPU (WASM) and Phone GPU (WebGL/WebGPU) [2, 5] | Host PC GPU (NVENC/QuickSync) via WebRTC [10, 11] |
| **Initial Load Overhead** | High (20 MB – 200+ MB download) [7, 13] | Instant (0 MB download, ~1–2s WebRTC handshake) [10] |
| **Engine Feature Support** | Mobile shaders only; No Nanite, Lumen, or raytracing [3, 4] | Full PC engine fidelity: Nanite, Lumen, high-res textures [10] |
| **Host PC Workload** | Idle (Host PC serves static files only) | High (Host PC renders game and encodes H.264/HEVC video) [10] |
| **Host PC Requirement** | PC can be off if hosted on Kesher Hub / CDN | PC must be powered on with dedicated GPU active [10] |
| **Network Sensitivity** | Zero after download; playable completely offline | Highly sensitive to packet loss, jitter, and uplink bandwidth [10] |
| **Bandwidth Demand** | One-time download burst | Continuous 10–25 Mbps video stream [10, 11] |
| **Phone Battery & Heat** | Heavy (Continuous 3D WebGPU rendering on phone GPU) | Minimal (Hardware video decoder decoding WebRTC stream) [10] |
| **Input Latency** | Near-zero (local touch processing) | Network RTT + encode/decode (15–45 ms on LAN; 40–90 ms WAN) [10] |
| **Memory Constraint** | Highly vulnerable to iOS Safari Jetsam crashes [8] | Completely immune to phone memory limits (video frame buffer) [10] |

### Synthesis: When to Use Which
* **Client-Side WASM/WebGPU:** Best suited for lightweight indie games, mobile-optimized Unity projects, 2D titles, or scenarios where the developer wants offline playability on the phone without keeping the workstation PC powered on.
* **Host WebRTC Streaming:** Best suited for high-fidelity Unreal Engine 5 projects (utilizing Lumen, high-polygon meshes, complex materials) where mobile packaging is impractical, or for instant testing of PC builds without waiting for a lengthy Web compile pass.

## 5. KesherAI Hosting, Security, and Mobile Interface Architecture

To enable playing game web builds securely on a phone, KesherAI must provide specific HTTP server configurations, security boundaries, and responsive mobile wrappers.

### 5.1 Cross-Origin Isolation (COOP & COEP)
Modern WebAssembly features—specifically multithreading via Web Workers and `SharedArrayBuffer`—require the hosting page to be **Cross-Origin Isolated** [12]. Without these headers, modern browsers completely disable `SharedArrayBuffer` and high-resolution timers:

KesherAI's Fastify static server must serve game build directories with the following response headers:
```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```
*Note on `require-corp` vs. `credentialless`:* When embedding third-party assets (such as web fonts or external CDNs), `Cross-Origin-Embedder-Policy: credentialless` is preferred to allow unauthenticated cross-origin asset loading without triggering CORS blocks [12].

### 5.2 Secure Context (HTTPS) Enforcement
* **The Constraint:** Both **WebGPU** (`navigator.gpu`) and `SharedArrayBuffer` are strictly restricted to **Secure Contexts** (`window.isSecureContext === true`) [5, 12].
* **LAN vs. Tunnel:**
  * If a phone connects over a local network using plain HTTP (e.g., `http://192.168.1.50:port`), mobile browsers mark the connection as insecure. `navigator.gpu` will be `undefined`, and multithreaded WASM will fail to initialize.
  * KesherAI already includes an automated tunnel service (`services.tunnel` using Cloudflare Tunnel / Tailscale Funnel) that assigns an authenticated HTTPS address (e.g., `https://*.trycloudflare.com`). Serving web game builds through this encrypted tunnel guarantees a Secure Context on the phone without requiring local certificate installation.

### 5.3 Static Serving Pipeline in Fastify
Game builds should be isolated under a dedicated route, for example `/api/games/play/:id/`:
* **Brotli & Gzip Handling:** Configure `@fastify/static` or custom stream routing to recognize `.wasm.br`, `.data.br`, and `.bundle.br` files, attaching `Content-Encoding: br` and `Content-Type: application/wasm` or `application/octet-stream`.
* **Byte-Range Requests:** Enable `Accept-Ranges: bytes` to allow audio players and streaming asset loaders to request partial chunks rather than buffering entire multi-megabyte soundbanks upfront.
* **Cache Headers:** Game code and data files should use immutable cache headers (`Cache-Control: public, max-age=31536000, immutable`), while the HTML entrypoint (`index.html`) must use `Cache-Control: no-cache` to ensure updates load immediately.

### 5.4 Sandbox Isolation and API Protection
Because game builds execute arbitrary third-party WebAssembly and JavaScript, they must not have access to KesherAI's internal management API (`/api/`) or sensitive local tokens:
* **Iframe Sandboxing:** Render the game inside an `<iframe>` configured with:
  ```html
  <iframe 
    src="/api/games/play/project-id/" 
    sandbox="allow-scripts allow-same-origin allow-pointer-lock"
    allow="autoplay; fullscreen; xr-spatial-tracking; screen-wake-lock"
  ></iframe>
  ```
* **Origin Separation:** Ensure the game shell does not leak KesherAI's Bearer authentication token to the inner window context.

### 5.5 Mobile Web Player Wrapper (390 px Viewport)
KesherAI's web interface is designed for 390 px mobile viewports. The game runner must provide:
1. **Virtual Touch Overlay:** A toggleable, semi-transparent HTML/SVG overlay providing a virtual analog thumbstick (WASD mapping) and action buttons (Space/Jump, E/Interact, Click/Attack) for games that lack native mobile touch interfaces.
2. **Dynamic DPI Switcher:** A quick settings menu on the player bar allowing the user to select between *Battery / Smooth (1.0x DPI)*, *Balanced (1.5x DPI)*, and *Ultra (Native DPI)*.
3. **Screen Wake Lock:** Utilizing the `navigator.wakeLock.request('screen')` API to prevent the mobile screen from dimming or locking during gameplay.
4. **PWA Standalone Helper:** An iOS detection banner prompting the user to tap *Share > Add to Home Screen* to enable borderless full-screen play on iPhone.

## 6. Implementation Roadmap for KesherAI

### Phase 1: Game Web Host & Secure Context (Immediate Foundation)
* Add a game build directory scanner in `packages/core/src/routes/games.ts` that detects exported WebGL/WebGPU builds within detected project folders (e.g., `<project>/Builds/Web/` or `<project>/Export/HTML5/`).
* Register a specialized Fastify static route `/api/games/builds/:projectId/` configured with:
  * Strict `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: credentialless`.
  * Automatic Brotli pre-compression resolution (`.wasm.br` -> `Content-Encoding: br`).
  * MIME type overrides for `.wasm`, `.data`, and `.pak`.
* Provide a direct launch button on `GamesPage.tsx` that opens the game runner in a secure popup or full-page view.

### Phase 2: Mobile Player Shell (Phone UX & iOS Adaptation)
* Build a responsive mobile game runner component (`apps/web/src/pages/GamePlayer.tsx`):
  * Implement `apple-mobile-web-app-capable` meta tags and standalone PWA detection.
  * Inject a responsive touch overlay (`VirtualControls.tsx`) offering a virtual joystick and action pads mapped to keyboard/mouse events.
  * Clamp `devicePixelRatio` to 1.5 on mobile user agents.
  * Add a one-touch AudioContext unlock listener to ensure seamless audio playback on iOS Safari and Android Chrome.

### Phase 3: Project Web Build Automation (One-Click Export)
* Extend KesherAI's existing `NightBuilds` system (`packages/core/src/routes/games.ts`):
  * Add `"web"` as a target platform alongside `"windows"` and `"android"`.
  * For Unity: Trigger headless batch builds via `Unity.exe -batchmode -quit -executeMethod BuildPipeline.BuildPlayer` targeting `BuildTarget.WebGL`.
  * For Unreal Engine 5.9: Invoke RunUAT (`RunUAT.bat BuildCookRun -project=... -platform=Web -cook -stage -package`).

### Phase 4: Local WebRTC Pixel Streaming Proxy (High-Fidelity Mode)
* For heavy Unreal Engine 5 projects that cannot be reduced to mobile web budgets, implement a WebRTC signaling proxy inside `packages/core/`:
  * Connect to Unreal Engine's built-in Pixel Streaming plugin via WebSocket (`ws://127.0.0.1:8888`).
  * Proxy video streams and input events over WebRTC to mobile clients connected via KesherAI's secure tunnel, enabling instant 60 FPS gameplay with Nanite and Lumen on any smartphone.

## 7. Conclusion

Bringing game builds to mobile browsers bridges a vital gap for local game developers, enabling instant testing and demonstration directly from a smartphone. 

While **Unity 6** now officially supports mobile browsers with experimental WebGPU backends, developers must recognize that **WASM64 (Memory64)** is exclusively a desktop solution; attempting to run multi-gigabyte 64-bit heaps on mobile devices will trigger fatal **iOS Safari Jetsam** process terminations. Similarly, **Unreal Engine 5.9 Preview's** native Web export target unlocks client-side WebGPU execution, but requires strict adherence to mobile-forward rendering pipelines, C++ project configurations, and conservative memory management.

For KesherAI, the recommended path is a hybrid architecture: implementing a **secure, COOP/COEP-isolated static hosting pipeline** with mobile-responsive controls for client-side Unity/Unreal Web builds, supplemented by a **WebRTC Pixel Streaming bridge** for high-fidelity PC builds that exceed mobile hardware limits.
